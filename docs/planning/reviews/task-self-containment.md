# Independent task self-containment review: T01

Reviewed 2026-11-04 against `docs/SLIM_SPEAKER_PLAN.md` T01, `docs/planning/task-catalog.json`, and `docs/SLIM_INTEGRATIONS_DESIGN.md` section 6 / INT-010. Source revision: `9d8d5308d6844c6339283ae088c6cb9bcd2da4da`; planning files were working-tree inputs. No hardware, network, credential or implementation action was performed.

Verdict: **not yet self-contained for independent implementation and closure**. T01 correctly distinguishes native membership from WireGuard and gateways, names E06/P02 dependencies, demands actual measurements, and preserves pending provider qualification. A new implementer can identify the problem, but cannot determine owned outputs or a reproducible pass/fail boundary from the task alone.

## Concrete gaps and repairs

1. **Inputs are task IDs, not artifact contracts.** Specify that E06 supplies pinned candidate revisions/features/licenses and ISA support, and P02 supplies exact target/kernel capability profiles for sockets, clocks, entropy and storage. Link INT-010 and section 6 directly. Missing capabilities must produce an explicit blocked candidate row rather than a guessed fallback.
2. **Owned files are unspecified.** Name a candidate comparison document, a machine-readable profile/measurement manifest, a bounded fixture suite and a receipt directory. Suggested paths are `docs/tailscale/feasibility.md`, `docs/tailscale/profiles.json`, `tests/tailscale-fixtures/`, and `toolchain/results/tailscale/`; these are proposed future outputs, not files created by this review. Keep private keys and real enrollment traffic outside public artifacts.
3. **No resource admission boundary.** For each profile record distinct ISA/ABI/kernel, selected build features, executable size, peak resident/heap/stack accounting, CPU cost and permitted peer/session/churn bounds. Derive admission budgets from the endpoint budget task rather than inventing a tiny footprint. Name the budget dependency or require an explicit provisional budget with unresolved status. Measure under bounded enrollment, network-map change, reconnect, key rotation and relay load, with audio contention represented separately. QEMU timing is guest evidence, not actual board performance.
4. **No concrete protocol matrix.** Carry the section 6 requirements into the task: own identity, enrollment, network-map updates, policy denial, discovery/NAT, relay fallback, revocation/key rotation, persistence and diagnostics. Compare official-client and Rust candidate approaches per row, separating source support, fixture results and actual interoperability receipts. Unsupported candidates remain explicit without dropping native scope.
5. **No reproducible fixture recipe.** Require synthetic credentials and offline enrollment/network-map fixtures covering success, malformed/stale updates, denied access, expired/revoked identities, reconnect and bounded peer churn. Fixtures test parser/state-machine behavior only. External provider enrollment and real target measurements remain separately authorized qualifications and cannot be inferred from mock success.
6. **Closure mixes feasibility with implementation.** Define T01 output as a supported candidate decision plus measurements and residual qualification matrix. It may finish an offline feasibility decision with a native candidate blocked, provided T02 remains blocked and the native requirement remains open. It must not call that native support delivered. If exact-target execution is unavailable, record the exact missing environment and avoid declaring the measurement acceptance passed.

## Ready-to-use acceptance refinement

T01 is ready to close as an **offline feasibility assessment** when each required endpoint profile has a pinned candidate comparison; a complete identity/control/data-plane capability matrix; reproducible per-ISA build and permitted guest measurement receipts or explicit unavailable-environment outcomes; declared resource limits and measured maxima; negative fixture results; and an admitted/blocked decision with reasons. Gateway, proxy and WireGuard-only cases are separately labeled. An admitted offline candidate is eligible for T02 implementation; native product acceptance still requires separately authorized end-to-end interoperability and board qualification.

The existing E06/P02 edges correctly constrain implementation feasibility, but a desk/source comparison can begin earlier. Avoid blocking all inexpensive source research on a completed platform layer. Preserve the stronger dependency for measured target admission.

## Audit boundary

This review does not establish official-client availability, licensing acceptability, target fit, service interoperability, or legacy-kernel compatibility. It evaluates whether T01 supplies enough local instructions to produce honest evidence. The changes above are recommended task refinements; this reviewer did not edit the plan, catalog, product code or canonical claim ledger.
