# Q01 contract: the offline Virtual House harness (`ffw-gmq`)

Bead `ffw-gmq`. Code: `crates/franken-speaker/src/harness.rs` (the campaign, the nodes, the oracles, the planted faults and their tests),
`playout_adapter.rs` (the N04 engine and N01 framing inside the campaign), `clock_log.rs` (the N03 clock diagnostics), and
`control_adapter.rs` (the G03 endpoint and N02 channel inside the campaign). All four are compiled only for unit tests or with the
off-by-default `harness` feature of `franken-speaker`, so a device build carries none of them. Entry point: `franken-speaker
--virtual-house` (or `--self-test`), built with `--features harness`: seed `0x2026_1104`, 250 blocks, one campaign.

Status: **offline simulation only; slices 1 to 4 of the harness are in the tree, and this document states what they do and, below,
what they do not.** Nothing here touches a device, a provider account or a network. The pieces this document adds with it (section 6,
limit 1: the `Asymmetric` source, its question and its planted fault) were written before they were compiled; the evidence level of any
claim is the judged central run recorded in the tracker, not this document. The bead stays **open**: section 8 lists what is missing.

## 1. What this is, and what it is not

A deterministic, seeded simulation of a house of five speakers of mixed generations streaming one source in lock step: the real
production code of the group, stream, clock, playout, control and DSP layers, driven over simulated links and simulated node clocks,
and judged by oracles that do not take the production code's word for what it did.

* **A test harness, not a product path.** It links `franken-test-support` (network impairment schedules, continuity, fencing and
  readiness oracles, a redacting diagnostic sink). A default build has no dependency edge onto it.
* **Simulation evidence only.** Every report says `simulation_only: true`. Nothing here is evidence about hardware, a stock kernel,
  a provider, a network, or what any real board sounds like. Hardware and provider claims need separate authorized receipts.
* **A check of samples and state, not of log strings alone.** Each claim below names the oracle that makes it and the faults that
  oracle is shown to catch.

## 2. The house

Five members, from the synthetic test fixture catalog (`synthetic_test_fixture_catalog`), each with its own simulated node clock
(an offset and a skew against true time) and its own seeded network schedule:

| member | board | hardware channels, as the profile routes them |
|---|---|---|
| `spk-office-s5` | S5 | 5: `TweeterLeft`, `TweeterRight`, `MidLeft`, `MidRight`, `WooferCenter` |
| `spk-bedroom-s1` | S1 | 2: `WooferMono`, `TweeterMono` |
| `spk-kitchen-s12` | S12 (the coordinator) | 2: `WooferMono`, `TweeterMono` |
| `spk-den-s3` | S3 | 3: `MidLeft`, `MidRight`, `TweeterMono` |
| `spk-living-sub` | Sub | 1: `SubwooferLfe` |

A left- or right-routed channel is fed the left or the right channel of the source; every other role is fed the mono mix
`0.5 * (l + r)` (`franken-dsp`, `BoardProtectionDsp::render_block`). That one fact decides limit 1 below.

## 3. Real and simulated

| real (the production code, unchanged) | simulated |
|---|---|
| N01 negotiation, `StreamSender`, `StreamReceiver` | the network (delay, loss, reorder, duplication: a seeded schedule per member) |
| N04 `PlayoutEngine`, one engine per stream generation | each node's own monotonic clock and its skew |
| N03 `GroupClock` and the audible gate | entropy (nonces, stream ids): deterministic stand-ins, **not entropy** |
| G01 `UnifiedGroupSession`, `SourceArbiter`, authority tokens | the boards (fixture profiles, not measurements) |
| G03 `Endpoint`, N02 `ControlChannel`, `PeerDirectory` (HMAC proofs) | the keys (public fixtures) and the controllers' transports |
| `BoardProtectionDsp` and the resampler | the HAL: a virtual device (`AudioHalDevice`), no hardware |

## 4. The oracles, and what each can and cannot see

| oracle | what it judges | what it cannot see |
|---|---|---|
| continuity and shadow (`SampleContinuityOracle`, `ShadowReference`) | every channel of every block, frame by frame, against a second render of the SAME input | a fault that hands both renders the same wrong input; the DSP's own arithmetic (it is a handoff check, not a check of D01/D02) |
| fencing (`FencedCommandOracle`, `CommandAudit`) | a fresh, a duplicate, a stale and a new-authority command, judged by an epoch and a record kept by the harness, not the session | commands that do not go through `CommandAudit` (the channel's own and the reference sets); it compares no revisions |
| readiness (`ReadinessOracle`) | each node's readiness state against the clock, board and amplifier observations the harness feeds it | anything the harness does not observe |
| N04 decisions | every block position is decided exactly once; a block played as real carries exactly the bytes the sender sent (FNV-1a taken at send time) | concealment quality |
| source arbiter (slice 3) | one owner at a time; a replaced adapter's publishes are refused (`SOURCE_REPLACED`, `SOURCE_EPOCH_STALE`); a datagram of a replaced stream is refused by the rebound receiver; the program each block carried is read from the bytes that sounded | a "state revision unchanged" check: `SourceArbiter::submit` takes the session by `&`, so such a check is vacuous, and the receipts are asserted instead |
| control model (slice 4) | each delivery's HTTP status, `NewVolume` and UPnP error code, and the session's (revision, member volume, group volume), against `VolumeModel`, which restates `g03.md` 3.1 and 9.1 and `n02.md` (the expected numbers in the tests were computed from those rules by a throwaway script kept outside the repository; it is not a gate) | the ledger's 30 s retention (not modelled; a campaign lasts about a second) |
| rendered-sound digest (slice 4) | a race of relative-volume steps must render exactly the samples of a reference that sets the same volumes directly (`output_fnv1a64`, FNV-1a over every rendered i16); a reference with one wrong volume must differ | a member that renders silence (limit 1); the absolute level of any block (limit 5) |
| rendered-something (this document, limit 1) | under the `Asymmetric` source, a member that sounded authentic audio rendered at least one non-zero sample | the original `Opposed` source (not asked there, by design) |

`--virtual-house` exits 0 when the fleet is a unified mixed S1/S2 group, the skew target was met by a measurement, the video-sync
bound holds and the evidence is complete (`virtual_house_passes` in `main.rs`). **It asserts nothing about the content of any
rendered sample.**

## 5. Planted faults

A planted fault is a defect injected into the campaign by a test (`OutputFault`, constructed only by tests). A fault only counts as
caught when its unplanted control passes first and the plant then fails for the planted reason.

| fault | what it does | what catches it |
|---|---|---|
| `CorruptSample` | flips one sample of one member's rendered block | the shadow comparison |
| `DropFinalBlock` | a member never produces its last block | the tail check (every channel must have produced every block) |
| `UnadmittedExcept` | the controller admits one member only, so the others stay muted | the skew gate: an unmeasured skew is not a pass |
| `LateBlock`, `ReorderedPair`, `StaleEpochPacket`, `ClockLeap` | a block arrives late, two swap arrival order, a previous-epoch datagram arrives, a node's clock leaps | each is judged against an independent model of the engine, member by member (`run_planted_in` in the unit tests) |
| `ReplacedSourceKeepsPublishing`, `StaleStreamDatagram` | a replaced adapter keeps publishing; a datagram of the replaced stream reaches a rebound receiver | the publish gate; the receiver's refusal |
| `TailnetRetryAsNewCommand` | a tailnet client retries a relative step under a new command number | `volume_response_mismatch: step 0 send 1:` |
| `TailnetStaleRevisionRefreshed` | a client names the current revision on a step the contract says is stale | `volume_response_mismatch: step 2 send 0:` |
| `SilentInput` | both DSPs are handed silence where the member's audio was delivered, and the block is still counted as having sounded | `member_rendered_silence: <member>:` under the `Asymmetric` source; **nothing** under the original one (`without_the_new_question_a_member_handed_silence_passes_every_other_oracle` is written to show exactly that; it has not run yet) |

The two tailnet faults are on the CLIENT side. The endpoint's own planted defects are `cfg(test)` inside `franken-control` and cannot
be reached from this crate; they are exercised by that crate's own tests (`g03.md` section 9.1).

## 6. Limits

These are limits of the evidence, stated as limits. None of them is a pass.

1. **Mono-routed members render silence under the original source.** The campaign's original source is `left = amp`, `right = -amp`
   (`SourceSignal::Opposed`), so the mono mix is exactly zero. A member whose every channel comes from that mix renders only zeros at
   any volume: `spk-kitchen-s12` (S12) was **measured** doing so (its output digest was exactly the digest of 400 blocks of silence on
   two channels, `5755000421370241829`; the `rendered_nonzero_blocks` counter that states it directly is new and not yet run);
   `spk-bedroom-s1` (S1) and `spk-living-sub` (Sub) have the same routing and are silent **by routing, not yet measured**. For those members, in every campaign with the original source, the
   continuity and shadow oracles compare zeros with zeros and the digest cannot tell one volume from another, so **no claim about
   what those members render is made by any assertion that uses the original source**. S5 was measured rendering the signal (the
   digest tests pass through it); S3 renders by routing (`MidLeft`, `MidRight`).
   The `Asymmetric` source (`right = 0.5 * left`, mono mix `0.75 * left`) gives every member something to render. Under it the
   campaign also asks, of every member that sounded authentic audio, that it rendered at least one non-zero sample, and `SilentInput`
   shows the question catches a member the other oracles cannot. The original source is untouched: every existing assertion, and
   every existing digest, is about it and is unchanged. The new scenarios are the ones that name `Asymmetric`.
2. **The shadow render shares the production DSP and its input.** A fault that is the same in both (a wrong input, a wrong gain
   applied to both) is invisible to continuity and shadow; this is why the digest comparison and the rendered-something question exist.
3. **The old SOAP skeleton is still exercised.** Every default campaign ends with a `handle_fsonos_soap` group-volume call (the
   superseded skeleton without authentication, lease or ledger, `g03.md` section 9). Slice 4 does not retire it; the real endpoint is
   driven only by a scenario that has a volume plan.
4. **Time, keys, entropy and boards are synthetic.** Node clocks, networks, keys, nonces and stream ids are simulated; the boards are
   fixture profiles. The ledger's retention is not modelled.
5. **No absolute level is asserted.** The DSP applies gain before the per-channel crossover filters and ramps it linearly within a
   block, so "volume 0 is exactly silent" is not safe to assert; sample evidence for volume is relative (a race against a reference
   that reaches the same volumes), never a level.
6. **Concealment quality, audio codecs, provider streams, AirPlay and Spotify transports, and every real network are out of scope.**
   The source arbiter is driven by simulated adapters; no real transport is involved.

## 7. Running it

Central, as the supervisor runs them (`rch` workers; never on the orchestrator):

* `cargo clippy -p franken-speaker --features harness --all-targets --locked -- -D warnings`
* `cargo test -p franken-speaker --features harness --lib --locked`
* `franken-speaker --virtual-house` built with `--features harness`: one campaign; exit 0 only under the gates in section 4.
