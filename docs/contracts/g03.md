# G03: the `fsonos` compatibility adapter (`ffw-xvv`)

Slice 1: the bounded server side. **Offline only.** Nothing here opens a socket, reads a clock, talks to
a device, or has been run against a real `fsonos` client.

## 2. What is being preserved

The wire contract is that of the `fsonos` controller side, `fsonos-proto` rev `775b08dc`, read from a
sibling checkout. It is an async client built on its own runtime, sockets and an XML library; it
cannot be a dependency of this workspace and cannot run in process, so nothing was reused from it. What
was taken from it is the shape of the messages, by reading:

* SOAP 1.1: an envelope whose body holds one `<u:Action xmlns:u="<service URN>">` with flat text
  arguments, and a `SOAPACTION: "<urn>#<Action>"` header; a response element `<Action>Response`; a
  fault whose `detail/UPnPError` carries `errorCode` and `errorDescription`.
* Services `RenderingControl`, `GroupRenderingControl`, `AVTransport`, `ZoneGroupTopology` and
  `ContentDirectory`, each `:1`, at the control and event paths in `soap.rs`.
* GENA: `SUBSCRIBE` with `CALLBACK`, `NT: upnp:event` and `TIMEOUT: Second-N`; renewal with `SID` and
  `TIMEOUT` only; `NOTIFY` bodies shaped `e:propertyset`, `SEQ` 0 first; `LastChange` documents for
  `RenderingControl` and `AVTransport`, plain properties for `GroupRenderingControl` and
  `ZoneGroupTopology`.
* The `ZoneGroupState` document: a `ZoneGroup` with a `Coordinator`, and members with `UUID` and
  `Location`.

## 3. Access policy (declared)

| Ingress | Reads (`Get*`) | Events | Commands |
|---|---|---|---|
| `LocalLegacy` | yes | yes | yes, as the local legacy bridge, unless `legacy_commands` is off |
| `Tailnet` | no (`401`) | no (`401`) | only with a valid command authorization |

* **Local legacy SOAP** is plain UPnP and has no authentication. It is for a link the owner has chosen
  to trust as a LAN. The transport decides which ingress a connection is; it must never present a
  tailnet connection as `LocalLegacy`, and must not bind the legacy listener to the tailnet interface.
  This is the compatibility surface the bead asks for, and no more.
* **Tailnet ingress** accepts nothing that is not an authenticated command. A tailnet request that
  is a read, an event subscription, a deferred action, an unknown action or the retired catalog is the
  same `401` with no body, so an unauthenticated peer learns nothing about the matrix.
* **A command's authorization** is the N02 request authorization: `X-Franken-Peer`, `X-Franken-Seq` (the
  command id), `X-Franken-Epoch`, `X-Franken-Revision` (the revision last read; mandatory for a
  relative change and for a set from a controller) and `X-Franken-Proof`, a hex HMAC over
  `RequestBody::signing_bytes`. The endpoint **rebuilds the command from the SOAP body**, so the proof
  covers what the body asks for and a changed argument fails authentication. A stop also carries
  `X-Franken-Now-Ns` and `X-Franken-Dma-Tail-Ns`, which are part of the signed command. Any problem with
  these headers is the same `401`.
* **Local legacy commands** carry no command id, so each is a new command from the configured bridge
  peer (a controller admitted to the channel's directory with its own key), signed by the endpoint at
  the current epoch and revision. Absolute changes are safe to repeat. **Relative changes
  (`SetRelativeVolume`, `SetRelativeGroupVolume`) are accepted, and a plain-SOAP retry applies again**
  (section 3.1).
* The legacy bridge is rate-limited, lease-checked and ledgered like any peer. A LAN flood is bounded by
  N02's per-peer limit and cannot use the local user's reserved priority slots.
* Events are offered on the local link only: there is no authenticated read to subscribe to over the
  tailnet.

### 3.1 The retry hazard of relative changes

`SetRelativeVolume` and `SetRelativeGroupVolume` are used by the observed controller, so they are
implemented rather than refused: a fault where the client expects success is a capability gap, not
safety. They are not repeatable. Plain SOAP carries no idempotency token, so over the local link the
same request sent twice is two steps (a controller that retries after a lost response moves the volume
twice). The hardware these controllers already talk to has the same property. It is bounded here:

* the result is **clamped to 0..=100** (by the control channel), and the **resulting volume is returned**
  as `NewVolume`, as the action specifies, so a controller that reads the response sees where it ended;
* the **tailnet route is deduplicated**: its command number is the command id, so a retried step with
  the same id is answered from the ledger and applied once, and a step must name the exact revision it
  was computed against;
* two tests pin both sides: a plain-SOAP retry applies twice
  (`a_plain_soap_retry_of_a_relative_change_applies_twice_and_that_is_pinned`), and a retry with the same
  command id applies once (`a_retried_relative_step_with_the_same_command_id_applies_once`).

## 5. Bounds (provisional, unmeasured)

The bead names no numbers. These are starting points, set in code, and every one is a bound:

| Bound | Value |
|---|---|
| Request body | 8 KiB, checked before decoding or allocating |
| Element depth / elements / attributes per element | 8 / 64 / 8 |
| Name length / decoded value length | 64 / 1024 |
| Arguments per action | 16 |
| Subscriptions | 16 |
| Subscription timeout | clamped to 30 s to 3600 s; default 300 s; `infinite` is the default |
| Callback length | 256 |

The XML reader refuses DTDs, entity declarations, comments, CDATA and processing instructions outright
and decodes only the five predefined entities and numeric references, so billion-laughs and external
entity attacks cannot be expressed. Nothing a peer sent is copied into a fault or a header: faults say
fixed words.

## 6. Faults

| Fault | HTTP | UPnP | Body |
|---|---|---|---|
| over the size limit | 413 | none | none |
| not a well-formed SOAP call | 400 | none | none |
| XML this endpoint does not accept | 400 | none | none |
| no such action | 500 | 401 | fault |
| invalid arguments (with the broken rule) | 500 | 402 | fault |
| action failed (with the reason) | 500 | 501 | fault |
| optional action not implemented | 500 | 602 | fault |
| a retried command number the channel forgot (outcome unknown) | 500 | 801 (UPnP vendor range) | fault |
| not authenticated | 401 | none | none |

Fault `801` ("Command Outcome Unknown (read the state)") is the typed answer to a retry whose
outcome has aged out of the control channel's ledger: the command number is at or below the peer's
floor and no longer on record. It means *unknown*: the command may or may not have been applied, it
will **not** be applied now, and the sender reads the state and decides. It is never a success and
never a re-application. It can only arise on the authenticated tailnet route, whose command number
is client-supplied.

`ActionFailed` reasons are fixed phrases such as "the group lease is not live; retry later" or "queued
behind other work; read the state to see whether it applied". A command that was queued and not yet
applied is a fault that says so; it is never reported as success.

## 7. Eventing

* **Subscribe**: `NT` must be `upnp:event`; `CALLBACK` must be exactly one `http://` URL whose host is an
  **IP literal equal to the address the request came from**. UPnP lets a subscriber name another host;
  this endpoint does not, so it cannot be made to send notifications to a third party. A bad callback
  or `NT` is `412`; a bad `TIMEOUT` is `400`; a full table is `503`; `ContentDirectory` is `501`.
* **Renew**: `SID` and `TIMEOUT` only; `CALLBACK` or `NT` makes it `400`. An unknown, expired or
  other-service `SID` is `412`, and the controller subscribes afresh. The new timeout runs from now.
* **Expiry**: exact. A subscription is live one nanosecond before its expiry and gone at it. Expired
  subscriptions are removed the next time anything touches the table.
* **SID**: `uuid:<nonce>-0000-4000-8000-<counter>`, synthetic. The nonce changes with each incarnation, so
  an id from before a restart can never be renewed by accident.
* **Events carry the state revision**: every body has `FrankenStateRevision` and `FrankenEpoch` as extra
  plain properties. A controller that does not know them ignores them.
* **Deltas**: each subscription remembers what it was last told. An event holds only what changed since
  then, so a late subscriber and an early one are each kept consistent. An unchanged state sends nothing.
  An endpoint that is not in the group reports no volume and no mute, and sends nothing false.
* **SEQ**: 0 for the initial full-state event, then +1; after `4294967295` it wraps to **1**, never to
  0.

Nothing here sends a `NOTIFY`: `Handled::notifications` is returned to the owner, who delivers it,
and who decides what to do when delivery fails.

## 8. Reads

Reads are of the live session at the moment they are asked, never of a copy, so a read cannot be stale
topology. Two things the session does not know are the owner's to supply: the transport state (the
session has no source model) and the `Directory` of device locations and room names. A member with no
location is listed with an empty one. `GetTransportInfo` reports the owner's state, which starts as
`NO_MEDIA_PRESENT`.

## 9. Every command is an N02 command

A SOAP action that changes the group is mapped to a `ControlCommand` and submitted to the
`ControlChannel`. N02's guarantees therefore apply: authentication first, the per-peer rate limit, the
bounded queues, G01's lease check, the epoch and revision checks, and exactly-once application by
command number. Nothing in `fsonos` writes to the session. The handler steps the channel up to
`step_rounds` times looking for its own command's outcome; the settlements of other peers' commands
that the same step produced are handed back in `Handled::settled_others`, so they are not lost.

The earlier skeleton `handle_fsonos_soap` in `franken-control/src/lib.rs` calls the session directly,
without authentication, a lease or a ledger. It is **superseded** by this module and is not a path
the adapter uses. Removing it belongs to the owner of `lib.rs`.

### 9.1 Drop the ack, retry through the adapter (N02 acceptance row 8)

A state-changing request commits, its response is lost, and the client sends the same request again.
Through the adapter, on the authenticated route:

* **Within retention** the retry is answered from the ledger with the committed result (`200`, the same
  body) and the group shows a single application: the state revision advances once, and a command that
  another controller sent in between is not undone.
  `a_dropped_ack_then_a_retry_through_the_adapter_is_one_effect`.
* **After retention** the retry gets fault `801`, outcome unknown, with no effect, for an absolute set and
  for a relative step alike. A fresh command number then works.
  `after_retention_a_retry_through_the_adapter_is_a_typed_out_of_window_fault`,
  `a_relative_step_retried_after_retention_is_unknown_and_never_applied_again`.
* **After a channel restart** (a new channel on the same session: empty ledger, no floors) the old copy
  is refused by the session's revision, not re-applied.
  `a_retry_that_outlives_a_channel_restart_is_refused_not_reapplied`. This replaces the channel, not the
  process.
* **Relative changes over plain SOAP** are still not repeatable: with no command id, the same request is a
  new step. That is the documented behaviour (section 3.1), pinned by
  `a_plain_soap_retry_of_a_relative_change_applies_twice_and_that_is_pinned`, which fails if it ever
  changes quietly. The exactly-once case is the command-id route.

The two judges that decide "one effect" and "unknown after retention" are plain functions over a rig.
Each is shown to pass the real adapter and to fail an adapter with a planted defect, built into test
binaries only: `ReapplyOnRetry` (the adapter throws the ledger's answer away and applies the command
again) fails the first judge with `RETRY-REAPPLIED`, and `SuccessAfterRetention` (a fabricated success
where the outcome is unknown) fails the second with `NO-TYPED-FAULT`. Each plant leaves the other judge
satisfied, so the plant is what failed it.

What this does not show: a socket, an HTTP framing or a real `fsonos` client (section 11 item 1), or any
adapter other than this one; there is no other adapter yet.

## 11. Open

1. **An actual `fsonos` client against this endpoint: OPEN.** No stand-in is presented as one. To close
   it, a build of the real client would have to talk to this endpoint over a loopback transport, which
   needs: a transport shim that owns sockets (this crate has none by design); the `fsonos` checkout
   available to the test host (it is an external path dependency that the remote builders do not have);
   and an authorized loopback-only run recorded with its exact revisions. Until then the evidence is the
   source-transcribed vectors above and nothing else.
2. **SSDP discovery and the device description**: not started. The bead's "minimum actually-used SSDP
   descriptions" needs a synthetic description, since real ones are site data and stay in the ignored
   local area.
3. **Join and leave, coordinator delegation, playback and queue actions, tone, sleep timer**: deferred
   rows in section 4, each with what it waits for.
4. **Authenticated reads and eventing over the tailnet**: no authenticated read format exists. Until it
   does, a tailnet controller learns the revision it must name from another path (N02's diagnostics).
5. **Delivery of `NOTIFY`**, retry and the point at which an unreachable subscriber is dropped: the
   owner's, with the transport.
6. **Wiring**: `pub mod fsonos;` in `franken-control/src/lib.rs`, and retiring the skeleton there.
7. **Relative changes over plain SOAP are not repeatable** (section 3.1). Accepted deliberately, not hidden.
8. **Bounds** are unmeasured starting points.
9. **No server-level model**: the policy table in section 3 is checked by Rust tests only.
