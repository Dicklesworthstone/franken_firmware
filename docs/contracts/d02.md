# D02 contract: board protection DSP (`ffw-7s0`)

Scope: per-board crossover/EQ, gain ceilings, limiter, DC rejection, ramps, and fault-mute parameter
loading. Code: `crates/franken-dsp/src/protection.rs` and `protection/{calibration,runtime}.rs`.
Offline and host-only.

**Numerical tests do not prove physical protection.** Everything here is validated against synthetic
fixtures and an independent numerical reference. No real board coefficients exist in this repository,
none are invented, and the calibration produced by `synthetic_calibration_for` says it is synthetic.
Acoustic and electrical qualification is a separate receipt that this module can reference but never
replace. Verification status lives on the bead, not in this file.

## Admission: who may produce audio

`ProtectedBoardDsp::admit(profile, calibration: Option<&BoardCalibration>, admission)` never fails. It
returns a board that is either `Active` or **fail-muted**: it renders silence, ramps any live output to
silence, and `set_muted(false)` returns `unmute_refused`.

| Mode | Profile must be | Calibration must be |
|---|---|---|
| `Production` | integrity-valid, every fact attested, real provenance (`activation_blockers()` empty, `facts.calibration == Attested`) | `owner_measured` or `published_datasheet`, non-empty `reference`, and an `acoustic_qualification` receipt id |
| `HostSimulation` | a synthetic fixture profile | `synthetic` |

Nothing in this repository satisfies `Production`, so every real board comes up fail-muted, which is
the intended state until measured data and an acoustic receipt exist. Fail-muted reasons, in the order the
profile gate checks them: `no_calibration`, `no_audio_output` (zero driver channels: an appliance such as the Bridge,
whose fixture row is "Sonos Bridge (Non-Audio)" with driver ABI `none-non-audio-bridge`; there is nothing to calibrate
or protect, in any mode), `invalid_layout` (more than 9 driver channels, or a routing list of the wrong length),
`amplifier_forbidden`, `unknown_board` (integrity, unattested or hypothesis profile, wrong mode), and every validation
error below. The refusal for the Bridge is deliberate and paired with the permitted behavior: every audio fixture board admits.

## Calibration and validation (fixed order, so the reported error is deterministic)

A `BoardCalibration` (JSON, `deny_unknown_fields`, schema `ffw.d02.calibration.v1`) is bound to one profile by
`profile_id` and `profile_digest`. Each driver channel has an explicit `source` (`left`, `right`, `mid`), `trim`,
`max_gain`, `ceiling`, `dc_block_hz`, up to 4 `sections`, a `limiter` and a `thermal` model.
Order: schema, profile gate, binding, provenance, board-wide ramps and sample rate (48 kHz only), channel count,
roles equal the profile's, then per channel: parameters (`trim`, `max_gain`, `ceiling`, `dc_block_hz`, limiter
threshold/attack/release, thermal tau/soft/hard), section count, per-section coefficients, gain bound,
intermediate range, stop-band guard. Ranges: trim and max_gain 0.01..4, ceiling 0.01..1, dc 1..100 Hz,
limiter threshold 0.01..ceiling, attack 0.05..100 ms, release 1..5000 ms, tau 0.05..600 s,
soft 0.001..1, hard in (soft, 4], ramp 1..1000 ms, fault ramp 0.1..100 ms.

**Admitted realization.** Coefficients **stored as `f32`**; direct form II transposed arithmetic and state in
**`f64`**; each sample enters and leaves a section as `f32`. The state is `f64` because of a measured defect, not a
preference: with `f32` state, the 300 Hz and 120 Hz low-pass step responses drifted 6.5e-5 and 5.2e-4 from an exact
evaluation of the *same stored coefficients* within 512 samples (poles at radius 0.973 and 0.989, roundoff amplified by
about `1/(1-r)`). Coefficient quantization is not that cause: it moves those poles by under 1e-8. It does shift the
realized DC gain, though: the stored 120 Hz low-pass step response differs from the unquantized design by up to 2.7e-4
(`1+a1+a2` is about 2.4e-4, so quantizing `a1`, `a2` is felt there). That is a property of the admitted `f32`-stored
coefficients, identical in the reference, and is not hidden: a calibration that needs better must store `f64` coefficients,
which is a separate decision. CPU cost of `f64` is measured on the soft-float MIPS target only (the precision row of the
acceptance map); the PowerPC targets are not measured. Validation runs on the
values the renderer holds:

* each coefficient is quantized to `f32` and must be finite and at most 8 in magnitude (a finite `f64` that
  overflows `f32`, such as `1e39`, is refused; `8.0000000001` stores as `8.0` and is accepted);
* stability: `1+a1+a2`, `1-a1+a2` and `1-a2` each above `1e-6`, on the stored `a1`, `a2`;
* gain and intermediate bounds for `|input| <= 1`, computed by `chain_bounds` on the stored coefficients and the stored
  DC pole (`dc_pole`, one definition shared with `DcRejector::new`). The largest value a quantity reaches is the L1 norm
  of the impulse response from the chain input to it, and the input that attains it is the sign of the time-reversed
  response. The quantities are the DC rejector's output and, for each section, its output `y` and its two states `z1`,
  `z2`. Two upper bounds are computed for each and the **smaller** is used:
  * the **product bound**: the sections' L1 norms multiply (L1 is submultiplicative), starting from the DC rejector's
    exact L1 of 2, each section's L1 summed over 8192 samples; `z2 <= |b2|x + |a2|y`, `z1 <= |b1|x + |a1|y + z2`.
    Rigorous and loose, see "The intermediate bound against the realized chain";
  * the **exact bound**: the unit impulse is run through the DC rejector and each section in direct form II transposed
    (the arithmetic of `Section::process`), the L1 norms of `y`, `z1`, `z2` are summed over the 8192-sample horizon,
    and the bound is `(sum + allowance) * 1.01` with
    `allowance = product / 2 * (R^8191 + tail * max(8192, 1 / (1 - rho)))`. `R^8191` is the L1 norm of the DC
    rejector's response past the horizon (0.0047 at a 5 Hz corner, 0.34 at 1 Hz); a following cascade amplifies a
    remainder by at most its product bound per unit of input L1, so that term is rigorous. `tail` is the largest
    unit-impulse peak a section leaves over the last 256 samples of the horizon and `rho` the slowest pole radius: the
    term assumes the responses past the horizon decay at that rate from a peak no larger than `tail`. That is the
    convergence rule the product bound already depended on, and it is the one assumption here that is not proved; the
    run-time guard (a filter output above 16 or non-finite latches a fault) is the backstop. `1.01` is spare: the
    effect of `f32` rounding in the DC rejector on a realized peak is 1.7e-7 of its value.
  The **gain bound** is the last section's `y` bound (2 with no sections); it must be at most 8, and every section's own
  unit-impulse response must have decayed to `1e-6` by the end of the horizon, else `gain_bound_exceeded`. The
  **intermediate bound** is the largest of the DC output and every `y`, `z1`, `z2` bound; it must be at most 16, else
  `intermediate_range_exceeded`. **The limits 8 and 16 are unchanged. Admission is more permissive than it was**, because
  the bound that is compared with them is smaller: by construction it is never larger than the product bound, so every
  calibration admitted before is admitted now, and calibrations the product bound refused are admitted when their exact
  worst case is inside the limits (next section).
* stop-band guard by role, on the stored coefficients: tweeters `|H(500 Hz)| <= 0.1`, woofers
  `|H(8 kHz)| <= 0.1`, sub `|H(2 kHz)| <= 0.1`; mid/array-mid roles have no guard. This is how "a tweeter route never receives
  unfiltered full-range output" is enforced. The guard numbers are provisional and synthetic.

## Render path (spec steps 4 to 7)

Per driver channel and sample: route (`left`/`right`/`mid = 0.5*(l+r)`, input non-finite to 0 and counted) ->
DC rejection `y = x - x1 + R*y1`, `R = exp(-2*pi*f/fs)` -> sections -> gain `min(trim * user, max_gain) * source_fade`
-> thermal scaling -> limiter -> hard `ceiling` clamp (counted) -> `i16` via the D01 conversion.
`render_into(&input, &mut ProtectedOutput)` takes preallocated fixed arrays and allocates nothing; zero-length and partial blocks are fine.
`render_block` is an allocating compatibility wrapper.

Volume has three separate quantities, reported separately in `BlockReport`: the **user value** (`user_gain`, as
set), the **applied gain** (`applied_gain`, slewed), and **protection-limited gain** (`min_limiter_gain`,
`thermal_scaled_samples`, `clipped_samples`). The applied gain moves by at most `1/(ramp_ms*fs)` per sample, so there is never a step.
A new board starts muted. Mute ramps to silence; unmute is refused unless the board is `Active`.

* **Limiter** (no look-ahead): `target = thr/|v|` above the threshold else 1; `gain += (target - gain) * a`, with the
  attack coefficient when falling and the release one otherwise, `a = 1 - exp(-1/(t*fs))`. The first samples of a
  burst pass before the gain falls, so the hard ceiling after the limiter bounds the output and counts the overshoot.
* **Thermal model** (synthetic, a leaky mean-square, not a model of any real driver): `level += alpha*(v*v - level)`,
  measured before scaling. Above `soft` the output is scaled by `sqrt(soft/level)`; at `hard` the board latches `thermal_hard`.
* **Faults.** A non-finite or out-of-range (above 16) filter value silences that channel at once and latches
  `non_finite_state` or `state_range`; `thermal_hard` latches without silencing the channel. Any fault ramps the whole board to
  silence over `fault_ramp_ms` and keeps it there. The level keeps cooling on silence. `clear_fault` is refused
  (`not_cooled`) until every channel is at or below its soft limit; it restarts signal-path state at zero and keeps thermal history.

## Board-lifetime history and events

| Event | Thermal level, limiter gain, fault latch, user gain, mute | Filter / DC state | Output |
|---|---|---|---|
| `Seek`, `Reconnect`, `SourceReplaced` | kept | kept | fade in from silence over `source_ramp_ms` |
| Valid profile switch | thermal and limiter carried per channel | zeroed at the swap (the output is exactly silent then) | drains to silence over `ramp_ms`, swaps, ramps back up |
| Unsafe profile switch | kept | n/a | board becomes fail-muted: ramps to silence and stays silent until a valid profile is admitted |
| `clear_fault` | kept | zeroed | ramps up |

A switch to a different board's profile id is refused (`profile_binding_mismatch`); a latched fault blocks switching (`fault_latched`).
The fade-out of the *old* source is the source adapter's job; the board only fades in.

## Legacy path

`BoardProtectionDsp` in `lib.rs` is the earlier host-simulation renderer (fixed filters, no calibration, no
admission). It is **not** an admitted protection path and the speaker still uses it; migrating the speaker onto `ProtectedBoardDsp` is a
separate change for that crate's owners. D02 does not claim it.

## The intermediate bound against the realized chain

**Why it changed.** The product bound is a sound over-estimate, and it was the only thing between a calibration and the
renderer's `f32` ranges, but it is loose: on the synthetic boards it is 2.5 to 7 times the true worst case, and it
refused a plain 60 Hz or 100 Hz Butterworth high-pass (bounds 20.4 and 20.3 against 16) whose exact worst case is 2.5.
That is the ordinary excursion-protection filter, so a validator that refused it met "validate intermediate-state ranges"
by refusing, which is not delivered capability. Nothing drove the real chain at its worst-case input either, and the
product bound's formulas (the rejector's L1 of 2, the `z1`/`z2` sums) live in both `calibration.rs` and `reference.py`,
so an error there would pass every vector.

**How it is checked.** `tests/d02/realized_chain.py` (and the Rust tests named below) drive the **real** `DcRejector` (`f32`)
and `Section`s (`f64` state, `f32` output), or an operation-for-operation emulation of them, with the input that
maximises one chosen quantity: the sign of the time-reversed impulse response to it, computed independently in direct form I.
`python3 -B -I tests/d02/realized_chain.py 32768` prints the full table; representative rows (DC corner 5 Hz unless
stated; 32768-sample runs):

|---|---|---|---|---|---|---|
| HP 100 Hz, `z1` | 20.264 | 2.294 | 2.2241 | 2.2288 | 2.2288 | 2.95% |
| HP 100 Hz, `y` | 4.832 | 2.483 | 2.4473 | 2.4473 | 2.4473 | 1.47% |

Reading it. The realized peak equals the independent exact L1 norm of the run to 1.7e-7 (that is the whole effect of
`f32` rounding), and it never exceeds the bound or the product bound in any of the 14 designs. Where the exact path is
active the spare over the realized peak is at least 1.01% (the 1% margin plus the allowance), about 58000 times the
`f32` effect. **The long-tail case** is the 1 Hz DC corner: `R^8191 = 0.34`, the sum over the horizon alone is low by 0.33
(`z1`: 2.0034 against 2.3300), and the remainder allowance is what keeps the bound above the realized peak (5.549 against
2.330). For the sections' own tails, `test_the_section_tail_allowance_covers_slow_converged_sections` builds
converged-but-slow sections (pole radius 0.998 to 0.9992, tail peak just under the 1e-6 threshold) and finds the response
past the horizon at most 0.09 of `tail * 8192`; beyond a pole time constant of 8192 samples (170 ms) the `1 / (1 - rho)`
factor takes over, and that is the assumption stated above.

The **refusal is warranted**, not merely conservative: the +24 dB design is refused for its middle node (20.569 against
16, final gain bound 3.09, well inside 8), and the real chain driven with that node's worst-case input reaches 20.28.
The +20 dB design (13.47) is admitted, and the real board driven with its worst-case input never latches a fault.

**What the tests kill.** Single-term defects planted in the bound (`tests/d02/test_d02.py`, `ExactBound`; the Rust tests
carry the same checks but cannot plant defects in the compiled function):

| Planted defect | Killed by |
|---|---|
| sum signed values instead of absolute values | realized peak above the bound (every high-pass: a zero-DC response sums to 0) |
| drop the state bounds (`z1`, `z2`) | realized state above the bound |
| take the rejector's L1 as 1 instead of 2 | realized peak above the bound (every low-pass) |
| drop the rejector remainder `R^8191` | realized peak above the bound on the two 1 Hz designs; at 5 Hz the 1% margin covers the 0.005 it removes, and the pinned numbers differ by 0.3% to 0.5% |
| drop the 1% margin | the spare check (at least half the margin over the realized peak) |
| take the worst case from the last section only | the pinned `worst` of the boost designs (13.47 against 3.37) and the +24 dB refusal |
| drop the minimum with the product bound | the "never stricter" check (pure gain 3: 6.04 against 6.00) |
| **drop the tail allowance** | **not killed by any committed design**: their tail peaks are below 1e-30, so the term is zero. A section converged only just adds at most `8192e-6 * product / 2`, comparable to the margin; no committed design separates them |

**Cases.** `D02-VAL-032` ("intermediate range only", product bound 23.2, exact 3.5) and `D02-VAL-033` (100 Hz high-pass,
20.3 against exact 2.5) were refusals and are now **positive controls**, in the same slots; `D02-VAL-029` (the high-Q
resonator, unconverged) and `D02-VAL-031` (a converged gain of 10) are unchanged and still refuse. Added, as
`D02-VAL-044` to `D02-VAL-046`: a 60 Hz high-pass at a 1 Hz DC corner (admitted), the +20 dB boost (admitted) and the
+24 dB boost (`intermediate_range_exceeded`, channel 2). No existing case id changes meaning: the three
malformed-document cases stay `D02-VAL-041..043`, and the new designs take the next free ids.

## Protection history through the render loop

The table in "Board-lifetime history and events" is about the board alone. The board's production consumer is
`franken_speaker::render::RenderLoop`, where a reconnect, a discontinuity epoch, a stop and restart and a profile switch actually
happen, so `crates/franken-speaker/tests/d02_protection_history.rs` drives each of them through the loop (a `FakeBackend`, the
synthetic calibration and a scripted timeline: host simulation) and reads the board back with `dsp()`. Its six tests are in the
judge's denominator through a third log (`speaker.log`, below); absent from the logs they are `blocked`.

Oracle: two laws that follow from the update rules documented above, not from the code under test. A leaky integrator with a
nonnegative input cannot fall faster than pure cooling, so `level_n >= level_0 * exp(-n / (tau * fs))`. A limiter whose target is at
most 1 cannot lose gain reduction faster than its release, so `(1 - gain_n) >= (1 - gain_0) * exp(-n / (release * fs))`. Both are
asserted with 0.2% slack for single-precision rounding, on every channel whose earlier reading is above a floor, after the board has
been heated from silence through the loop until it holds a nonzero thermal level and gain reduction. The heater's result is asserted
too, so a heater that built nothing fails instead of passing.

Each event test runs twice. The unplanted run is the control and must find no violation. The planted run replaces the board with a
fresh one at the event (`*l.dsp_mut() = fresh`, the defect the acceptance text exists to prevent) and must be caught. On a model of the
chain (`tests/d02/loop_history_model.py`, `LoopHistoryModel`) the control passes every event and a rebuilt board breaks both laws on
every event. The event is asserted to have happened in both runs (a resampler epoch began, or the switch installed), so neither run
passes vacuously.

The fault test overdrives the board through the loop until it latches `ThermalHard`. It checks that the loop faults with
`ProtectionFault`, that `recover()` resets the device and not the board, that `start()` is then refused (`ProtectionNotActive`), that
`reconnect()`, unmuting the board and `clear_fault()` while hot are refused, that after silence has cooled the board `clear_fault()`
succeeds with the thermal history carried (the first law again) and the fault counted once, and that `start()` then succeeds. A planted
loop that replaced the latched board at `recover()` is caught by the refused `start()`.

Stated plainly:

- Host simulation only. Nothing here is a board, an amplifier or a measurement of heat. Numerical tests do not prove physical protection.
- **A thermal fault has no way back inside the loop.** `RenderLoop` renders nothing while it is `Faulted`, `Ready` or `Stopped`, so a
  latched board's thermal level does not move there, and no production code calls `clear_fault` (only tests do). The way out is the one
  the test uses: feed the board silence through `dsp_mut()` until `clear_fault` succeeds. The thermal model also counts frames rendered,
  not time, so a stop does not cool the board in wall-clock time. That is conservative (it never under-reports heat) but it strands a
  latched board until something outside the loop cools it. The test pins this and fails if a cooling path appears, so that adding one is
  a decision. Whether the loop, the board or a supervisor owns cooling is not decided here.
- `RenderLoop` has no seek call, and `begin_epoch` reports every epoch to the board as `SourceEvent::Reconnect`. The board treats
  `Seek`, `Reconnect` and `SourceReplaced` alike, so a seek has no case of its own.
- There is no excursion history: D02 has no displacement model, and one needs driver parameters from E04 (`ffw-25l`).
- Central result (b42, a fresh export of `aea8c8a` with the patch applied at `--fuzz=0`; committed as 815aad1): `clippy -p franken-speaker
  --all-targets --locked -D warnings` exit 0 on the first compile; `--test d02_protection_history` 6 passed, 0 failed; the D02 judge
  `QUALIFIED planned=122 passed=122 failed=0 blocked=0`. Those are host-simulation results on a `FakeBackend`: no device, no board.
  The acceptance-map row below stays `partly` for the excursion half (E04) and because the host backend is the only backend run.

## Running, and the evidence boundary

```
RCH_REQUIRE_REMOTE=1 rch exec -- cargo test -p franken-dsp -- --nocapture      > dsp.log
RCH_REQUIRE_REMOTE=1 rch exec -- cargo test -p franken-alloc-probe             > probe.log
RCH_REQUIRE_REMOTE=1 rch exec -- cargo test -p franken-speaker --test d02_protection_history -- --nocapture > speaker.log
scripts/e2e/d02 --tier full --judge dsp.log probe.log speaker.log [--receipts DIR]
```

The judge reuses the D01 cargo-log parser (RCH output shape, deduplicated inputs). It compares each `D02-OBSERVED` line with the
independent reference. Section responses are compared within 1e-6: the Rust section and the reference run the same stored
coefficients, so only the final rounding of the output to `f32` (about 6e-8) remains; the tolerance is 17x above that and 65x
below the `f32`-state drift it exists to catch. DC and limiter responses use their own stated tolerances. Scenario traces are judged against closed forms the judge computes itself (the leaky-integrator thermal level,
exponential cooling, the fault block from `ln(1 - hard/v^2)/ln(1 - alpha)`, the 480-sample drain) and against persistence
invariants. A case or required Rust test with no observation is `blocked` (exit 3), never passed.

Limits, stated plainly: host-only synthetic data; no board CPU, timing or electrical measurement; the thermal and limiter numbers are
synthetic, not a driver model; the limits 8 and 16 on the gain and intermediate bounds are policy numbers for this `f32`-coefficient
realization and would need re-derivation for a fixed-point port (the bounds compared with them are checked against the
realized chain, above); scenario judging is validated here only on constructed traces until a real Rust log exists.
