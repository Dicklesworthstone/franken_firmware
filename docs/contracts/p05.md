# Contract P05 — Semantic 64-bit replacement for targets with no 64-bit atomics (slice 1)

Bead `ffw-ipz`. This contract describes the original offline semantic-atomic slice and its pinned upstream scan.
The scan reads Asupersync Git objects without editing them; that restriction describes the scanner, not the subsequent
upstream adaptation work. Host checks and the big-endian MIPS QEMU evidence below have separate qualification scopes.
Nothing here establishes behavior on the physical speakers or on their stock kernels.

Evidence label: model and host simulation, plus the separately scoped QEMU guest receipts below.

The owner has authorized changes to Asupersync and the other Franken libraries; see the
[recorded review decision](../planning/reviews/fresh-review-20261104.md).
The November 7 DNS future-erasure host run (57 tests) is recorded separately in
[the native DNS evidence](../../toolchain/results/p05/20261107-native-dns/RUN.md); it does not cover later upstream work.
It does not complete this bead's feature-gating, resource-cap or target qualification requirements.

## No-claim line

This slice **does not make Asupersync compile on the big-endian MIPS or PowerPC targets**, does not gate any Asupersync
module or dependency, and does not show that anything runs on a physical board. It provides the replacement an adaptation
would use, the reasons for choosing it per class of use, and tests that a naive replacement fails. `cfg` metadata, a green
host run and a classification table are not runtime proof. The one atomic-cell receipt is a QEMU guest run on big-endian MIPS32
(`P05-EXT-GUEST`, below): the runner re-judges its committed log. There is none for PowerPC and none from hardware. The runtime
probe's two single-owner guest runs are a separate record (**What ran**, below).

### Operations

| `core` atomic call | In `franken-atomic` | Difference |
|---|---|---|
| `load`, `store` (any `Ordering`) | `load()`, `store(v)` | the `Ordering` argument is gone; see the ordering row below |
| `swap` | `swap(v)` | same |
| `compare_exchange`, `compare_exchange_weak` | `compare_exchange(current, new)` | two orderings gone; no spurious failure, so a loop written for `_weak` still works |
| `fetch_add`, `fetch_sub` | `fetch_add`, `fetch_sub` returning `Result<_, ArithError>` | **behaviour change**: `core` wraps; this refuses, leaves the cell unchanged and says why. Code that wants a wrap must say `fetch_add_wrapping` / `fetch_sub_wrapping` |
| `fetch_max`, `fetch_min`, `fetch_and`, `fetch_or` | same names, over all 64 bits | same |
| `fetch_xor` (no uses), `fetch_nand` | not provided | nothing to replace |
| `fetch_update` (9 token uses) | not provided | a closure would run under the lock and could re-enter it; use a `compare_exchange` loop |
| `get_mut`, `into_inner` | same | same |
| `Ordering` | dropped | every operation is as strong as `SeqCst` **per cell** and nothing is promised across cells; the 11 `fence(` calls and any `SeqCst` use that needs one order across two different cells are the audit criterion for slice 2 |

## Semantics of the replacement

`crates/franken-atomic` (role `library`, layer set by NavyHollow's P01 entry, `#![forbid(unsafe_code)]`, std only, no
dependency edges). Every shared value is one `Mutex` around one integer.

* **Whole values.** All 64 bits are read or written under one lock. There is no pair of words a reader can see half updated
  and no narrowing cast on a value path (`P05-META-002` rejects `as u32`-style casts in the production modules).
* **Linearizable per cell.** Each operation takes effect at one instant between its call and return, in an order every thread
  agrees on, and a thread that sees an effect also sees what the writer did before it. Cells are independent: this is not
  `SeqCst` across cells.
* **Typed range errors.** `fetch_add`/`fetch_sub` return `ArithError::{Overflow, Underflow}` and leave the cell unchanged.
  Wrapping exists only under a `_wrapping` name. `Sequence` never issues `u64::MAX` and reports `Exhausted` forever after.
* **Bounded critical section; cancellation.** No caller code runs under the lock, nothing allocates after construction, and
  an operation contains no await or cancellation point, so cancellation cannot split it: it happened completely or not at all.
  A panic elsewhere cannot tear a value; a poisoned lock is recovered with the stored value intact.
* **Re-entrancy and signals.** A blocking call while the same thread holds the lock would deadlock (or panic), and a signal
  handler may interrupt the holder. The `try_load`/`try_store` pair answers `Contended` at once instead; they are the only
  shape a handler or re-entrant callback may use, or the handler uses a native 32-bit atomic. The fallback is **not**
  async-signal-safe.
* **Off the render deadline.** The shared cells are lock-based and a preempted holder delays every user of that cell, so they
  are for management, supervision, telemetry and identity, never for state a render deadline reads. `P05-META-006` checks
  that `franken-dsp`, `franken-hal` and `crates/franken-speaker/src/render.rs` do not depend on or name them.

Why a `Mutex` and not the alternatives, as a decision record:

| Option | Decision |
|---|---|
| `portable_atomic` `fallback` (Asupersync's facade at the pinned revision; `franken-platform` no longer uses it, its 64-bit cells are this crate's) | Stays a valid interim where Asupersync's facade still uses it. It has `core`'s API, so overflow wraps silently and nothing in the type says "do not use on a deadline"; E06 counts 628 `unsafe` tokens in that dependency. This crate is the zero-`unsafe`, typed-error alternative where a use needs those properties |
| seqlock over `AtomicU32` words | Deferred. Readers would not block writers, but writers still need mutual exclusion and a reader can retry without bound under a writer storm, which is worse than a bounded lock for management paths. Revisit only if a measurement shows lock contention on a retained path |
| interrupt-disabling or `unsafe-assume-single-core` | Rejected by the bead for Linux userspace, and unsafe |
| thread-local or per-thread sharded counters | Allowed only for owner-local state (`LocalU64`), never as a stand-in for shared state |

How the planted negatives work: `planted.rs` holds the two wrong versions (two independent 32-bit atomics; one 32-bit atomic
cut with `as u32`) as step machines. A seeded scheduler (SplitMix64, 3 threads of 4 operations, 256 seeds) interleaves their
micro-steps, and a Wing-Gong checker judges each history against the sequential specification. The real cell passes all 256;
the split-word cell is caught on 198 and the truncating cell on 231, numbers predicted by `tests/p05/reference.py` and pinned
in `tests/p05/vectors.txt`, which the Rust tests read and require to be reproduced. The hand-written directed scripts show the
mechanism: a torn store makes a load return `0x1_FFFF_FFF0` (a value nobody stored); a carry between words makes a load return
`0`, which the value never was; a truncated store loads as `1`. The same scripts pass on the real cell, which is the
remove-the-plant control. One script does not catch the split-word cell (`P05-DIR-008`), and the case file says so.

What this does **not** show:

* **Each run needs its own evidence.** Unless a central `cargo test -p franken-atomic` log is passed to
  `scripts/e2e/p05 --central-log`, that invocation's Rust cases are blocked and its run is NOT QUALIFIED. Missing evidence
  in an invocation does not establish that the code has never been compiled. A host x86_64 pass would still say nothing
  about a target compile: that needs the `-Z build-std` builds in `P05-EXT-TARGET-BUILD`.
* **Not a device result.** The only guest evidence for the atomic cells is one QEMU run on the Debian 4.19 Malta kernel
  (`P05-EXT-GUEST`). Whether std's `Mutex` works on the stock board kernels (futex support, scheduling) is unverified, QEMU's
  24Kf is one CPU so the threads there are preempted rather than parallel, and PowerPC has no atomic-cell guest run.
* **Model and Rust share an author.** The reference and the Rust model agree because both implement the same rules; that
  shows the arithmetic was done twice, not that the contract is right.
* **Bounded search.** The checker handles at most 62 operations, and the real-thread tests sample interleavings; they cannot
  prove the absence of a bad one. The model's value for the `Mutex` cell is mostly the control and the checker, since one
  operation is one step; the real concurrency evidence is the thread tests.
* **No measurements.** No latency, contention or size numbers exist. `size_of` on the target belongs in the memory ledger (P06).

## The guest receipt (`P05-EXT-GUEST`)

`toolchain/src/p05-target` is a std PID 1 that `#[path]`-includes this crate's source files and `tests/p05/vectors.txt`
unchanged, so it compiles the text the host tests run, and prints `FFW_P05T_*` lines. `toolchain/src/measure-p05-target.py`
boots it under QEMU (the Debian 4.19 Malta kernel, `-cpu 24Kf`) and judges the transcript against values that do not come
from the Rust: hand-written results of ten vector programs, the pinned counts in `vectors.txt`, the reference's per-seed
history digests for the pinned sweep and for a sweep from a per-run seed (so a replayed transcript fails), nine scripted
interleavings, real-thread outcomes that are exact for any correct cell, and `uname` and the ELF header saying 32-bit
big-endian MIPS. The committed evidence is in `toolchain/results/p05/guest-<revision>/` (serial log, seed, receipt, console
output).

The runner does **not** read the receipt to decide anything. `P05-EXT-GUEST` re-runs the judge on the committed serial log
with the committed seed. The receipt can only make the case fail, and it is held to what the runner can re-derive: the log's
sha256, the seed, the judge's own schema name and no-claim text, the verdict of every gate against the re-judged gates, and
what the case pins (the repository revision, the QEMU version, and 128-bit prefixes of the ELF's and the kernel's sha256).
With no committed log the case is BLOCKED, never passed; with no receipt it still passes, because a receipt only ever adds
failures. `P05-EXT-GUEST-PLANT` changes one byte of the log in nine places (each gate has one) and one byte of the receipt in
twelve (each check has at least one), and requires each change to be refused by exactly the gate or check meant to refuse
it, with the unplanted log and receipt as the controls. It fails, rather than skips, when the receipt is missing.

The ELF binary is not in the repository, only a 128-bit prefix of its sha256 in the case file, so the ELF-header gate is
re-judged only when the file is passed with `--guest-elf`; otherwise the case says it was not re-judged. With the file, the
receipt's whole ELF hash and size are also compared with it. What a changed byte is **not** caught in: the second half of the
ELF's and the kernel's sha256 and the ELF size in the receipt (the kernel and, without `--guest-elf`, the ELF are not in the
repository to compare), JSON whitespace, and bytes of the serial log that the judge does not read (kernel messages), which only
the receipt's transcript hash covers while a receipt is present. What it shows is that the same source behaves as the
reference says on a 32-bit big-endian guest under real preemption; it is QEMU evidence, a model, and the reference and the Rust
share an author.

## The runtime probe and its single-owner profile

`toolchain/src/p05-runtime` is the pinned Asupersync runtime under its own bounded `LegacyProfile`, run natively and as an
E07-supervised child in the big-endian QEMU guest. Its default run is the threaded profile (two scheduler workers, 13 phases,
23 operations), judged by `toolchain/src/measure-p05-target.py`. This section specifies its second run. It is mostly a
specification: what has actually run is recorded in the results directories and their receipts, and the **What ran** paragraph
below only summarizes two of those records.

**What "single-owner" means.** In P05, single-owner is `worker_threads: 1` built through `LegacyProfile::builder` / `build` and
checked by `audit`: one scheduler worker polls every task, and the blocking pool keeps its own threads. It is not the caller-driven
`RuntimeBuilder::current_thread()` mode. At Asupersync `460306de` (the revision of the committed single-owner receipts, no longer the probe's pin), `LegacyProfile` cannot build that mode: the profile's
builder starts from `RuntimeBuilder::new()` (`legacy_profile.rs:406-407`), the mode's flag is private to the `current_thread()`
constructor (`builder.rs:3911-3914`), and a profile cannot state zero workers.

**Selecting it.** The probe's argument `--profile=single-owner` selects it natively. The unchanged supervisor passes the child a
fixed argv and an empty environment, so in the guest the runner packs an initramfs marker file `/ffw_p05_profile` containing
exactly `single-owner` (the way other guests read `/ffw_seed`); any other content, or no file, is the default threaded run. The
judge and runner side is `scripts/e2e/p05 --runtime run|analyze ... --profile single-owner`.

**The run.** 20 phases and 13 census samples: 33 operations, 32 `ok` and 1 `unsupported`, in 35 markers of an exact order, with
`workers=1/1`. The extra rows check that one OS thread polls the phase's tasks and that a held blocking job does not starve the one
worker; and, on a fresh runtime with a byte-bounded pool and no platform reactor (`reactor=none`), that an oversized charge is
refused as `ChargeTooLarge` and starts no thread, that the first accepted job starts the pool's thread, and that the same runtime
then still runs work and drains.

**The declared row is a declaration, not a pass.** `CALLER_DRIVEN_CURRENT_THREAD` is printed `status=unsupported`. The probe of this
revision gives `reason=caller_driven_mode_is_the_separate_caller_driven_profile reason_source=profile_split
evidence=LegacyProfile::caller_driven`: the single-owner profile states a blocking pool of one thread, which the caller-driven
topology forbids, so that mode is the separate caller-driven profile (below). The receipts of the committed single-owner runs come
from the earlier probe, which gave `reason=profile_builder_cannot_build_caller_driven_mode reason_source=static_source_reading` and
citations of the source read at Asupersync `460306de`; the judge accepts each reason only with its own source. Either reason is a
declaration, not an observation: the one runtime observation beside it (`observed_tasks_on_caller_thread`) can only contradict it,
and nothing checks the file and line citations of the earlier one. The row is never counted `ok`. The probe exits 0 only when that
is the only row that is not `ok` (33 operations, 32 `ok`, exactly that one `unsupported`, with the current reason); a second
unsupported row, a failed, partial or unknown row, or a run in which the declared row is missing or `ok` exits nonzero. The
transcript keeps the truth either way.

**How it is judged.** `--profile single-owner` requires the exact marker order, the declared row as exactly one `unsupported`
row, and the standard supervisor envelope unmodified (`FFW_SPEAKER_EXIT status=0`, `TEST_SUCCESS failures=0`): no line of the log
is changed before the strict verifier reads it, and an exit-2 or `TEST_FAILURE` accounting is refused. An accepted run is recorded
as `accepted_with_declared_unsupported`, with `declared_unsupported` and a scope text saying so in the receipt. The summary line is
`ACCEPTED WITH DECLARED UNSUPPORTED`, never `PASSED`, and the command-line exit is 4 (0 is a full pass, 1 failed, 2 usage or
error, 3 blocked). A single-owner receipt is therefore never a plain pass. The census rows `after_runtime_drop` and
`after_byte_budget` must also carry the probe's report that each runtime drop was awaited (a join can return before the kernel has
unlisted the joined thread; this is by source reading and has not been reproduced in a guest): `settle=settled`, a `settle_threads`
no larger than the `start` row's thread count, and a `settle_polls` of at least 1, and the row's own stable thread count may not
exceed the start count either. The judge reads that report and cannot see the wait. A transcript without those pairs, from a probe
built before the settle, is refused, and the threaded profile is judged as before.

**FIRST_USE_BACKGROUND.** `FIRST_USE_BACKGROUND` is `ok` only when the blocking pool's own counters show no thread before the
first accepted job and one while it runs and the OS thread count grew; if the counters are right and the OS count did not grow or
could not be read, the row is `partial`, never `ok`; a wrong pool counter is `failed`. (The first version of the probe reported the
did-not-grow case as `failed`; the change to `partial` is deliberate and is disclosed in the headers of the v2.1 patches.)

**The caller-driven profile (in the probe source, not run).** `--profile caller-driven`, selected in the guest by the same marker file
holding `caller-driven`, is a third run: a runtime built with `LegacyProfile::caller_driven()`, whose one scheduler worker is driven by
the thread that calls `block_on` or `shutdown_drained`, with no worker, blocking or helper thread. The probe source calls that constructor and the accessors
that go with it (`is_caller_driven`, `os_thread_ceiling`, `topology_violations`), so the whole probe, the threaded and single-owner runs
included, builds only against an Asupersync that has them. The pin in `toolchain/src/p05-runtime/Cargo.toml` and `Cargo.lock`
is Asupersync `91509bcd8`, a published revision that carries them (they first appeared in `4f624497a`): its `legacy_profile.rs`, `builder.rs`
and `current_thread.rs` have the sha256 prefixes `e828a2d2`, `9ec5fcef` and `f37f616e`, the same at both. The earlier pin (`460306de`, the revision of the committed single-owner
evidence) did not carry them, and `toolchain/asupersync-cancel-audit` still pins it. The probe has not been built against the new pin
here, and the lockfile's four Asupersync entries were moved by hand, not by Cargo (see the manifest's comment). Selecting the run is exact: the argument or the marker must be the word, and when both runs are asked for, the
single-owner run wins. Its rules:

* 18 phases and 12 census samples: 30 operations, all `ok`, in 32 markers of an exact order. Nothing is declared unsupported, so
  an accepted run is a plain `passed` (exit 0), unlike the single-owner run.
* The profile row states `blocking_max_threads=0` and `os_thread_ceiling=0`. Every census row prints `os_thread_ceiling=0`, and the
  judge refuses any census row, and any thread count read inside a running task (`ABORT_TIMER_PARKED`, `CALLER_DRIVEN_RUNTIME`), that
  shows more threads than the `start` row. The runtime row also requires the tasks to have been seen on the thread that called
  `block_on` (`tasks_on_caller_thread=true`, `task_threads=1`), and the row after the drop carries the same settle pairs as the
  single-owner run's.
* The stated caps are one worker, no blocking thread, a blocking stack and queue of 0, a global queue of 256 and a 1 MiB worker stack.
  `PROFILE_ACCEPT` therefore shows `worst_case_stack_bytes=1048576` and a budget of the same: the one worker's stated stack, which the
  source itself calls an over-count because no thread is started for it. It is a stated cap, not a measured stack. `RUNTIME_AUDIT` pins
  `blocking_queue=0/0` on both halves: the audit accepts any stated queue for a forbidden pool, so the judge does not leave it to the audit.
* Blocking work is refused as `Forbidden` and starts no pool thread; it is never run inline. Work spawned through a handle between
  `block_on` calls does not run until the next `block_on` (`CALLER_DRIVEN_HANDLE_SPAWN_WAITS`): the mode's documented limit, asserted
  and not only stated.
* The row set is not the single-owner row set. The four rows that need the blocking pool's one thread (`BLOCKING_POOL`,
  `SINGLE_OWNER_BLOCKING_OFFLOAD`, `BYTE_BUDGET_REFUSAL`, `FIRST_USE_BACKGROUND`) have no counterpart, because this mode forbids
  blocking threads.
* The single-owner run's declared row says so (see **The declared row is a declaration, not a pass**): the probe of this revision
  declares `reason=caller_driven_mode_is_the_separate_caller_driven_profile reason_source=profile_split
  evidence=LegacyProfile::caller_driven`, and the judge accepts each declaration only with its own source (the earlier one with
  `asupersync_460306de:` evidence), so the committed receipts still judge valid.

**Not claimed for the caller-driven profile.** No run of it, natively or in a guest, is recorded, and no central compile or native
test result is recorded for the probe code that would produce one. The judge rules and their tests are checks on handwritten
transcripts. Nothing here shows the mode suits the speaker's I/O load, and a synchronous block inside a task stalls the whole runtime
by design.

**Required native tests.** The probe's native test names are listed in `tests/p05/native_runtime38_names.txt`: the 25 names of
the recorded first run, in order and unchanged, then 13 for the single-owner run, 38 in all. The first-run list,
`toolchain/results/p05/20261108-runtime-probe/native-required-tests.txt`, is frozen evidence of that run and is not edited.
`tests/p05/test_runtime_contract.py` shows that the existing reconciler's `reconcile()` takes the 38 names as its registry: a
complete log is complete, and a missing, duplicated, extra or `FAILED` name and a nonzero exit status are each refused. A probe that
has the caller-driven profile is listed in `tests/p05/native_runtime45_names.txt`: those 38, unchanged and in order, then 7 for the
caller-driven run, 45 in all. The 38 file is not edited: it is the registry of the single-owner revision. The reconciler's command
