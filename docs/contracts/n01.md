# Contract N01 — Authenticated Stream Framing (`ffw-ey5`)

**Status: implemented offline in `crates/franken-stream`. The framing tests passed centrally at commit
`5aa3a07` (27 unit + 1 loopback, clippy clean). Compatibility negotiation (§9) is implemented but has
no central result yet. A replay of every vector for a big-endian guest is written (§7) and has not run on
one. A coverage-guided fuzz harness for the parsers is written (§11) and has not run. Bead open.**
Scope is the datagram framing, its authentication, the receive-side admission gate, and the
compatibility negotiation that precedes media admission (§9). Transport lifecycle (N07), the control
channel (N02) and FEC coding (N05/N06) are not specified here. Nothing in this contract touches a
device, a network beyond loopback, or a provider.

## 1. Datagram

A datagram is `header (64 B) || payload (4..=1024 B, multiple of 4) || tag (16 B)`. Total 84..=1104
bytes. Every integer is big-endian; no native struct is serialized.

| Offset | Size | Field | Rule |
|---|---|---|---|
| 0 | 4 | magic | `FFWS` |
| 4 | 1 | version | `1`; any other value is rejected, never interpreted |
| 5 | 1 | kind | `1` media, `2` repair; others rejected |
| 6 | 1 | flags | `0xF0` critical bits: any set bit is rejected. `0x0F` ignorable: accepted, preserved, authenticated |
| 7 | 1 | format | `1` = signed 16-bit big-endian stereo PCM, 48 kHz; others rejected |
| 8 | 8 | stream_id | nonzero; random per stream start (§4) |
| 16 | 8 | epoch | group-transition epoch (§4) |
| 24 | 8 | seq | per (stream, epoch), starts at 0; `u64::MAX` reserved |
| 32 | 8 | start_frame | multiple of 256 (a defined frame boundary, not a receive time) |
| 40 | 8 | presentation_time_ns | at most 2^62 ns |
| 48 | 8 | consume_by_ns | at most `presentation_time_ns` |
| 56 | 2 | fec_group_id | coding block |
| 58 | 1 | fec_index | symbol position |
| 59 | 1 | fec_group_size | media: 0 (no FEC, index must be 0) or 1..=16 with index < size. repair: 1..=16, index < 16 |
| 60 | 2 | frame_count | 1..=256 and `payload_len == frame_count * 4` (frame count is derived and checked) |
| 62 | 2 | payload_len | at most 1024 |

There are no reserved bytes: a field a receiver might silently ignore is either defined as ignorable
(`flags & 0x0F`) or rejected.

## 2. Authentication

`tag = HMAC-SHA256(key, "FFWS-v1-auth" || header || payload)[0..16]`, compared in constant time. The
tag therefore covers every routing, timing, epoch, format and payload byte, and the context prefix
separates this protocol's MACs from any other that shares key material. The key is one shared 32-byte
stream key; it is never serialized, formatted, or logged (`StreamKey` prints `[REDACTED]`).

Threat model: this stops forgery, mutation and replay by parties without the key. A party **with** the
key can still send authenticated packets, so admission is additionally bounded (§3 step 7, §4) so that
one such packet cannot fence out the genuine stream. Per-sender keys or signatures are out of scope.

## 3. Receive order (`StreamReceiver::accept`)

1. Length: under 80 B is `PACKET_TOO_SHORT`; over 1104 B is `DATAGRAM_TOO_LONG`.
2. Magic, then version (`BAD_MAGIC`, `UNSUPPORTED_VERSION`).
3. Declared `payload_len` over 1024 is `PAYLOAD_TOO_LARGE`; the datagram must be exactly
   `64 + payload_len + 16` (`TRUNCATED`, `TRAILING_BYTES`). Steps 1-3 are O(1) and run before any MAC,
   so unauthenticated garbage costs no hashing. `mac_verifications` counts MACs actually computed.
4. MAC (`AUTH_FAILED`). Nothing below runs, and no state changes, before this passes.
5. Field validation in table order (`UNKNOWN_PACKET_KIND`, `UNKNOWN_CRITICAL_FLAGS`, `UNKNOWN_FORMAT`,
   `FRAME_COUNT_OUT_OF_RANGE`, `FRAME_COUNT_MISMATCH`, `MISALIGNED_START_FRAME`, `INVALID_TIMESTAMPS`,
   `INVALID_FEC_FIELDS`, `INVALID_STREAM_ID`). The encoder runs the same validation, so a sender cannot
   emit a frame its own receiver rejects.
6. `stream_id` must equal the bound stream (`WRONG_STREAM`).
7. Epoch and sequence (§4). Only now, if every earlier step passed, is the window updated.

A rejected datagram changes only the counters. In particular a tampered copy never consumes its
sequence number: the genuine datagram with that number is still admitted afterwards.

## 4. Identity, epoch, sequence

- `stream_id`: drawn by the sender from admitted entropy at every start. A restarted or rekeyed sender
  uses a fresh one and the receiver is told over the control channel (`bind_stream`); packets of the
  previous stream are then `WRONG_STREAM`, and the new stream reusing sequence 0 is not a replay. This
  is what makes (key, stream_id, epoch, seq) unique across restart and rekey. A sender with no admitted
  entropy must not transmit (`StreamId::new(0)` is refused).
- `epoch`: monotonically increasing within its authority. **Media packets never advance it.** A newer
  epoch is announced by the authenticated control channel (`advance_epoch`); a newer epoch seen in
  media is `FUTURE_EPOCH` and ignored; an older one is `STALE_EPOCH` and ignored. The stream is not
  modified by either.
- `seq`: starts at 0 in every epoch (or at a seeded origin for a mid-stream join). The receiver keeps a
  64-packet reorder window: up to 63 behind the highest is admitted once; 64 or more behind, or already
  seen, is `REPLAY_OR_DUPLICATE`. A packet more than **1024** ahead of the highest (or of the origin,
  for the first packet) is discarded and counted as `FUTURE_SEQUENCE` and leaves the window untouched.
  1024 is a provisional bound (about 5.4 s of blocks) chosen so loss bursts pass while a forged huge
  `seq` cannot turn every genuine packet into a replay. The sender stops at `u64::MAX`
  (`SEQUENCE_EXHAUSTED`) and must advance the epoch.

## 5. Diagnostics

Every error is built from integers; none can carry a key, tag or payload byte. `ReceiverCounters` has
one field per reason plus `accepted` and `mac_verifications`; `datagrams_seen == accepted + sum(rejected_*)`.
A bad version is reported as `UNSUPPORTED_VERSION` with the offending number and counted; **this layer
sends no response datagram** (an unauthenticated reply is an amplification vector). A rate-limited,
authenticated diagnostic reply belongs to N02/N07.

## 6. What jitter-buffer admission assumes

`BoundedJitterBuffer::push_packet` rejects non-media packets and reports undecodable PCM truthfully
(`NOT_MEDIA_PACKET`, `PAYLOAD_FORMAT_MISMATCH`). It still accepts any `AuthenticatedStreamPacket` value
a caller builds, so "authenticated before scheduling" is guaranteed by routing every datagram through
`StreamReceiver::accept`, not by the type system. Making the buffer take only receiver output is a
possible hardening, not done. The one in-tree consumer, the `franken-speaker` virtual-house campaign,
sends through a per-member `StreamSender` and admits every datagram at every simulated member through
`StreamReceiver::accept`; a refusal there fails the campaign instead of being skipped. It creates those
endpoints through negotiation (§10).

## 9. Compatibility negotiation (mixed firmware revisions)

Before any media datagram is admitted for a (peer, stream, epoch), the sender and the receiver
exchange an authenticated **Offer** and **Answer** (`crates/franken-stream/src/negotiation.rs`).
Media endpoints for a negotiated session are created only by `StreamSender::from_negotiated` and
`StreamReceiver::from_negotiated`; the plain `new` constructors are the fixed baseline profile
(everything this build implements, an out-of-band key).

**Capabilities.** Each side states what it can do. Differences between firmware revisions or hardware
generations live here and nowhere else: there is no per-generation framing, and no field in either
message identifies a hardware generation.

| Field | Meaning |
|---|---|
| `wire_min..=wire_max` | media wire versions spoken (this build: 1..=1) |
| `formats` | bit set; bit 0 = signed 16-bit big-endian stereo PCM, 48 kHz |
| `max_payload_bytes` | largest media payload accepted; a common limit below one full block (1024 B) has no v1 session |
| `mandatory_features` | the other side must also support these or there is no session |
| `optional_features` | used only when both sides support them |

Features: bit 0 `XOR_PARITY_FEC` (repair packets), bit 1 `PARTIAL_FINAL_BLOCK` (media shorter than a
block). A claim is well-formed only if `1 <= wire_min <= wire_max`, `formats != 0`, the payload limit is
a multiple of 4 and at least 4, and the mandatory and optional sets are disjoint. A build may claim
only what it implements (`wire_max <= 1`, known features, known formats, limit at most 1024).

**Message** (all integers big-endian; a 100-byte body then a 16-byte tag; Offer and Answer share it):

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic `FFWN` |
| 4 | 1 | message version (`1`) |
| 5 | 1 | kind: `1` offer, `2` answer |
| 6 | 1 | flags: `0xF0` critical (any set bit is rejected), `0x0F` ignorable |
| 7, 8 | 1, 1 | `wire_min`, `wire_max` |
| 9 | 1 | formats |
| 10 | 2 | `max_payload_bytes` |
| 12, 16 | 4, 4 | mandatory features, optional features |
| 20 | 8 | peer identity (nonzero) |
| 28 | 8 | stream identity (nonzero) |
| 36 | 8 | epoch |
| 44 | 16 | nonce (nonzero, fresh per message, from admitted entropy) |
| 60, 61 | 1, 1 | selected wire version, selected format |
| 62 | 2 | selected max payload |
| 64 | 4 | selected features |
| 68 | 32 | SHA-256 of the exact Offer datagram |

All selection fields and the digest are zero in an Offer and must be well-formed in an Answer.
`tag = HMAC-SHA256(group key, "FFWS-v1-hello" || body)[0..16]`. Parsing order mirrors §3: exact length,
magic and message version (O(1), no hashing), then the tag, then kind, flags, capabilities, identities,
nonce and selection. A message of any other length is `HELLO_LENGTH`; nothing allocates from an
unauthenticated length.

**Selection** is a pure, symmetric function of the two capability sets, so neither side can pick for the
other: the highest version in both ranges (`NO_COMMON_VERSION` otherwise); a mandatory feature the other
side lists as neither mandatory nor optional is `MANDATORY_FEATURE_MISSING` (this is how an unknown
mandatory bit from a newer peer fails closed, while unknown optional bits are carried and ignored); the
lowest common format bit (`NO_COMMON_FORMAT`); the smaller payload limit, capped at 1024
(`LIMITS_INCOMPATIBLE` below one block); and every feature both sides support.

**Checks.** The responder verifies the Offer (kind; `min_epoch`, so an Offer for an epoch older than its
own is `STALE_OFFER_EPOCH`; its own peer identity and nonce must differ from the Offer's), selects, and
answers with the digest of the exact Offer bytes. The initiator trusts the responder with nothing and
verifies the Answer: kind, stream, epoch, not a reflection (same peer identity or nonce), the digest
equals the SHA-256 of its own Offer (`OFFER_DIGEST_MISMATCH`), and the selection equals what it computes
itself from its capabilities and the answered ones. A lower wire version than is jointly supported is
`DOWNGRADE_DETECTED`; any other difference is `SELECTION_MISMATCH`. `Initiator::finish` consumes the
initiator, so one Offer completes at most once.

**Binding.** `transcript = SHA-256("FFWS-v1-transcript" || offer || answer)` and
`media_key = HMAC-SHA256(group key, "FFWS-v1-session-key" || transcript)`. The transcript contains both
peer identities, the stream, the epoch, both nonces, both capability lists and the selection, so two
sides that did not hold byte-identical messages derive different keys and every media datagram between
them fails `AUTH_FAILED`. Media endpoints take the stream and epoch from the session and enforce the
negotiated features on both ends: a frame using a feature outside the selection is
`FEATURE_NOT_NEGOTIATED` on send (no sequence number is consumed) and on receive (counted in
`rejected_not_negotiated`), even when signed with the session key. A session whose wire version or
format this build does not implement is refused at endpoint creation.

**Downgrade analysis.** Each row is covered by a test with a hand-written expectation; byte-level
tampering of any field is covered for every byte by the exhaustive bit-flip test.

| Attempt | Outcome |
|---|---|
| lower `wire_max` or strip a feature in an Offer in flight | `HELLO_AUTH_FAILED` |
| the same, re-signed by a party holding the group key | the Answer binds the digest of the modified Offer: `OFFER_DIGEST_MISMATCH` at the initiator |
| Answer selecting a lower version than is jointly supported | `DOWNGRADE_DETECTED` |
| Answer dropping a negotiated feature, or claiming a higher version | `SELECTION_MISMATCH` |
| replay of an earlier Answer, or of an Offer for a superseded epoch | `OFFER_DIGEST_MISMATCH`, `STALE_OFFER_EPOCH` |
| Offer fed back as the Answer, or an Answer under the Offer's identity or nonce | `WRONG_HELLO_KIND`, `REFLECTED_HELLO` |
| media from a different negotiation (same peers, stream, epoch) | `AUTH_FAILED` |

**Incompatible join.** A failed negotiation yields no session and sends nothing (no refusal datagram, for
the reason in §5; timeouts belong to the control channel). It touches no sender or receiver state:
`an_incompatible_join_leaves_the_existing_group_playing_unchanged` snapshots every member's next
sequence number, epoch and counters across two failed joins, then continues playback without a gap.

**Verification of §9.** `tests/n01/reference_negotiation.py` is an independent implementation (stdlib
`hmac`/`hashlib`/`struct`, its own key derivation) that writes
`crates/franken-stream/tests/vectors/n01_negotiation_vectors.json`: 4 negotiations and 31 rejections
(22 for the responder, 9 for the initiator) with hand-written expected codes. The Rust tests replay the
offers, answers, transcript digests and media keys byte for byte and check every rejection code. Three
codes cannot be produced through the public API of a build that refuses to claim more than it
implements (`NO_COMMON_VERSION`, `NO_COMMON_FORMAT`, `DOWNGRADE_DETECTED`); the Rust unit tests reach
them through `select` and with stand-in firmware, and the Python model reaches `DOWNGRADE_DETECTED`
with stand-in firmware too. `LIMITS_INCOMPATIBLE` was listed with them in error: a build may
claim *less* than it implements (only *more* is refused), so a responder, an Offer or an Answer that
advertises a payload limit below one block (1024) is refused with it. Vectors pin it at each end
(`N01-NR-119` and `-120`, the second one step of four below a block, a responder; `-121`, an Offer;
`N01-NF-209`, an Answer), pin its place in the check order (`N01-NR-122`: a responder with a small limit
that also lacks a mandatory feature reports the feature), and pin the accepted side of the boundary (a
limit of exactly one block as the receiver in `N01-NG-001` and as the sender in `N01-NG-004`). The
speaker campaign produces it end to end as well (§10).
`tests/n01/test_reference_negotiation.py` also checks that `negotiation.rs` declares exactly the contract's
error names, wire constants and field offsets.

**Limits.** The group key is shared, so a party holding it can negotiate as any peer and can re-sign
messages end to end; per-peer keys or signatures are out of scope. Wire version 1 is the only version
that exists, so version arithmetic beyond it is exercised only with stand-in firmware (`wire_max` 2 or
3) that this build refuses to claim. The payload limit currently reduces to "one full block". The nonce
source and negotiation timeouts belong to P01 and N02. The `franken-speaker` campaign negotiates each member's stream (§10).
No claim is made about which boards support which features:
nothing has been measured.

## 10. Negotiated streams in the Virtual House

The `franken-speaker` virtual-house campaign (`harness.rs`, `Q01`) creates every member's stream through
the §9 exchange. It used to build them with the baseline constructors, so the negotiated path was never
exercised end to end.

- **Per member.** The coordinator makes an Offer (baseline capabilities, the campaign stream id and
  epoch); the member answers with `respond`; the coordinator checks the Answer with `Initiator::finish`;
  each end builds its media endpoint with `from_negotiated` from its own copy of the session. The two
  copies must agree on the selection and the transcript digest, or the campaign fails.
- **Own key per member.** A media key is bound to one transcript, so the coordinator holds a sender per
  member (the simulation owns both ends, so each sender lives with the member it sends to) and encodes
  each block once per member. A sender advances whether or not the network delivers a block. A datagram
  made for one member is refused by every other (`AUTH_FAILED`); under the baseline constructors every
  member held the same key and accepted every member's stream.
- **Recorded.** The report carries, per member, what was agreed (wire version, format bit, payload
  limit, features) or the refusal that left it without a stream.
- **Refused, not degraded.** A member the coordinator cannot negotiate with gets no receiver and no
  sender. Every block it is due is muted with silence at the right stream position (counted in
  `muted_blocks` and `stream_refused_blocks`), nothing is played or concealed for it, and one critical
  `stream_refused` record carries N01's stable code and its bounded text (numbers and words, never a
  key, tag, nonce or digest). The campaign does not fail, and every other member is unchanged: the
  existing campaign tests still require every block of every member audible and none muted.
- **What the skew claim covers.** An incompatible join changes nothing for the existing group, so the
  2 ms target is judged over the *participants*, the members that have a media stream, and the report
  says how many (`skew_participants`: 4 with one refusal, 5 normally). The refused member is outside
  the claim and is reported with its cause (`members[..].stream`, the critical `stream_refused`
  event). A participant that does not sound, because a fault muted it, is not outside it and makes its
  blocks unmeasured, so a refusal cannot excuse one
  (`a_refused_member_is_out_of_the_skew_gate_but_a_silently_muted_one_is_not`). With fewer than two
  participants there is nothing to compare, so every block is unmeasured and the target is never met
  (`a_house_with_one_participant_left_makes_no_synchronisation_claim`). A campaign that compared nothing
  at all (zero blocks) makes no claim either: `within_2ms_skew_target` needs at least one measured block
  (`a_campaign_that_compared_nothing_does_not_report_the_skew_target_as_met`). The first version of this
  section counted a refused member as unmeasured in every block, so a campaign with one planted
  refusal read as missing the target; the first central run that reached it (b24) found that, and the
  gate and this paragraph were corrected together.
- **Planted refusals, one for each end that can refuse.** A member whose Answer carries negotiation
  message version 2 is refused by the coordinator as `HELLO_UNSUPPORTED_VERSION`. The decoder checks
  the version before the tag, so planting this needs no key, and a test shows that altering any other
  byte of the same Answer is `HELLO_AUTH_FAILED`, so the refusal is about the version and not a broken
  tag. A member that accepts payloads of 4 bytes is refused by the member as `LIMITS_INCOMPATIBLE`.
- **Not planted.** `NO_COMMON_VERSION` (a member whose wire-version range excludes 1) cannot be produced
  this way: this build refuses to claim a wire version it does not implement (§9). It stays covered by
  the `select` tests and the stand-in firmware.

**Limits.** Peer identities and nonces in the simulation are deterministic stand-ins, not entropy (the
source is `P02`). Each member is negotiated once at the start; the campaign's fencing probe advances the
session's command epoch, not the stream epoch, so there is no renegotiation or rekey in it. The campaign
sends full media blocks only, so the FEC and partial-block features are negotiated but not exercised
end to end. Everything here is a simulated component: it is not evidence about real hardware, real
firmware revisions or a real network.

## 11. Fuzzing the parsers (coverage-guided)

The seeded, bounded tests of §7 cannot find what they were not written to look for. `crates/franken-stream/fuzz/` is a
cargo-fuzz crate that lets libFuzzer search for it, with an independent oracle for every target. **It is written and has
not run**: no clean run, no control run, and no compile of it exists.

**Where it lives, and what P01 sees.** The crate is host-only: it has its own `[workspace]`, so it is not a member of the
repository workspace and no device build resolves it; it depends on `franken-stream` by path and nothing depends on it.
`tests/p01/facts.py` reads crate manifests one level deep (`crates/<name>/Cargo.toml`), so **P01 does not scan this path**.
That is a fact about the scanner and not a reason for the location (the location is cargo-fuzz's layout). The contract's
`assets` list can still own it, as it owns `crates/franken-stream/tests/vectors`: the row `{"path":
"crates/franken-stream/fuzz", "owner": "N01", "kind": "fixture"}` is generated by the P01 contract generator once this
directory exists (it refuses to write a row for a missing directory, and a row is not hand-edited into the JSON), and
until that row lands this crate is recorded here as unscanned, not as P01-covered.

**Its lock.** `Cargo.lock` is committed. It was written by `cargo +nightly generate-lockfile --offline` from the local
registry cache (no network, nothing compiled) and locks 39 packages: 30 of them at exactly the version the
workspace `Cargo.lock` pins (the closure of `franken-stream`), and 8 registry crates only here (`arbitrary 1.5.0`, `cc 1.11.0`, `find-msvc-tools 0.1.15`, `getrandom 0.4.3`, `jobserver 0.1.35`, `libfuzzer-sys 0.4.13`, `r-efi 6.0.0`, `shlex 2.0.1`). Every
central line passes `--locked`, which refuses when a manifest in the closure (the fuzz manifest, `franken-stream`,
`franken-dsp`, `franken-board-profile`) changed without the lock; `tests/n01/test_fuzz_lock.py` finds that on the host
first. **Unverified:** that the worker's offline registry holds the 8 crates only this lock needs (if it does not,
drop `--offline` from the fuzz lines: `--locked` keeps the versions), and that a build accepts the lock as written.

**Targets.** Every target takes arbitrary bytes. For the datagram and Hello targets the first byte picks the mode: `1`
keeps the header (or Hello body) the mutator wrote and **re-signs** it, anything else uses the rest as is. A mutator
cannot forge a 16-byte tag, so without the re-sign mode every input dies at the MAC and the field checks behind it are
never reached; with it, an edit to any field still produces a datagram that passes the MAC. `stream_decode` has a third
mode, `2`, **re-sign and fit**: it also sets the declared payload length to four bytes per frame when the frame count
is in range (1 to 256) and leaves it alone otherwise. The contract couples the two fields (`FRAME_COUNT_MISMATCH`), so
under mode 1 a mutator that edits the frame count is refused on the payload length, and to reach an accepted packet of
a new size it would have to change both, at exact values, in one step. Mode 2 makes the frame count the one free choice.
Mode 1 stays, because it is the only way to reach `FRAME_COUNT_MISMATCH` behind a valid tag. The first central control
run is why mode 2 exists (below).

| Target | Calls | Oracle (all written from this contract, in `fuzz/src/wire.rs`, `model.rs`, `hello.rs`; none calls the code under test) |
|---|---|---|
| `stream_decode` | `AuthenticatedStreamPacket::decode_and_verify` | no panic; the verdict is the one the contract gives from the bytes alone, first rejection in receive order (structure, MAC, fields), with the code; an accepted packet re-encodes **byte for byte** and is inside every declared bound (payload 4..=1024 and a multiple of 4, no critical flag, aligned start frame, timestamps, FEC fields, nonzero stream) |
| `stream_receiver` | a real `StreamReceiver`, driven by an operation stream (datagram as is, datagram re-signed, `advance_epoch`, `bind_stream`) | the stateless verdict, then stream, epoch and sequence window from an independent set model (no bitmap); an accepted packet is for the bound stream and the active epoch, no `(window, sequence)` is accepted twice, the sequence high-water mark never moves backwards, the active epoch never moves except through `advance_epoch`/`bind_stream`; **at the end every datagram is in exactly one counter bucket and `mac_verifications + rejected_structure + rejected_unsupported_version == datagrams_seen`** (nothing that failed a structural check cost a MAC: the unauthenticated-work cap) |
| `negotiation_respond` | `respond` (parses an Offer) | the decode verdict and code from an independent parse of the 116-byte layout (§9), then the receiver's own checks (kind, stale epoch, reflection, `select`); an accepted exchange has an Answer that verifies, names the SHA-256 of the offer and repeats the selection, and a session carrying the offer's identities, epoch and that selection |
| `negotiation_finish` | `Initiator::finish` (parses an Answer) for the fixture's own offer | the same, then the initiator's checks (kind, stream, epoch, reflection, offer digest, selection, downgrade); an accepted session carries the exchange's identities and the selection `select` gives |

**Seed corpus.** The committed golden vectors, in each target's input format: every wire vector as is and, for the accepted
ones, as a re-sign input and as a re-sign-and-fit input; every distinct datagram the scenarios feed a receiver; the first 40
steps of each scenario as an operation stream; every Offer and Answer as is and re-signed; every negotiation rejection by the
target it belongs to. Rust writes it (the `seed_corpus` **example**, one manifest line per target; `cargo run --example
seed_corpus -- <corpus>`) and the host tests replay the same list in process; the files are derived and are not committed.
It is an example and not a `[[bin]]` because `cargo fuzz build` builds every bin of the package with the coverage
instrumentation, and a bin that does not link libFuzzer's runtime does not link (below).

**The control.** A fuzzer that finds nothing proves nothing until it is shown to find something. Built with
`--features control`, the harness's call into the real decoder panics when an **accepted** packet carries a payload of 600
to 796 bytes (150 to 199 frames: 50 of the 256 valid payload lengths, 19.5 percent), the shape of a length-dependent defect
that only a mid-sized payload reaches. No seed has such a payload (the seeds' accepted payloads are 4, 8, 12 and 1024, that
is 1, 2, 3 and 256 frames), and no seed is a bit flip, a step of up to ten, or a byte swap of the frame count from one
(`the_planted_band_is_no_seeds_and_no_bit_flip_or_small_step_from_one`, in Rust and in Python). Reaching it takes a datagram
that is structurally valid, carries a valid tag and declares a frame count in the band, which in mode 2 is one edit of one
field. The control run uses the same target, the same seeds and the same budget as the clean run; if it does not find the
crash, **the budget or the harness is too weak and the clean runs prove nothing**. The plant lives in the fuzz crate, not in
`franken-stream`: a device-closure crate carries no deliberately broken path, even a gated one. What the control proves is
reach and reporting; it does not prove that the real decoder has no bug the oracles cannot see.

**The first central control run missed the first plant, and why.** The first plant was one exact length, 516 bytes (129
frames), reached through mode 1. On the supervisor's run (job on the trj worker, `cargo-fuzz 0.13.1`, `rustc 1.101.0-nightly
(708c94ef0 2026-11-03)`, the clean `stream_decode` seeds, `-max_total_time=120 -max_len=8192`) it executed 20,541,985 inputs
in 121 s (about 170,000 a second), ended at coverage 167 and 244 features with a corpus of 52, and never printed the plant's
panic. The last input that added a coverage point was number 10,854 and the last that added a feature was number 238,814,
out of 20.5 million: the search had stalled, not slowed. The cause is in the harness and not in the budget: the seeds' accepted shapes are 1, 2, 3 and 256 frames, and an accepted 129-frame packet
needs the frame count (2 bytes) **and** the payload length (2 bytes) edited to exact values at once, three bytes at least;
one edit alone gives `FRAME_COUNT_MISMATCH`, which every seed run already covers, so the half-way input adds no coverage and
is not kept; nothing compares a length to 516 before the packet is accepted, so libFuzzer's comparison tracing never learns
the constant; the length limit and the zero-padding of the payload are not in the way (`resign` pads to whatever is declared
and the limit libFuzzer used grew past 5,000 bytes). Mode 2 removes the coupling, and the band keeps the plant a learned
edit and not a bit flip. The numbers above are the supervisor's log, which is not committed; this paragraph is the record.

**Host tests (no fuzzer needed).** `fuzz/tests/harness.rs` (22 tests in a clean build, 20 with `--features control`): this crate's copy of the contract numbers equals
`franken-stream`'s; the seed corpus is complete (each accepted vector as is, re-signed and fitted, each giving the vector
back) and every seed passes every oracle; the scenario seeds are accepted exactly
as often as the vector file says (which also checks the operation encoding end to end); every structural and field rule has a
hand-pinned code, each paired with the untouched datagram accepted, and the oracle and the decoder agree on it; the bounds
oracle flags each of nine planted violations and passes the golden packets; replay, stale epoch and wrong stream are
refused and the first delivery accepted; the independent window model agrees with the real `ReplayWindow` over 60,000
seeded steps; every Offer and Answer rule is pinned by hand the same way; a seeded mutation run and an arbitrary-bytes run
violate no oracle; a datagram of every valid payload length is accepted; the fit rule gives an accepted packet of four
bytes per frame for each of the 256 frame counts where re-signing the same bytes as they stand is refused as a mismatch,
and leaves an out-of-range frame count alone; the planted band is no seed's length and no bit flip, step or byte swap of a
seed's frame count; and the control build panics for exactly the 50 planted lengths and no other, while the clean build has
no plant.

**What the first central run showed** (the supervisor's single `rch exec --job --worker trj` script at 1066336; the logs are
the supervisor's and are not committed). Seen: `cargo-fuzz 0.13.1` and a C++ toolchain are on the worker (`cargo fuzz run
stream_decode` built, linked libFuzzer and ran 20.5 million executions); the lock held (`--locked --offline`, its hash
unchanged before and after) and the crates it needs built offline from the compile-mode cache (`CARGO_HOME` had to be set to

**Unverified:** the four clean runs (none was done: the control gates them), the 50,000-execution floor against a clean run

The control and clean runs share `S`; the judge's floor is 50,000 executions per clean target (`--min-execs`).

**What the judge checks** (`tests/n01/fuzz_judge.py`; it reads logs and one crash file and runs nothing). A clean run: no
crash marker, a `Done N runs in T second(s)` line with N at least the floor and T at least the budget, coverage lines with
the seed corpus loaded (`INITED`) and coverage that never falls, a `seed corpus: files: F` line with F at least the
manifest's count for the target. The control run: it did **not** finish, the panic message is the planted one with the
planted length, inside the band (a panic from an oracle is "crashed on something else"), libFuzzer reported the crash and kept
the artifact, and the crash input has the SHA-1 the log names and **is an accepted packet of a planted length**, re-derived
with the independent Python decoder through the mode byte's own rule (mode 1 or 2). The crash input is the file given with `--crash` or, without one, the
`Base64:` line libFuzzer prints under the artifact line (judged identically; the record says which it was). It prints one
JSON record per run (executions, coverage, features, corpus units, crashes). **A crash in a clean run fails the run; the minimised input becomes a new regression
vector in the vector files (by the generator, never by hand-editing the JSON).**

**What a clean pass would mean:** within the budget, no input the fuzzer found made any target disagree with this contract
or panic. It would not mean the parsers are bug-free, that the budget was enough beyond what the control shows, or anything
about a device.
