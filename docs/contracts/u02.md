# U02 — signed staged artifact and update policy (`ffw-76j`)

Per-board signed manifests, artifact verification, an anti-rollback floor, and the offline staging, trial, activation and rollback state
machine, over U01's journal and E01's board profile. `tests/u02/reference.py` is an independent implementation of this document;
`crates/franken-update` is the Rust implementation, with comparison cases in `crates/franken-update/tests/vectors/u02_vectors.json`.

**Qualification status (2026-11-07).** The first actual native run at `2ccb1a5` returned 101: 28 tests passed and one failed on an unsupported
`>100` refusal-count precondition. Its independent E2E judge correctly failed; the full initial record is retained under
[`toolchain/results/u02/20261107-2ccb1a5-initial`](../../toolchain/results/u02/20261107-2ccb1a5-initial/README.md).
The corrective pass preserves all 176 original case objects and adds 12 genuine boundaries, replaces the count with semantic named-case/positive
coverage and planted controls, rejects nonexistent group targets, and requires a nonzero capacity-receipt digest before claiming A/B proven.
The subsequent production-evidence correction preserves those 188 cases and appends ten more: matching all-zero evidence digests now
refuse admission and restart recovery in production, while matched nonzero evidence and offline admission remain permitted. Actual old-code
regression execution fails four of 33 tests; the correction passes all 33, all 53 Python tests, strict remote all-target Clippy and source-bound
PowerPC/MIPS compilation. Full E2E passes 6/6 with 50 planted defects detected and 13 critical diagnostic events without loss; its judge also
passes against the published native transcript. The commands, failures, source witnesses and observed results are preserved in
[`the final offline qualification record`](../../toolchain/results/u02/20261107-evidence-digest/RUN.md).
Offline implementation qualification awaits the nonauthor supervisor's final committed-revision decision. Cryptographic dependency inventory
does not establish BE arithmetic execution or board resource admission. No device, retained-driver, provider or effective SSH-server
qualification is established; prestart capacity refusals remain distinct from product tests.

**Authority.** Offline engineering only. Nothing here opens a device, a network, a flash part or a file other than the ones a test names. No
firmware image, key or site identifier is in the repository: the test keys are the public Ed25519 test keys of RFC 8032 section 7.1, the
boards are the synthetic fixtures of `franken-board-profile`, and every artifact is a byte pattern.

**What this is not.**
* Not a claim that any speaker accepts, boots or survives an update. The state machine is a model of the *decision* to stage, try, keep or
  roll back; the boot selector, the watchdog and the flashing are U03's and the human-led lane's.
* Not a claim of A/B capacity. No board's flash capacity is known in this repository, so the default plan is a single slot with a recovery
  path, and A/B is planned only when an external capacity receipt covers two slots. A receipt for a synthetic fixture is refused for any
  board that is not one, and a receipt without a digest (all zero, which means absent here as everywhere else) binds nothing and plans no A/B.
* Not a vendor acceptance claim and not a bypass. See "The trust boundary".
* Not a hardware-backed key store and not a secure boot chain: the floor is a journal mark, and U01 states that it does not defend against
  someone who can rewrite the medium.
* Not proof of the dependency's behaviour on a big-endian 32-bit target: see "The signature primitive".

## 1. The trust boundary

Two trust domains exist and this document only ever speaks for one of them.

| Domain | Who holds it | What it covers here |
|---|---|---|
| **Factory boot trust** | the vendor | the stock bootloader, kernel and signed packages: observed, never modelled, never claimed |
| **Our signing trust** | the owner's release key(s) | our userspace payload, verified by this update policy against keys in the device's trust store |

Consequences, each enforced and each a vector:

* A manifest names exactly one target stage, **our userspace payload**. A kernel, bootloader or vendor-package stage is refused
  (`stage_forbidden`).
* A manifest cannot claim vendor acceptance, a factory bypass or A/B capacity (flag bits 0, 1, 2): each is refused by name
  (`vendor_claim_forbidden`, `bypass_claim_forbidden`, `ab_claim_forbidden`), after the signature is verified.
* An admitted plan has no field that can say the vendor accepted anything: `vendor_acceptance` is the constant `not_claimed`.
* The A/B status is `not_proven` unless an external capacity receipt that carries a digest covers two slots (`proven_by_external_receipt`).
* The trust store holds at most four keys; each must be a canonical, on-curve, prime-order, non-identity Ed25519 point; a key id is *derived*
  (first eight bytes of SHA-256 of the key), never supplied.

## 2. The manifest (all integers big endian)

Fixed layout, at most 512 bytes. The signed bytes are `"ffw-u02-manifest-v1\0" || body`, where the body is everything before the final 64-byte
Ed25519 signature; the prefix separates this use of a key from any other.

| Field | Size | Rule |
|---|---|---|
| magic | 4 | `FFWM` (`bad_magic`) |
| format | 1 | 1 (`unsupported_format`) |
| stage | 1 | 1 userspace, 2 kernel, 3 bootloader, 4 vendor package; others `bad_field` |
| flags | 2 | bit 0 vendor claim, bit 1 bypass claim, bit 2 A/B claim; other bits `bad_field` |
| key id | 8 | which trusted key signed |
| profile id | 1 + 1..48 | ASCII, lower case, first byte a letter or digit, `[a-z0-9._-]` |
| hardware revision | 1 + 1..24 | as above, upper case allowed |
| kernel capability profile | 1 + 1..40 | as profile id |
| ISA | 1 | 1 PowerPC32 big endian, 2 MIPS32r2 big endian |
| version, security version | 4 + 4 | display/ordering number; anti-rollback number |
| settings schema, settings read-min | 2 + 2 | what the image writes; the oldest it reads (`read_min <= schema`, both non-zero) |
| calibration schema | 2 | non-zero; never converted |
| wire schema, wire read-min, wire read-max | 2 + 2 + 2 | what the image emits; the oldest and the newest it reads (`read_min <= schema <= read_max`, all non-zero), so a newer sender beyond a peer's upper bound is as unreadable as an older one below its lower bound |
| features | 2 | bits 0..5: airplay2, alexa_bridge, protected_render, spotify_connect, synchronized_groups, tailnet_native (P01's required features) |
| artifact size, artifact SHA-256 | 4 + 32 | size non-zero |
| evidence digest | 32 | E01's evidence digest for the board; zero means none, and an image that names none is not admitted in production (section 4, step 8) |
| SSH present | 1 | 0 or 1; if 1: source digest 32, build digest 32, libc 1+1..16, OpenSSH major, minor, portable (1 each), fix (1), fix-evidence 32, auth flags (1), qualification receipt 32 |
| signature | 64 | |

A manifest longer than 512 bytes is `manifest_too_long`, one that runs out of bytes `manifest_too_short`, one with bytes after the signature
`trailing_bytes`. Lengths are compared with their bounds before any byte is taken.

## 3. Admission

`admit(policy, state, bytes)` runs the rules below in this order and returns the first refusal. The signature is verified before any other field
is believed.

| # | Rule | Refusal |
|---|---|---|
| 1 | structure (section 2) | the codes above |
| 2 | key in the trust store | `unknown_signing_key` |
| 3 | key not revoked | `revoked_signing_key` |
| 4 | Ed25519 signature over `DOMAIN || body` (strict) | `bad_signature` |
| 5 | stage is our userspace payload | `stage_forbidden` |
| 6 | no vendor / bypass / A/B claim | `vendor_claim_forbidden`, `bypass_claim_forbidden`, `ab_claim_forbidden` |
| 7 | profile id, hardware revision, ISA, kernel capability profile equal the board's | `wrong_board`, `hardware_revision_mismatch`, `isa_mismatch`, `kernel_profile_mismatch` |
| 8 | production only: the board is not a synthetic fixture and every fact is attested (E01 `activation_blockers` empty); the manifest's evidence digest is not zero and equals the one supplied for the board (zero means none on either side: two zeros are not a match) | `profile_not_attested`, `evidence_mismatch` |
| 9 | the image carries every required feature | `required_feature_missing` |
| 10 | `security_version >= floor` | `below_security_floor` |
| 11 | the candidate has not already failed its trial | `candidate_previously_failed` |
| 12 | if an image is installed: not the same manifest, not the same version number, a lower version only with explicit consent, the same calibration schema, and the stored settings schema readable (inside the candidate's read window, or restorable from a preserved copy that is) | `already_installed`, `version_reused`, `downgrade_not_permitted`, `calibration_schema_mismatch`, `settings_incompatible` |
| 13 | SSH declaration (section 7) | `ssh_fix_missing`, `ssh_unbound`, `ssh_password_forbidden`, `ssh_auth_unresolved`, `ssh_unqualified` |
| 14 | `artifact_size + reserve <= staging capacity` | `insufficient_capacity` |
| 15 | a plan: A/B only with an external receipt that carries a digest and covers two slots; otherwise a single slot, which needs a recovery path | `synthetic_receipt_for_real_profile`, `no_recovery_path` |

Consent to downgrade never lowers the floor (rule 10 comes first). A refusal keeps nothing about the candidate.

**Board identity.** `Board::from_profile` builds the device's board from E01's `BoardProfile` and refuses a profile that fails its own
integrity and admission gate (`profile_invalid`) or whose ISA this format cannot name (`isa_unsupported`). A candidate never supplies the
board it is checked against. E01's `activation_eligible` means the *evidence is complete*, nothing more; production admission is the separate
decision in rule 8, and no profile in this repository is attested, so production refuses every board today. That is the correct answer, not a
gap: it is what "unknown profiles are rejected before opening an output device" and "production admission is a distinct policy decision in the
update design" ask for.

## 4. The signature primitive

Ed25519 is verified by **`ed25519-dalek =3.0.0`** (`verify_strict`), behind one 50-line file, `src/sig.rs`. This crate implements no curve or
field arithmetic and no signing; it holds no secret. The dependency's default features are off, but its signing APIs still exist; U02 never calls them.
The shared workspace dependency graph can enable additional features, so the selected graph must be inventoried rather than inferred from this declaration.

The added crypto chain requires a current E06 review for each selected host and big-endian target. A parent crate's `forbid(unsafe_code)` does not cover
its dependencies: `subtle` includes unsafe operations, and the host SIMD backend differs from the expected serial 32-bit PPC/MIPS backend. A conditional
Fiat entry in the lock is not evidence that the default target uses that backend. These source observations do not establish target compilation, runtime
correctness, memory use or approval of the new dependency graph; those gates remain pending until their actual evidence is supplied.

`VerifyingKey::from_bytes` follows ZIP-215 (it accepts encodings RFC 8032 would not) and `verify_strict` does not look at a key's torsion
component, so a key enters a trust store only through `sig::key_admissible`: y below p (a byte comparison), decodes, not of small order,
torsion free. `verify_strict` then refuses a non-canonical S, a small-order R or key, and an R that is not byte-for-byte what it recomputes.

The signature and key vectors are produced by `tests/u02/ed25519_ref.py`, a pure-integer RFC 8032 implementation that shares nothing with the
crate. It is **a test oracle only and ships nowhere**: `test_u02.py` checks it against the RFC's section 7.1 vectors and, when the
`cryptography` module is installed, against OpenSSL (signatures byte for byte, verdicts on flipped bits). If that module is missing the check
is *not run*, and the runner says so.

**Not claimed:** that the dependency builds and answers identically on big-endian 32-bit MIPS/PPC (its backend is chosen by pointer width and
is the serial 32-bit one there), and nothing about its `unsafe` (in `constants.rs` and the x86 SIMD backends, outside the 32-bit path) beyond
this: it belongs to E06's reviewed dependency boundary, not to this crate. The host replay of the vectors says nothing about a BE guest.

## 5. The staged artifact and the persisted state machine

**Artifact.** The staged bytes are checked against the manifest: fewer than `artifact_size` is `artifact_truncated` (the stage stays open so the
missing bytes can be sent), more is `artifact_oversized` (a write that would pass the declared size writes nothing), the right length with
another digest is `artifact_digest_mismatch` (the stage is cleared and the candidate is remembered as failed). The medium is read again at
`finish_stage` and at `activate`: a verdict remembered from before is not trusted over the bytes now there.

**Persistence (U01).** Records `u02.upd` (phase, candidate SHA-256, staged checkpoint, boots left), `u02.inst` (summary of the installed image),
`u02.fail` (the last candidate that failed) and the mark `u02.floor` (the anti-rollback floor). **Every transition is one journal
transaction.**

```
Idle --begin_stage--> Staging --finish_stage--> Staged --activate--> Trial --report_boot(healthy)--> Idle (installed = candidate, floor raised)
                       |  ^                       |                   |
                       |  +- write_chunk          |                   +- report_boot(unhealthy) x3 --> Idle (rolled back; candidate remembered as failed)
                       +--------- abort ----------+  (not allowed in Trial)
```

* **The floor is raised in exactly one place**, the confirm, in the same frame that writes the installed image. Staging, activating and a
  failed trial never move it, so a failed trial rolls back to an image that is still above the floor, and a confirmed image can never be
  followed by one below it. `mark_regressed` (the journal's own rule) backs this.
* **Checkpoints.** The staging medium's writes are durable only after `sync`; the journal records a checkpoint (every 64 bytes) only after one.
  A restart resumes at the checkpoint and discards what is beyond it.
* **Restart is an admission.** `Engine::open` is also the restart. An update in progress is resumed only if the manifest copy on the staging
  medium (untrusted, like everything on it) hashes to the journal's record **and** `admit` accepts it again, in full, under the policy the
  engine is opened with and the journal's installed image, floor and failed candidate as they now are: a key revoked, a board or required
  feature changed, production turned on, evidence changed, a floor raised, consent to a downgrade withdrawn or a staging capacity shrunk since the
  stage began therefore drops it, in `Staging`, `Staged` or `Trial`. Admission never consults the update record, so a stage is not refused for
  being in progress. A dropped update leaves the installed image, the failed record and the floor untouched and the engine idle. A record this
  code cannot read is `corrupt_state`. Vectors `U02-ENG-019` (unchanged policy: every phase resumes and the trial still confirms) to
  `U02-ENG-029`.
* **A journal fault** poisons the journal; every further transition returns the journal's `poisoned` until it is reopened, which returns exactly
  the state before or exactly the state after the transition that was running (U01's contract, exercised here at every storage operation of
  every transition).
* **Trial.** `TRIAL_BOOTS` (3) unhealthy reports in a row roll the trial back; one healthy report confirms. What counts as healthy is U03's.

## 6. Rolling updates and rollback after a migration

`group_decision(members, index, candidate)`: may member `index` take `candidate` while the others stay as they are? Two images are
wire-compatible when **each** one's schema is inside the other's read window `read_min..=read_max`, upper bound included: there is no
negotiation and no fallback to an older version. A member that cannot talk to the candidate is a **conflict**: the
admission is refused (`wire_incompatible`) and the answer contains **no action on another member** (nobody is upgraded or migrated to satisfy
a new sender). A disconnected member is judged by the image it last reported and the answer lists it as `assumed`; a member nobody
has ever heard from, **connected or not**, cannot be assessed, so the admission is refused (`unknown_member_state`, naming every such member).
The model covers one upgraded member, one old member, one disconnected member and a member of unknown state.
`index` must name a member: an empty group, or an index at or past the number of members, has nobody to upgrade and is refused as `invalid_target`
before any member is assessed (never answered `ok` for a member that does not exist, and never as `unknown_member_state`).

`rollback_decision(stored_settings_schema, backup, target)`: after a settings migration the target image may be restored only if it reads the
stored schema or a preserved copy of an older one (`allow`, else `refuse:settings_incompatible`). Calibration is never migrated: a different
calibration schema is refused at admission.

## 7. The SSH declaration

An image that adds or retains an SSH daemon must bind the daemon's source and build digests, its libc, the OpenSSH version and the fix for the
musl/no-PAM password bypass (CVE-2026-123158; fix `4353fdc`, first in OpenSSH 10.6p2): `fix = upstream` is accepted only at 10.6p2 or later,
`fix = reviewed` only with the digest of the review; an older daemon with neither is `ssh_fix_missing`. Production admits public-key-only
authentication with `Include`/`Match` resolved, refuses password authentication, and requires the digest of the isolated-guest qualification
receipt. An offline-test configuration admits a password-enabled *lab* image and an unqualified one; neither can pass production.

This is a **release declaration**, not a scan: nothing here proves what is inside an artifact, and a byte pattern, a filename or a version
string is not evidence of the fix. The guest qualification itself (authorized key succeeds, unauthorized keys and passwords fail, 255/256/257
byte and maximum-length boundaries) is an external receipt that this crate only binds by digest. **No SSH server exists in the current
bootstrap or speaker paths, so no patch is claimed delivered for absent code.**

Primary-source check (2026-11-06): [Alpine's advisory](https://alpinelinux.org/posts/2026-11-05-openssh-password-authentication-bypass/)
describes passwords of **257–1,024 bytes**, under specific musl/no-PAM and account/configuration conditions; this is not a
256-bit threshold or a bypass of every SSH implementation. The [OpenSSH fix](https://github.com/openssh/openssh-portable/commit/4353fdc43ef646c43a8dda7025cc1a898caf1482)
changes the password/hash error handling. Patched backports require the reviewed-source path above, not an inferred version pass.
