# D04 contract: the protected render loop on the retained HAL (`ffw-5h5`)

Status: implemented offline, **verification pending**. Everything here runs against the P04 **fake
device**, which is a model, with render cost injected as ticks. It shows the scheduling, accounting
and ownership logic and says nothing about any board's CPU, any driver, or what anything sounds like.
Host simulation is not acoustic proof.

**A host-simulated CPU cost proves the classification logic, not that a board meets its deadline.**
The tests choose how long a render "takes" and show that the loop calls the result on time, a CPU miss
or a late wake-up correctly, and acts on it (drops the block, counts it, trips the watchdog). They
cannot show that any real render fits its window. The real per-block cost on each target stays open,
as D02's does.

## What exists

| Piece | Path | What it is |
|---|---|---|
| The loop | `crates/franken-speaker/src/render.rs` | `RenderLoop`: source -> D03 resampler -> D02 protection -> bytes -> `HalSession::submit` |
| Independent model | `tests/d04/reference.py` | the loop's timing, classification and accounting, written from this document |
| Scripted runs | `tests/d04/scenarios.json`, `generate.py` | 12 runs and what the model says happens; the Rust test replays each through the real loop |

| Log model and golden | `tests/d04/log_reference.py`, `log_golden.json` | an independent model of the log, and a hand-written run with its exact expected lines |
| Cases and runner | `tests/d04/cases.json`, `run_cases.py`, `scripts/e2e/d04` | invariant-to-test map, planted wrong rules, blocked items |

Nothing in D01, D02, D03 or P04 was changed to build this. The loop calls their public APIs. It uses
P04's event queue (`HalSession::take_event`) and one test hook on the fake (`capture_submissions`).

## Timeline

Time is the device tick. `start()` fixes `base`; block `k` is **released** at `base + 1 + k * period`,
must be **submitted** by `release + window` (its deadline), and is **presented** `min_submission_lead`
ticks after that. The lead comes from the device (`min_submission_lead_ticks`); if the device cannot
state it, or cannot state a stop deadline, the loop is not admitted.

* The one CPU renders one block at a time. A block starts at its release plus any wake-up delay, and
  not before the previous block finished.
* A block that finishes **on** its deadline is on time. One tick later it is late and is **dropped,
  never submitted**: audio that plays late is out of sync, and old audio must not accumulate.
* The device's irrevocable cursor is the frames it accepted. The loop only ever appends, so it never
  asks to change anything before that cursor; the stop path reports how many accepted frames were
  still unplayed (`StopReport::irrevocable_tail_frames`).
* A source that has nothing gives silence for the rest of the block. The block is still submitted, so
  the device never sees a gap it was not told about.

## Four causes, kept apart

Every started block ends in exactly one outcome:

| Outcome | Meaning |
|---|---|
| `OnTime` | submitted by its deadline with all of its programme |
| `Starved { IngressLoss }` | packets did not arrive; the content is gone |
| `Starved { DecodeDelay }` | packets arrived but decoding was late; the content is intact |
| `CpuMiss { late_by }` | the loop itself finished after the deadline with the source healthy; dropped |
| `CapacityRejected` | the ordinary share of the ring was full: **logical capacity**, not memory exhaustion |
| `ShortWrite { discarded }` | the device took only part of the block after the attempts allowed |

A fourth cause, a **driver underrun**, is a device-side observation counted apart from block
outcomes: the device reports that it consumed everything it was given although the loop dropped
nothing. If the loop had dropped a block since its last good submit, the dryness is explained by the
loop (`underruns_explained`) and is not blamed on the driver. The observation needs a position report
whose class is not `Unknown`; with an unknown class no underrun can be claimed either way.

A late wake-up that still meets the deadline is on time; one that does not is a CPU miss, and
`late_wakes` counts every delayed start. Content lost on the way in is a **discontinuity**: the
stream resumes as a new D03 epoch with a D02 fade-in, once, when the source returns. A late decode
loses nothing and starts no epoch.

Counters obey two identities once no block is in progress: every started block is in exactly one
outcome bucket, and `frames_generated = submitted + dropped_late + dropped_capacity + discarded_short`.
`reserve_breaches` counts renders that used more than the window less the 25% reserve, late or not.

## Lifecycle

`Ready -> Running <-> Muted`, `Running|Muted -> Draining -> Stopped`, and any active state to
`Faulted`; `Stopped -> Running` restarts (a new epoch); `Faulted -> Ready` only through an
acknowledged HAL reset.

* **Muted** is software: the output ramps to silence and the timeline keeps running, so unmuting
  needs no restart. The amplifier stays unmuted; the admitted safe device state is reached on a stop
  or a fault. Unmute is refused unless the protection DSP is active.
* **Stop** renders the ramp-out (bounded by `max_ramp_blocks`), then asks the device to drain and
  waits no longer than its stated stop deadline. **Cancel** mutes the device at once and waits the
  same bound for the acknowledgment. Neither claims `Stopped` without the device's acknowledgment.
* A fault requests a hardware mute and records whether it was acknowledged. Mute-requested is not
  mute-acknowledged.

## A held buffer is never released on a timeout

The loop never frees a slot. The session frees storage only on a device acknowledgment: a
completion, a flush, or a reset. Consequences, each a test:

* lost completions leave slots kernel-owned for as long as they last; blocks then find the ordinary
  share full and are `CapacityRejected`;
* a stop the device does not acknowledge, within its deadline, **faults and quarantines** what is in
  flight (`cancel_drain`); it does not free it;
* destroying the loop (process death in this model) keeps what the kernel may still read alive, and
  the leak ledger counts it.

## Admission and the cleanup reserve

Everything the render path touches (block buffers, interleave buffer, event queue storage) is
allocated before `Running`. `reserve_slots` ring slots are **never** used by ordinary submission, so
the stop path always has room for its ramp-out. A ring with no ordinary slot is refused at admission.

`AdmitFaults` injects **logical** admission failures. This is a model of admission control saying no;
it is not the allocator aborting and not the kernel killing the process, neither of which can be
reasoned about here.

* `start` and `reconnect`: refused with a typed error, nothing changed, the playing stream untouched.
* `cancel` and `drain`: ordinary capacity is gone, and the stop must still finish on the reserve.

The render path's own code allocates nothing after construction. The P04 session and the fake device
do allocate (the fake allocates per polled event), so an allocation-free claim covers the loop and
the DSP stages only.

## Control

Other tasks reach the loop through a `ControlPort`: a bounded queue (16) with `Mute` and `Stop`
latched so they are never refused and are applied first. The loop only ever `try_lock`s the port, so
a sender that is slow, or blocked while holding the lock, cannot delay a render: the loop skips
servicing that tick and counts it. At most four commands are applied per tick, so a storm cannot take
the render budget. Commands queued before a start do not outlive a stop.

## Events and the sink

The loop emits `RenderEvent`s (state changes, non-on-time blocks, driver underruns, faults) into a
bounded, critical-first queue of 64 that its owner reads with `take_event`. It is the same queue
policy P04 uses for session events: ordinary events are dropped first, a fault evicts the oldest
ordinary event, and every loss is counted. A full, slow or unread sink changes no deadline and no
outcome (tested: the same run, read every tick and never read, differs only in the drop counter).
Events carry counters and codes, never audio.

## Diagnostics (`ffw.log.v1`)

The bead asks for versioned structured JSONL with identifiers, counters, the injected fault and the causal
chain; bounded memory with dropped-event counts; redaction; and "critical test evidence loss marks the result
incomplete". `RenderLog` writes that JSONL itself from the loop's events; `franken-test-support` is a
dev-dependency used only by the tests, which round-trip every line through its `DiagnosticEvent` and its
redactor. The owner calls `log_event(&event, &counters, in_flight)` for each event taken from the loop and
`log_summary` once at the end.

The log is a **consumer**. It takes shared references and has no way back into the loop, so a full, tiny, absent
or never-drained log changes no deadline and no outcome. This is tested by running the same watchdog scenario
with no log, with a one-line log and with an unread one: the counters, the state and the tick are identical.

| Event | `event_kind` | `cause` | Critical |
|---|---|---|---|
| state change | `d04_state` | none | when it enters `faulted` |
| block | `d04_block` | `ingress_loss`, `decode_delay`, `cpu_miss`, `capacity_rejected`, `short_write`; none when on time | no |
| driver underrun | `d04_driver_underrun` | `driver` | no |
| rejected control command | `d04_control_rejected` | `queue_full` | no |
| fault | `d04_fault` | the reason's root: `hal_session_fault`, `device_gone`, `flush_not_acknowledged`, `consecutive_cpu_misses`, `protection_dsp_inactive`, `resampler_refused_block` | yes; `fault` names the reason |
| summary | `d04_summary` | none | yes |

Field rules. `correlation_id` is `block-N` for a block and `tick-N` otherwise. `state_revision` counts the
state changes logged so far. `source_epoch` is the loop's `epoch_resets`. `queue_depth` is the ring slots in
flight. `latency_us` is a CPU miss's lateness times the tick length **if the owner supplies it**
(`with_tick_micros`), and 0 otherwise; the loop's tick is the device's tick and this module does not know how
long it is. `timestamp_mono_ns` is the tick count times that length (one nanosecond a tick when unknown): it
orders lines and is not wall time. On a line that is not a fault, `fault` names the injected admission failures
in force (`admit_start+admit_drain`); on a fault line it is the reason. The summary carries the counters that
give the denominator (`n`, `ok`, `ing`, `dec`, `cpu`, `cap`, `sw`, `ur`), what the loop's own queue dropped
(`evd`, `eve`, `evc`) and what this log dropped before it (`ld`, `lc`).

**Bounded, and loss is visible from both sides.** The log keeps at most its capacity. A full log drops ordinary
lines first, a critical line evicts the oldest ordinary one, and a critical line is lost only when the log holds
nothing but critical lines. Every line is counted, and `emitted` equals kept plus dropped plus evicted plus
lost. `evidence_complete()` is false when this log lost a critical line **or** the loop's counters say its own
event queue did (`events_lost_critical`). A line is built from enum names, numbers and identifiers that passed
`safe_id`, so no audio, token, address or free text reaches one.

**What this does not give.** There is no separate human-readable summary file: the summary line and the runner's
output are the human view. A real wall clock, a per-line byte cap and a rate limit are not provided (the line
count and the message length are the bounds). Nothing here is device evidence.

**How it is checked.** `tests/d04/log_golden.json` holds a hand-written run of events and the exact twelve lines
it must produce, and a bounded scenario (capacity 3, ten ordinary blocks, one fault: the log keeps blocks 1 and 2
and the fault). `tests/d04/log_reference.py` is an independent model written from this section; it and the Rust
must both reproduce the golden byte for byte. Five planted wrong rules (a frozen revision, an unscaled latency,
an ignored epoch, a dropped schedule, critical lines not given priority) must each make the model disagree with
the golden against a green baseline. The Rust additionally drives the real loop into a watchdog trip and checks
the log tells that story.

## Samples: what is and is not checked

A differential test runs the real stages (D03 then D02) with no loop around them and requires that
the bytes the fake device received equal that, block for block, in both byte orders, with none lost
or repeated. A graceful stop is checked to ramp down in the submitted samples and to end within the
ramp plus the stop deadline. This pins the loop's plumbing and framing.

It does **not** check D02's and D03's arithmetic against an independent model here: each has its own
independent reference and tests. The bead's wish for sample output compared against an independent
Python reference of the whole chain is therefore **only partly met**: the loop is differential-tested
and the stages are separately referenced, but there is no single independent model of the composed
chain. The byte order handed to the device is a stated harness model until E04 maps it.

## Process death versus device loss

* **Device loss** is a persistent fault: the loop records `DeviceLost`, requests a mute the gone
  device cannot acknowledge (`last_mute_acknowledged == Some(false)`), and a reset cannot recover it.
* **Process death** is invisible to the loop, because the loop is gone. What can be shown is what the
  dying owner leaves behind: a best-effort mute requested, the kernel's buffers kept alive, the leak
  counted. Whether the amplifier muted is **external qualification** (`D04-EXT-PROCDEATH`).

## What stays open

* **P03**: the production control runtime (regions for device lifetime and streams, cancellation
  ownership, pre-admitted task and finalizer capacity, the render task's separately measured budget).
  This loop takes commands through a bounded port and never waits on it; binding that port to the P03
  runtime is open (`D04-OPEN-P03`).
* **E04**: the real driver's submission lead, underrun signal and byte order. The lead is the fake's
  and the byte order is a stated model.
* **Board CPU**: render cost is injected. No CPU, p99.99 or 24-hour claim is made
  (`D04-EXT-BOARD`).
* **Driver counter reset** (the bead's section on failure behaviour: invalidate the presentation mapping and
  reinitialize safely). The loop does not do this yet, and the HAL has no anomaly kind for a consumed counter that
  goes backwards, so it is a P04/E04 change first. The diagnostics log would carry it as one more critical line.
* Wiring: `pub mod render;` and `pub mod render_log;` in `franken-speaker/src/lib.rs` are added by the supervisor.
  Until then neither file is compiled, and `D04-META-002` and `D04-META-007` are blocked, not passed.

## Running and verifying

```
scripts/e2e/d04 --tier smoke      # scenarios, mapping, hygiene: qualified when all pass
scripts/e2e/d04 --tier full       # adds planted wrong rules and the self-test; exits 3 by design
```

The full tier exits 3 (NOT QUALIFIED) because required items are counted as blocked, not passed:
the central Rust run, the board measurements, the process-death qualification and the P03 runtime.
Central Rust verification, each its own invocation:

```
RCH_REQUIRE_REMOTE=1 rch exec -- cargo test -p franken-speaker
RCH_REQUIRE_REMOTE=1 rch exec -- cargo clippy --workspace --all-targets -- -D warnings
RCH_REQUIRE_REMOTE=1 rch exec -- cargo fmt --all -- --check
```

Expected values come from the model, which shares an author with the loop. Tests do not prove
perfection.
