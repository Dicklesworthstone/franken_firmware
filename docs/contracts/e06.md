# Contract E06 — Dependency Feature and Target-Availability Audit

Bead `ffw-unk`. Offline, stdlib Python, no build: `scripts/e06/audit.py` reads the resolver and the dependency
sources already in the local cargo cache and reports **facts** per package and per target. It never says a
dependency is admitted; every `review` item is a decision for a human. Its input, E03, is closed (`48fa17c`).

## Inputs and what is, and is not, a build
- `cargo metadata --format-version 1 --locked --offline --filter-platform <triple> --manifest-path Cargo.toml`, once
  per platform: the two big-endian targets (`mips-unknown-linux-musl`, `powerpc-unknown-linux-musl`) and the host as a
  **reference platform**. A resolver read: it compiles nothing. The unfiltered view is never used, because it keeps
  edges no target takes (serde's `cfg(any())` markers).
- `Cargo.lock` (exact version, source, checksum) and the crates' own sources in the registry cache.
- The compiler's own target spec (`rustc --print target-spec-json -Z unstable-options --target T`, nightly) for the
  floating-point ISA and atomic width. If it cannot be captured the report says so; it does not guess.

## What it records
| Fact | Source and rule |
|---|---|
| **Pin** | name, version, source and checksum from `Cargo.lock`, plus the features cargo enabled on that target, as `pins.<platform>.rows` with a sha256 `digest` over them. |
| **Role per platform** | `member`, `linked` (reachable from a member over normal edges, never entering a proc-macro crate), `host-only` (proc-macro crates, build-dependencies, member dev-dependencies and everything beneath them, with the reason), `absent`. |
| **Native code** | `links` key; a build script; build-dependencies on `cc`/`cmake`/`pkg-config`/`bindgen`/...; `rustc-link-lib/-search/-arg` strings or `cc::`/`pkg_config::` paths in `build.rs`. A build script alone is only `info`: most just probe the compiler. |
| **Unsafe** | count of the `unsafe` keyword in the crate's **own** source tokens (lexer, not text search: comments, strings, raw strings and `r#unsafe` do not count) per file; and the declaration mechanism: crate attribute, manifest lint, workspace lint, with level `forbid` or `deny`. |
| **std / alloc / no_std** | per target, from the crate attributes and the features cargo enabled there: `#![no_std]`, `#![cfg_attr(<pred>, no_std)]` and every `[#[cfg(gate)]] extern crate std;` (thiserror, serde_json and memchr are `#![no_std]` yet link std under their `std` feature). A crate is *effectively* std if any linked dependency is. `references_alloc` is a path reference, not a proof of allocation. |
| **Duplicate versions** | several versions of one name, per platform; `review` only when more than one is linked. |
| **License metadata** | `license` expression, or a `license-file` that exists; `missing` and `file-missing` are separate findings. |
| **Target-gated dependencies** | every `[target.'cfg(..)'.dependencies]` declaration and, per platform, whether cargo kept the edge. |
| **Floating point** | the compiler's target spec (`+soft-float`?) and which workspace crates and dependencies use `f32`/`f64`. |

## Severities and exit codes
- **blocker**: the audit cannot stand. A platform cargo cannot resolve (`target-unsupported`, or `resolver-failed`: two
  different outcomes); a registry package missing from `Cargo.lock` or without a checksum; a git source not pinned to a
  40-hex commit; a path dependency outside the workspace; a workspace crate with unsafe that other workspace crates depend
  on (unless named in the unsafe-allowed policy input) or that declares no forbid/deny at all; a planned build check that
  failed or whose results conflict.
- **review**: a human decision is required. Unsafe in a linked dependency; `links` or a native build signal; two linked
  versions; a missing license; unscanned source; a std/no_std question the audit cannot decide; our own workspace crates
  using floats on a soft-float target; a workspace crate with unsafe that nothing depends on.
- **info**: everything else (build scripts without native signals, gated dependencies, candidates not in the graph,
  host-only duplicates, no native atomic64, planned checks with no result).
- A **review** item found only on the host platform is demoted to info: the host is not firmware. Blockers are never lowered.
- Exit codes of `audit.py audit`: `1` blockers, `3` only review items, `0` nothing to review, `2` usage. `scripts/e2e/e06`
  runs the tests first and does not audit with a tool that fails them.

## The rule about forbidding parents
A crate's unsafe finding is computed from **its own source only**; no parent's `forbid(unsafe_code)` is an input to any
dependency's classification. Where a forbidding parent pulls in a child with unsafe, the finding names both ("the
forbid(unsafe_code) of mid does not cover this crate"). The tests plant exactly this graph and also prove the child's
record is identical whether its parent forbids unsafe or not.

## Minimal selected graph per target
`audit.py plan [--jobs N]` prints one command per workspace crate per big-endian target:
`RCH_REQUIRE_REMOTE=1 rch exec -- cargo +nightly check --locked --release -p <crate> --target <triple> -Z build-std=<set> [-j N]`.
`<set>` is `core,alloc` only when the crate and its whole linked closure are no_std, otherwise `std,panic_abort`.
`--jobs` exists because RCH admits a build against a worker's slot count with its own core estimate (it ignores
`CARGO_BUILD_JOBS`), as the refused E03 run showed. The commands are **proposed**: the first run decides. Results come back
as JSON lines (`crate`, `target`, `status` `pass`|`fail`, `evidence`, `note`) through `--build-results`; a missing result is
`not-run` and is counted, never `pass`; contradictory results are `conflicting` (blocker); a result for something not in the
plan is rejected. A crate that does not build for a big-endian target is a **finding** (`does-not-build`, blocker), not a
detail to hide. The analyzer never runs a build itself.

**Central results are verified before they are believed.** `audit.py ingest` reads the raw log behind every supplied
row and requires the command the worker ran to equal the planned command, the remote exit status to be the row's and
to be 0 exactly when the row says `pass`, a cargo `Finished` line and no error line, the row's worker and revision to
be the log's and the expected revision, and the denominator to match the plan (every planned check exactly once, no
unplanned result). It writes nothing unless every claim is supported, and what it writes is a **redacted** record: raw
RCH logs carry a worker's network address and the absolute paths of the machine that ran the checks, so they are not
committed; the record keeps the command, exit status, timings, unit and warning counts and the sha256 and size of each
raw log. A pass here is a **type-check**: `cargo check` shows that the pinned graph resolves and type-checks for the
target with `-Z build-std=std,panic_abort`; it does not link, run or boot anything.

## Candidates
Asupersync, `franken_kernel` (a crate inside the Asupersync repository), FrankenLibC (the Rust `libc` crate is only an FFI table) and codecs
are not in this workspace's graph, so the audit of the workspace reports each as `not in graph; unevaluated`. The first three are local
Cargo repositories and are inventoried **at pinned revisions, read-only**, in `toolchain/results/e06/upstream/` (README there): Asupersync
`8940119023c0`, FrankenLibC `76d7f3469f5f`. Codecs are not: see the next section.

How a third party is audited (`audit.py audit --subject upstream`):
- **Per configuration, through a scratch consumer.** `cargo metadata` of an upstream workspace resolves all members together, so features that
  other members enable are unified into the crate whatever `--no-default-features` says (measured: `asupersync` showed `fuzz`, `metrics`,
  `test-internals` and `default` enabled with no feature selected). A configuration is therefore audited as a one-member workspace that depends on the
  pinned export by path with the exact features, starting from the upstream's own `Cargo.lock`; the lock's registry packages are checked to be exactly the
  upstream's.
- **Upstream's unsafe is reviewed, not a violation.** This project's rule (P01: workspace crates forbid unsafe) is not a rule of another repository, so
  those findings are `review` items for an upstream subject (`upstream-crate-unsafe`), never blockers. A resolver failure is still a blocker.
- **A missing lock is said so.** `--generate-lock` generates one offline in an *export* (refused inside a git work tree), and the report carries
  `lock.origin: generated-offline` and a `lock-generated-not-an-upstream-pin` review item.
- **Roots can be named** (`--scope-crates`), features selected (`--features`, `--no-default-features`, validated, forwarded to cargo and to the planned check
  lines) and the plan narrowed (`--plan-crates`). A compact per-package record (`--inventory`) is what is committed; the full report is 1.4 MB for a 477-package graph.
- Nothing is downloaded: a crate missing from the local registry cache makes the resolve fail and is recorded (FrankenLibC's whole workspace is, for 13
  crates that are only dev-dependencies, so its inventory is of a reduced scratch export whose two edits are recorded).

## Codecs: why E06 cannot inventory them
The bead's scope lists codecs. The plan names codec **formats**, not codec **crates**: A02 (AirPlay) names AAC and ALAC profiles, the Spotify path is a native
integration, and S02 (`ffw-6dh`, "Qualify negotiated source-codec profiles") owns the selection: "Bounded pure-Rust codec selection ... Derive mandatory decoder set from
pinned Spotify/AirPlay negotiated formats". No codec crate appears in any bead or in `FIRMWARE_ASSESSMENT.md`, and none is in the local cargo registry cache, so there is
nothing to pin or audit offline.

**A dependency cycle sits here.** S02 lists E06 as an input ("Pinned per-target dependency/unsafe/license feature inventory for ... codecs"), while the codec set that E06
would inventory is S02's output. E06 can audit any named candidate with the same method as the upstream inventories (pin it in a scratch consumer, read the closure, own unsafe,
license, std/alloc and floating-point use on the soft-float MIPS target) the moment someone names one, and the offline method needs its sources in the local registry cache. Until
then E06 cannot satisfy that part of its scope without inventing a candidate, which it will not do: this is a question for the owner (name candidates, or re-scope the codec
inventory to S02), not a gap another run closes.

## Known limits (recorded, not covered)
- Unsafe produced by a macro expansion is invisible; unsafe under a `cfg` that is off for the target is still counted
  (e.g. `portable-atomic` counts its 128-bit backends); `#[path]` modules outside the scanned directory are not followed;
  `tests/`, `benches/` and `examples/` are not scanned.
- Cargo reports one feature set per package per platform, which can union what a build-dependency and a normal
  dependency would each get under resolver 2.
- A compiler target spec cannot establish that a board's CPU has an FPU. For MIPS the spec says `+soft-float`; for
  PowerPC it says nothing, so the report says "hardware FPU presence is not established here".
- `Cargo.lock` pins the sources; the audit reads the cached copies, so a cache that differs from the registry is not
  detected beyond the checksum cargo itself verified.
- A reviewed capability manifest is an inventory and test input, not a promise that scanning finds every dynamic syscall.
- `cargo check` is not `cargo build`: the central pass type-checks and does not codegen, assemble or link.
- `cargo metadata` unifies features across all workspace members, so the audit of a multi-member workspace (this project's own included) reports each package's
  features as the union over members, not as one crate's build would see them. A per-crate `cargo check -p X` unifies only over X's closure. For a third party's
  configuration the consumer method above is the one that is valid; this project's workspace is audited as built together.
- An upstream inventory is of a graph, not of a build. A crate missing from the local registry cache cannot be resolved offline, and nothing is downloaded.
- One central run, one worker, one revision: nothing measures variation between workers, and a different revision
  needs a new run (the evidence directory is named for the revision it describes).
- The ingest verifies that a log supports a row; it cannot tell whether the worker's toolchain was the one named,
  because RCH does not print it in the log. The log's command and exit are checked, not the compiler.

## Running
- `scripts/e2e/e06` tests, then audits this workspace. `--tests-only` and `--audit-only [--json OUT] [--build-results F]
  [--unsafe-allowed a,b] [--jobs N]` select a half. Audit a **clean export of a revision** (`git archive`), not a worktree
  another agent is editing: a half-made manifest edit makes `cargo metadata --locked` fail there.
- `python3 -B -I scripts/e06/audit.py plan --jobs 2` prints the central build-check lines, or refuses (exit 1, reasons on
  stderr, nothing on stdout) when a platform cannot be resolved or the plan would be empty.
- `python3 -B -I scripts/e06/audit.py ingest --plan-file PLAN --results RESULTS --logs-dir LOGS --rev SHA --out NEW`
  verifies centrally produced results against their raw logs and writes the redacted record (exit 1 and no file when
  any claim is unsupported). `audit.py audit --build-results NEW` then folds the record into the report.
- `audit.py audit|plan` also take `--features`, `--no-default-features`, `--plan-crates`, `--scope-crates`, `--subject {own,upstream}` and `--generate-lock`;
  `audit` takes `--inventory OUT --subject-name N --subject-rev SHA` for the compact record. `python3 -B -I scripts/e06/fp_isa.py` establishes the float ABI per target.
- Tests: `tests/e06/test_rustscan.py` (lexer), `test_audit.py` (hand-written graphs, a deliberately contaminated graph),
  `test_live.py` (a real path-only workspace through real `cargo metadata`, and a clean export of HEAD),
  `test_checks.py` (the ingest verifier over synthetic logs), `test_upstream.py` (feature selection, scopes, the upstream subject, offline
  lock generation and the inventory, on real cargo over small workspaces), `test_fp_isa.py` (the float-ABI probe) and `test_evidence.py` (the committed evidence
  directories agree with themselves, with the revisions they name, and carry no path, address or user name).
