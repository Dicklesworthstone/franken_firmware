# V01 measured latency timeline

`franken_clock::latency` accounts for one audio snapshot in one monotonic
clock epoch and route revision. V01 remains open: D04/N04 integration,
real queue/driver measurements and central runtime-event checks remain pending.

The previous `LatencyLedger` API is a compatibility summary of component
durations. It cannot establish nonoverlap or measured output latency. The
new `LatencyTimeline` consumes intervals, not an assumed sum of delays.

- Eight fixed stage slots bound storage and work. Queue observations replace
  their previous slot. Required missing/unknown stages refuse an estimate.
- Ingress and output are mandatory. Effective latency is the elapsed span
  between these endpoints. The union of stage intervals reports accounted
  time; gaps remain `unaccounted_ns`. Fixed-only, variable-only and shared
  time partition that union without double-counting parallel stages.
- Each observation binds clock, source epoch, route revision and snapshot.
  Changing any of these invalidates the old estimate. Freshness uses a local
  monotonic observation time and an explicit maximum age, including refusal
  of future snapshots. Driver depth changes require a new observation;
  observations from different snapshots cannot be mixed.
- Affine clock conversion has anchors, rate, an admitted horizon and endpoint
  uncertainty. Conversion rounds intervals outward and scales uncertainty
  upward. Negative inputs, reversed intervals, nonpositive rates and arithmetic
  overflow produce typed errors. Rejected replacements retain the last value.
- Endpoint uncertainty widens the elapsed-latency range. Inferred stages are
  explicitly flagged. Unknown/unbounded output delay cannot be supplied as
  an exact result: omit/invalidate the stage or supply a finite justified
  bound and mark it inferred. The type cannot verify a caller's provenance.
- `video_delay_advice` gives a cooperative caller a requested delay plus a
  residual range. Its 40 ms test covers both extremes, and is a single
  observation bound, never a percentile or proof that a phone honors timing.

## Executable checks

The central supervisor runs, through strict-remote RCH:

```sh
cargo test -p franken-clock --test latency_timeline -- --nocapture --test-threads=1
cargo test -p franken-clock --test latency_events -- --nocapture --test-threads=1
cargo test -p franken-clock --lib events::tests -- --nocapture --test-threads=1
cargo test -p franken-alloc-probe --test latency_no_alloc -- --nocapture --test-threads=1
cargo clippy -p franken-clock --all-targets -- -D warnings
```

The first command executes seven integration tests. Four hand-specified
delay injections cover serial, overlapping, gapped and nested stages.
An independent discrete occupancy oracle checks all 441 interval pairs
over a five-tick domain. Other tests cover ordering, moving depth,
unknown/stale/route/epoch/snapshot invalidation, affine conversion,
uncertainty, signed inputs, overflow, and video residual bounds.

Judge the actual central test log:

```sh
scripts/e2e/v01 --tier smoke --rust-log path/to/central-latency-timeline.log
scripts/e2e/v01 --tier full --rust-log path/to/central-latency-timeline.log \
  --event-log path/to/central-latency-events.log \
  --event-unit-log path/to/central-events-unit.log \
  --allocation-log path/to/central-latency-no-alloc.log
```

Smoke requires all ten registered case events and the exact seven-test
summary, with no ignored/filtered cases. It checks independent expected
values. Missing cases, duplicate events, malformed data, lost events or
failed tests remain incomplete. Diagnostics use fixed synthetic identifiers
and a virtual monotonic timebase. The judge reads at most 8 MiB and each
event at most 8 KiB. Retain the original central command/source receipt and
log; the log digest alone does not prove which source produced it.

Full additionally requires six event-adapter tests, four shared queue unit
tests and the actual allocation-counter test (18 Rust tests total). All four
logs are mandatory. A missing/failed/filtered supplemental test remains
incomplete. The named `events::tests` invocation permits filtering unrelated
library tests while still requiring all four exact queue test names. A broader
passing library run is accepted only with those four named cases present;
its actual test count remains in the report. Combined Cargo logs are selected
by authentic binary sections, retaining their original summary bytes, parent
log digest and byte ranges. A failed/ignored parent or truncated/ambiguous
section refuses qualification. The same combined clock log can therefore be
passed for the first three arguments above. Every timeline and event-adapter
test also requires its exact passing result line; removing a line invalidates
the evidence even if its case events and summary remain. Sixteen Python judge canaries
test the judge only. `--tier soak` remains incomplete until
a separately bounded soak campaign is implemented.

## Runtime logging path

The shared `franken_clock::events::EventBuffer<T, N>` uses fixed storage and
the HAL's critical-first policy: critical records evict the oldest ordinary
one, and a queue containing only criticals reports critical loss. N03 and
V01 use this one implementation without adding a HAL dependency. Every
emission advances its sequence, including dropped records. Counters retain
full/rate/unavailable/regressed-clock losses, evictions and critical loss.
`emitted = delivered + pending + dropped` holds until counter saturation,
which is explicitly flagged. Critical loss is a subset of dropped events.

The V01 adapter computes first and attempts a bounded typed-event insertion.
Successful estimates are ordinary; refusals are critical. The control side
pops records, then calls `to_jsonl`; only serialization allocates. Tests parse
each line into the shared Q00 schema and compare re-serialized bytes. No
test-support crate enters the production dependency closure. Identifiers
must already be numeric pseudonyms; no audio or peer text enters the records.

The generic queue tests port the HAL's hand-traced priority case and compare
6,561 seven-operation schedules against a separate deque model. The allocation
probe uses the existing audited test allocator, proves it is active, measures
healthy/full/rate-limited/unavailable/refusal computations, and uses allocating
control-side serialization as the positive control. This proves an allocation
property, not a hardware deadline. Disk persistence/caps and actual D04/N04
call sites remain caller-owned, pending integration.

No device, Spotify/AirPlay application, acoustic delay or actual display
behavior is qualified by these synthetic observations. Sink-independence
tests and allocation instrumentation must actually run before admission;
the bounded test log itself cannot establish those properties.
