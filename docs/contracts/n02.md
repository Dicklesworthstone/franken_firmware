Scope is the message-handling state machine between authenticated peers and one
`franken_session::UnifiedGroupSession`: authentication, replay and retry handling, bounded queues,
rate limits, epoch and revision fencing, cancellation, and counters. Transport (sockets, framing,
encryption of the link) is N01/N07's, user-interface wiring is U01's, and the real key hierarchy is

host simulation of a state machine; it says nothing about a network, a real MAC, a board or what is
audible.

## 1. What the channel is

`ControlChannel<A: PeerAuthority>` has two calls, deliberately separate:

* `submit(now_ns, request)` — a peer's signed request arrives. The answer says whether it was
  **accepted into a queue**, answered from memory, or turned away. **Accepted is not committed.**
* `step(now_ns, &mut session)` — the owner of the session applies what has been accepted, a bounded
  number per call, and gets back one `Settlement` per command that reached a terminal outcome.

Time is passed in as nanoseconds; the channel reads no clock and opens no socket. The caller drives
`step` from its own schedule, so the latency of "accepted to applied" is the caller's period times
the queue position, not something this module hides.

## 2. Request and what the proof covers

A `ControlRequest` is a `RequestBody` plus an `AuthProof` (1..=64 bytes). The body is
`(peer, seq, epoch, expected_revision?, command)`:

| Field | Rule |
|---|---|
| `peer` | 1..=32 bytes of `a-z 0-9 . _ -`; the identity the authority knows |
| `seq` | at least 1; per peer; the idempotency key together with `peer` |
| `epoch` | the group epoch the sender believes is current |
| `expected_revision` | the session `state_revision` the sender last read. **Required** for relative commands, and from a remote controller for `SetMemberVolume`, `SetGroupVolume` and `SetMemberMute`; a stop and a cancel need none, and the local user needs none (§3, §4) |
| `command` | one of the seven below |

| Tag | Command | Lane | Notes |
|---|---|---|---|
| 1 | `SetMemberVolume{member, volume 0..=100}` | ordinary | |
| 2 | `SetGroupVolume{volume 0..=100}` | ordinary | |
| 3 | `AdjustMemberVolume{member, delta -100..=100}` | ordinary | relative |
| 4 | `AdjustGroupVolume{delta -100..=100}` | ordinary | relative |
| 5 | `SetMemberMute{member, muted}` | priority | |
| 6 | `StopGroupPlayback{now_ns, irrevocable_dma_tail_ns}` | priority | |
| 7 | `Cancel{target_seq}` | priority | withdraws an earlier **ordinary** command of the same peer |

The bytes the proof covers (`RequestBody::signing_bytes`), all integers big-endian:

```
"FFCP" | version=1 | len(peer) peer | seq u64 | epoch u64 |
presence u8 [revision u64 if presence=1] | tag u8 | command fields
```

with a member label as `len u8 | bytes`, a volume as one byte, a delta as one two's-complement byte,
a mute flag as one byte, and the stop and cancel fields as `u64`s. Every field is covered; the
presence byte makes "no revision" differ from "revision 0". Five worked byte strings are pinned in
`crates/franken-control/tests/vectors/n02_scenarios.json` (`signing_vectors`), derived by hand and
checked by both the Python reference and the Rust replay.

## 3. Submit order

Each stage refuses without having changed any later stage. **Nothing is mutated before stage 1
passes.**

1. **Authenticate.** `PeerAuthority::authenticate(peer, signing_bytes, proof)`. A failure
   (`UnknownPeer`, `Revoked`, `BadProof`) returns at once: no rate-limit bucket is created or spent, so
   a flood of forgeries cannot use up a real peer's allowance. Priority is not an exception.
2. **Epoch binding.** A key bound to epoch *e* is refused (`EpochNotBound`) under any other epoch. A
   peer not bound to an epoch (the local user) skips this.
3. **Rate limit**, per authenticated peer **and** per lane: a token bucket of `burst` with one more
   token per `interval`; a refusal states the exact wait.
   3b. **Observed revision.** A remote controller's volume or mute setter without `expected_revision` is
   `RevisionRequired`, turned away before it is queued. This is what lets a copy composed before a
   restart be told from a fresh command (§4). It is a form check after the rate limit, so a peer
   cannot send it for free.
4. **Duplicates.**
   * A request with the same `(peer, seq)` already waiting: identical → `AlreadyQueued`; different →
     `IdReuse`.
   * An outcome on record: identical request → `Settled(outcome)` (the recorded outcome, never a new
     one); different → `IdReuse`.
   * Not on record but at or below the peer's **floor** → `OutOfWindow{floor}`: unknown, and not
     applied.
5. **Bounded enqueue** into the ordinary or the priority lane; a full lane → `QueueFull`.

A request refused at stages 1–3 or 5 records nothing and consumes no command number: the same bytes
can be sent again when the reason has passed. (A stage 5 refusal has already spent a rate-limit token,
because the limit is checked first; a stage 1 refusal spends none.)

## 4. Step order

Expire anything that has waited `pending_ttl` (→ recorded `Refused(Expired)`). Then, at most
`max_per_step` times: take the next command — the local user's priority command first, otherwise the
oldest priority command, otherwise the oldest ordinary one — and:

1. **Re-check the authority** (`is_current`). A peer revoked, re-admitted or rebound since the command
   was accepted yields `Refused(AuthorityExpired)` with no effect.
2. **Cancel** is handled here (§6) and skips the checks below.
2b. **Group lease** (G01, below): a command that changes the group needs a live lease, or it is refused
   before anything else is looked at and before the session is touched.
3. A **remote controller** is held to the group epoch (`StaleEpoch`, `EpochAhead` — both refused, and
   the channel never advances the epoch) and to its `expected_revision`:
   * a revision the session has not reached is `RevisionMismatch`, for any command;
   * a **relative** command must name exactly the current revision (`RevisionMismatch`): its delta
     was computed against that state and means nothing against another;
   * an **absolute** command (volume or mute setter, or a stop that names one) must not be older than
     the revision at which this channel incarnation began, the *floor*, taken from the session at the
     incarnation's first `step`: `StaleRevision{observed, floor}`. It may be older than the current
     revision, however far the group has moved since, because absolute volume is naturally repeatable:
     a client may pipeline updates before the first acknowledgement and two controllers may interleave
     (`INV-ABSOLUTE-REPEATABLE`). What it may not be is composed before the incarnation began, which is
     how a copy delayed across a restart looks (`INV-RESTART-FENCE`).

   The **local user** is exempt from the epoch and revision checks: it acts on what is audible in front
   of it. It is still authenticated, rate limited, and deduplicated.

   *Why not require the exact current revision for absolute commands as well.* It would refuse the
   pipelined and interleaved cases above, which are legitimate, and it would contradict the bead's
   "absolute volume is naturally repeatable". The floor refuses exactly the stale class, a copy that
   outlived a restart, and nothing else.
4. A relative command is resolved against the live value (member volume or group master) and
   clamped to 0..=100; an unknown member is `Refused(UnknownMember)`.
5. The command is handed to `UnifiedGroupSession::apply_command` at the session's current epoch with
   a channel-minted number (§8). An unknown member is `Refused(Session(UnknownMember))`: the sender's.
   **Any other session refusal** (a repeated or out-of-window number, a stale epoch) cannot be the
   sender's doing, because the channel chose both; it is `Refused(InternalFault)`, counted in
   `ChannelStats::internal_faults`, kept for the operator in `last_internal_fault()`, and recorded
   without detail. The next command is minted a fresh number, so a collision clears itself.

Every terminal outcome is recorded by `(peer, seq)` together with the request body it answered.

### The group lease (G01)

`franken-session` (G01) gives the group one configured issuer and an `AuthorityToken { group_id,
issuer_id, epoch, expires_at_ns }`, checked by `AuthorityToken::check(session, now_ns)` on every group
mutation, with `advance_epoch` the only epoch mint. The channel gates on it in this way:

* **The owner installs the lease.** `install_lease(session, token, now_ns)` accepts the token only if
  the session accepts it at `now_ns` (the same gate as G01's `discover_authority`): a foreign group or
  issuer, a stale or future epoch, or an already expired lease is refused with the session's own error,
  and a lease already held is left alone. `now_ns` is the group's monotonic timebase, the one `step`
  is given. The session judges a token in this order (G01 slice 2): group, stale epoch, future epoch,
  issuer, expiry; a token flawed in two ways is refused for the first. A replaced coordinator names the old
  issuer *and* the old epoch, so it is refused as `STALE_AUTHORITY`, not as a foreign issuer. A single-flaw
  vector cannot tell the orders apart, so `N02-S032` carries seven two-flaw tokens, and the Python
  reference judges them in the same order (`tests/n02/test_lease_order.py` checks every combination).
* **The channel re-checks it on every group-changing command**, against the session as it is at that
  `step`. A deposed leader (the issuer advanced the epoch; the lease is for the old one), an expired
  lease, or no lease at all is refused as `Lease(StaleAuthority | FutureAuthority | AuthorityExpired)` or
  `NoLease`, before the session is touched.
* **No lease is the default.** A new channel, and a restarted one, holds none until the owner installs
  one: it fails closed, as G01's `AuthorityNotDiscovered` does for the membership engine. The owner
  installs a lease only after it has obtained one from the group's authority.
* **These refusals are transient.** They are reported in the `step` result and counted
  (`refused_for_lease`), but not recorded in the ledger, because they say nothing about the command, only
  about the moment, and the command took no effect. A resend after the lease is installed or renewed is
  queued and judged afresh. Recording them would turn a resend after renewal into a refusal read back
  from memory.
* **The clock-uncertainty margin.** `ChannelConfig::lease_margin_ns` is G01's `u`
  (`MembershipConfig::lease.clock_uncertainty_ns`; `with_lease_terms` copies it). Both the install check
  and the gate use `AuthorityToken::check_with_margin(.., u)`, so the holder stops `u` before its lease
  ends, at exactly the instant G01's own `lease_is_live` stops it (a test sweeps the boundary and compares
  the two). With `u = 0`, the default, this is the plain expiry check. A token with no more than `u` left
  cannot be installed.
* **Renewal.** `ControlChannel::renew_lease(membership, session, win, now)` takes the lease the channel
  holds, has the engine extend it to what a voter quorum acknowledged (`GroupMembership::renew_lease`,
  which requires a quorum group, a lease still live under the margin, a renewal win by this holder for this
  epoch, and a real extension within the maximum), and installs the result. A refusal is the engine's own
  error and leaves the held lease alone. A holder whose lease has **lapsed** cannot renew
  (`AUTHORITY_EXPIRED`); it has to win a new epoch (`QuorumRound` with a takeover request, then
  `GroupMembership::assume_authority`) and the owner installs the token that returns. A node that learns of
  a newer holder (`adopt_authority`) needs no call on the channel: its old lease is a stale epoch to the
  session and the gate refuses it. `advance_epoch` is the epoch mint only in the configured-issuer mode;
  in a quorum group it refuses (`QUORUM_REQUIRED`).
* **What needs no lease.** A local stop and a local mute-on only silence. A cancel only withdraws its own
  sender's waiting work. A remote stop is gated: a deposed leader may not stop the current group either.
  A local unmute or a local volume change is gated, because it changes the group.
* **Authentication first.** The lease is consulted at `step`, long after `submit` authenticated the
  request, so a forged request never reaches it (`INV-AUTH-BEFORE-LEASE`).

*Why the token is held by the channel and not carried in each request.* An `AuthorityToken` is four
plain fields with no MAC: any authenticated peer could write one, so a token on the wire would add no
authority beyond the peer's key. What fences a stale remote leader on the wire is the key's epoch binding
(`EpochNotBound`, and a rebinding or revocation expires queued commands); what fences a stale local
leader is this gate, which keeps comparing a token the owner got from the authority with the session.
If the orchestrator wants a lease carried in requests as well, that is a wire change (a new field under
the signature) and is not done here.

## 5. Guarantees

Each is checked by named scenarios in the golden file and by named Rust tests; the mapping is
`tests/n02/cases.json`, and `tests/n02/test_reference_model.py` verifies it.

| Id | Claim |
|---|---|
| `INV-AUTH-FIRST` | A request that does not authenticate changes nothing: no queue, no ledger entry, no rate-limit allowance. |
| `INV-LOST-ACK` | When the acknowledgement of a committed command is lost, the retry is answered with the recorded outcome and the command is not applied again. |
| `INV-ONE-EFFECT` | However many times a command is delivered, it takes effect at most once. |
| `INV-DUP-RELATIVE` | A duplicated relative volume change applies exactly one delta, whether the copy arrives before or after the original is applied. |
| `INV-RETRY-STORM` | A storm of retries leaves queue length and ledger size unchanged and produces one effect. |
| `INV-ID-REUSE` | The same command number with different content is refused, while the first is waiting and after it settled. |
| `INV-WINDOW-AGE` | After the retention period an outcome is forgotten, and a retry is answered as unknown (never re-applied). |
| `INV-WINDOW-COUNT` | When the ledger is full the oldest outcome is forgotten explicitly, and newer ones are still answered. |
| `INV-NOT-FOREVER` | Exactly-once is not promised forever: beyond the window the channel reports unknown and does not guess. |
| `INV-STALE-LEADER` | A controller acting under an old epoch changes nothing once the group's epoch has moved on. |
| `INV-EPOCH-BINDING` | A key bound to one epoch is refused at the door under any other epoch. |
| `INV-NO-EPOCH-ADVANCE` | Nothing the channel applies can advance the group's epoch, so a request cannot fence out the legitimate leader. |
| `INV-EXPECTED-REVISION` | A command whose expected revision is not the current one is refused with no effect. |
| `INV-EXPIRED-AUTHORITY` | A peer revoked or rebound after its command was accepted has no effect when the command would run. |
| `INV-BOUNDED-QUEUE` | Every queue is bounded; a full lane refuses new work, and a refusal for want of room does not consume the command number. |
| `INV-REFUSAL-KEEPS-NUMBER` | A request turned away before acceptance can be sent again unchanged once the reason has passed. |
| `INV-REFUSAL-RECORDED` | A command refused after acceptance has its refusal recorded as its outcome, and a retry is told the same. |
| `INV-RATE-LIMIT` | Rate limits are per authenticated peer and per lane, and refusals state the exact wait. |
| `INV-PRIORITY-LANE` | Stop, mute and cancel travel in a separate lane that is served before ordinary work. |
| `INV-LOCAL-STOP-FIRST` | A local stop is applied in the first step after it is accepted, ahead of every queued remote command, through a full queue and a remote flood. |
| `INV-RESERVED-SLOTS` | The local user keeps priority slots a remote peer cannot take, and the lane is still bounded. |
| `INV-PRIORITY-NOT-BYPASS` | Priority never bypasses authentication: a forged stop is refused like any forged request. |
| `INV-LOCAL-EXEMPT` | The local user is not refused for epoch or expected revision; a remote controller in the same position is. |
| `INV-PENDING-EXPIRY` | An accepted command that waits longer than the pending limit expires unapplied, and that is its recorded outcome. |
| `INV-NO-UNBOUNDED-RETRY` | No retry or wait is unbounded: queue time, ledger memory and rate are all limited. |
| `INV-CANCEL` | Cancel withdraws a waiting ordinary command of the same peer before it commits, and changes nothing after, for another peer, or against a stop. |
| `INV-RELATIVE-CLAMP` | Relative volume is resolved against the live value in the channel and clamped to 0..=100. |
| `INV-STEP-BUDGET` | A step applies at most its budget of commands; the rest wait for the next step. |
| `INV-LEASE-REQUIRED` | A command that changes the group is applied only under a live group lease (a G01 `AuthorityToken` the session still accepts at the time of the step); with none, a superseded one or an expired one it is refused before the session is touched. |
| `INV-LEASE-MARGIN` | With a clock-uncertainty margin u the held lease stops being usable u before its expiry, exactly where G01's own liveness rule stops it; a lease with no more than u left cannot be installed. |
| `INV-ACK-LOG-ONE` | A permitted acknowledgement writes one record, joined to its command's record by correlation id, and every rejection writes one typed record; nothing a peer supplied is echoed. |
| `INV-ACK-LOG-NEUTRAL` | No state of the log (absent, roomy, small, tiny, byte-starved, never drained) changes an acknowledgement's or a command's result, the session or the counters; every record is held or counted as dropped. |
| `INV-ACK-LOG-BOUNDED` | Acknowledgement records are held to half the log's records and bytes, can never push a command record out (a flood larger than their half drops exactly the excess, counted in `ack_dropped`, and loses no command record), and are evicted first when a critical record needs room. A log that gave them the whole budget fails the flood judge. |
| `INV-ACK-ONCE` | An on-time acknowledgement completes its ledger entry exactly once; a second is a duplicate. Acknowledging does not change how long an outcome is remembered. |
| `INV-ACK-INERT` | An acknowledgement writes nothing: it never applies, re-applies or resurrects a command, and never extends the lease, the epoch binding or the revision floor, however late it is, before or after an epoch or lease change, and for a command that was withdrawn or superseded. |
| `INV-ACK-NEVER-GATES` | Nothing waits for an acknowledgement: with any number pending, the local stop is the first settlement of the first `step` after it is accepted. |
| `INV-ACK-TYPED` | Every acknowledgement is counted in exactly one typed bucket (on time, late, superseded, duplicate, not settled, unknown, out of window, mismatch, unauthenticated), on both sides of the budget and of the retention. |
| `INV-LEASE-RENEWAL` | A holder whose lease is about to expire renews it through a quorum win and keeps applying commands with no gap; a lapsed holder's renewal is refused and its commands stay refused until it wins a new epoch; a newer holder's adoption fences the old lease; a renewal needs a held lease and a quorum group and cannot be replayed to stretch the lease. |
| `INV-DEPOSED-LEADER` | After the issuer advances the epoch, a late command under the old lease is refused, and the same command is applied once the new epoch's lease is installed. |
| `INV-LEASE-EXPIRY` | A lease is live up to the instant before its expiry and refused from that instant; renewal plus resubmit is applied. |
| `INV-LEASE-INSTALL-CHECKED` | A lease the session does not accept (foreign issuer or group, stale, future, already expired) cannot be installed, and the lease already held keeps working. |
| `INV-LEASE-REFUSAL-TRANSIENT` | A refusal for want of a live lease is reported but not recorded, so the same request sent again after the lease is installed or renewed is judged afresh. |
| `INV-SILENCE-NEEDS-NO-LEASE` | A local stop and a local mute-on only silence and need no lease; a cancel only withdraws its sender's waiting work and needs none. |
| `INV-AUTH-BEFORE-LEASE` | A forged request fails authentication before the lease is consulted. |
| `INV-RESTART-FENCE` | After a channel restart against a session that kept running, a copy composed before the restart is refused whatever its kind, nothing is reverted, and a command composed after the restart is applied. |
| `INV-NUMBER-ABOVE-HIGH-WATER` | A restarted channel numbers its session commands above everything its predecessor used, so the first commands after a restart are not session faults. |
| `INV-ABSOLUTE-REPEATABLE` | Absolute volume stays naturally repeatable: a command composed against an older revision than the current one still applies within an incarnation, so pipelined updates and interleaved controllers are not stale. |
| `INV-REVISION-REQUIRED` | A remote controller's volume or mute command must name the revision it last read, or it is turned away at the door without consuming its number; stop, cancel and the local user need none. |
| `INV-FUTURE-REVISION` | A command naming a revision the session has not reached is refused with no effect. |
| `INV-SESSION-FAULT-INTERNAL` | A session refusal that is not about the command's content (a repeated or out-of-window number, a stale epoch) is an internal fault: counted, kept for the operator, recorded without detail and never shown to the sender. An unknown member is still the sender's. |
| `INV-LOG-ONE-PER-OUTCOME` | Every command that reaches a terminal outcome in a step is written to the log exactly once, with its correlation id, the committed revision, the epoch, the queue depth and the time it waited. |
| `INV-LOG-SHARED-SCHEMA` | A record is one line of JSON in the shared `ffw.log.v1` shape, byte-identical to the shared event after a round trip, with keyed pseudonyms identical to the shared sink's. |
| `INV-LOG-NO-ECHO` | Nothing a peer supplied reaches the log: a refusal that carries a key-shaped peer id or member id never echoes it, nor the peer's key or proof; identifiers appear only as keyed pseudonyms. |
| `INV-LOG-BOUNDED` | The log holds at most its record and byte bounds, no line is longer than the line bound, nothing blocks, and every record handed to it ends stored or counted as dropped. |
| `INV-LOG-CRITICAL-EVIDENCE` | An internal-fault record evicts the oldest ordinary record to make room, and if even that cannot make room it is counted as lost evidence and the log reports itself incomplete. |
| `INV-LOG-CAUSE` | A refusal's underlying reason is logged as a vocabulary word (a session error's variant, a lease error's code), never as the error's text. |
| `INV-LOG-NO-EFFECT` | Turning the log on changes nothing the channel does: the same settlements, counters and session state. |
| `INV-LOG-MONOTONIC` | Record timestamps never go backwards, whatever clock the owner passes. |

## 6. Cancel

A `Cancel{target_seq}` names an earlier command of the **same peer** (the target is looked up under
the cancelling request's own peer, so one peer cannot withdraw another's). In order:

* the target is waiting in the ordinary lane → it is removed and recorded `Withdrawn`; the cancel is
  `CancelApplied{target_seq}`;
* the target is waiting in the priority lane (a stop or a mute) → `Refused(NotCancellable)`;
* the target has an outcome on record → `Refused(TooLateToCancel)`;
* the target is at or below the floor and forgotten → `Refused(TargetOutOfWindow{floor})`;
* otherwise → `Refused(NothingToCancel)`.

A cancel cannot target itself (refused when the body is built). A cancel skips the epoch and revision
checks: it can only remove its own sender's waiting work, which is harmless under any epoch.

## 7. The outcome ledger and what "unknown" means

`OutcomeLedger` remembers the terminal outcome and the request body for each `(peer, seq)`, bounded by
**count** (`ledger_capacity`, oldest evicted first) and by **age** (`retention`, measured on a clock
that never runs backwards). When an entry is evicted the peer's **floor** rises to at least its `seq`.

* A retry found in the ledger is answered from it.
* A number at or below the floor and not in the ledger is `OutOfWindow`: the channel no longer knows
  whether it was applied, and **will not apply it**. The sender must read the group state and decide.
* A number above the floor and not in the ledger has never been recorded. This holds because an
  applied command stays in the ledger until eviction, and eviction raises the floor. The floor is
  conservative in one direction: it can also cover numbers never seen that sit below an evicted one,
  and those too are reported unknown rather than guessed at.

**This is not exactly-once forever, and the contract does not claim it.** It is: *at most one
application per command, an answer for as long as the outcome is remembered, an explicit "unknown"
afterwards*. The ledger is volatile — it does not survive a restart, and a restarted channel starts
with empty memory and no floors. Whether a command sent before the restart was applied is then
unknowable from the channel's own memory; the session state is the record.

**A copy that outlives a restart is refused, not re-applied.** What stops it is not the ledger but the
session's monotonic `state_revision`, which the restarted channel reads at its first `step` as its
revision floor (§4). A relative copy fails the exact-revision check. A volume or mute copy was
composed against a revision older than the floor and is `StaleRevision`. A new incarnation therefore
refuses everything composed before it began, and applies what a client composed after reading the
state again. A stop is the exception by design: a stale stop only silences.

**The boundary of that fence.** It holds while the session's revision is monotonic across the
channel's restart, that is, while the session kept running. If the whole process restarts and the
session is rebuilt from persisted intent ("a restored desired group is not a restored live session"),
the fence is only as good as the rebuilt session's revision: a revision that restarts below what
clients last saw makes their commands `RevisionMismatch` (a revision the session has not reached), but
one that climbs back past a stale command's revision would admit it. Restoring the session with a
revision, or an epoch, that continues from a persisted high-water mark is G01/U01's, and is listed as
uncovered. Durable idempotency across a full restart is likewise not provided here.

### Acknowledgements

A command is *settled* when its outcome is recorded; it is *acknowledged* when its sender says it saw that
outcome (`AckRequest`, signed over `FFCA | version | peer | seq | epoch`, a different magic from a request
so neither proof verifies as the other). `ControlChannel::acknowledge` is checked in the same order as
everything else: authentication first, then what the ledger knows.

**An acknowledgement is nearly inert on purpose.** It sets one flag on one ledger entry and bumps one
counter. It takes the session by shared reference, so it cannot write it; it touches no queue; it does not
read or change the lease, the epoch binding or the revision floor; and nothing in `step` looks at it, so
nothing, the local stop included, waits for one. It does not shorten or lengthen retention: an acknowledged
outcome is remembered as long as an unacknowledged one, and a retry of it is still answered from the ledger.

Typed outcomes (`AckOutcome`), each counted in exactly one bucket (`acks_accounted() == acks_received`):

| Outcome | When | Effect |
|---|---|---|
| `OnTime` | first acknowledgement, age ≤ `ack_budget` | entry completed |
| `Late` | first acknowledgement, age > `ack_budget`, outcome still remembered | entry completed |
| `Superseded` | first acknowledgement of a command issued under an epoch older than the session's | entry completed; nothing else |
| `Duplicate` | already acknowledged | none |
| `NotSettled` | the command is still waiting in a queue | none |
| `Unknown` | never recorded | none |
| `OutOfWindow` | forgotten (aged out at exactly the retention, or evicted) | none |
| `Mismatch` | names an epoch other than the recorded command's | none |
| `Unauthenticated` | did not authenticate | none |

`Superseded` takes precedence over `Late` over `OnTime`. The budget boundary is exact (age equal to the
budget is on time; one nanosecond over is late), and so is retention's (one nanosecond short of it is
`Late`, at it is `OutOfWindow`).

What is deliberately **not** done: acknowledgements do not release ledger entries early (so the ledger can
still fill with outcomes whose senders have already moved on), they have no rate limit of their own (a flood
of valid ones is counted and nothing more), their records in the JSONL log are held to half of it (§11), they are not carried by
the `fsonos` adapter, and there is no golden scenario or Python model for them (the Rust tests judge them).

## 8. The session boundary and an open dependency

`UnifiedGroupSession::apply_command` has its own per-epoch idempotency (`command_seq`, window
`COMMAND_DEDUP_WINDOW` = 1024, floor eviction) but no authentication, no expected-revision check, no
relative volume and no cached outcomes. The channel therefore sits **above** it:

* client numbers never reach the session (two peers' numbers would collide in its single space); the
  channel mints its own strictly increasing numbers, each the larger of the previous one plus one and
  `session_seq_base` plus the session's `state_revision`;
* the channel always passes `session.current_epoch`, so it can never advance the epoch.

**Open dependency (raise with the session owner).** The session's number space is shared by every
caller in an epoch, and it keeps only the newest 1024. After roughly a thousand channel commits in one
epoch its floor has risen past the small numbers a membership caller would use, and those are refused
as below the window. Until the session offers a sequence space for the channel of its own (or a
separate dedup namespace per caller), a membership change after that many channel commits needs a new
epoch. The test `the_channels_own_command_numbers_never_collide_with_the_session_even_past_its_window`
shows the channel's own commands are unaffected; it does not, and cannot, cover the membership case.

**Status of that dependency.** The session owner confirmed (mail 3659) that driving `apply_command` with a
strictly increasing channel-minted number at `session.current_epoch` is the intended use, and that
`DuplicateCommand` or `CommandBelowWindow` from the session can only mean a channel counter fault, never
a client-facing result. G01 is additive (mail 3686): a separate `membership` module with its own error
type, `GroupMembership::advance_epoch` (issuer-token gated) and the cutover methods. An epoch advance
or a membership activation resets the session's record, bumps `state_revision` once, and consumes no
`command_seq`; a client whose expected revision predates it is refused by this channel's revision
check, which is the intended result. The orchestrator accepted option (c) as a known limit for this
slice (mail 3678). The channel maps those session errors to `InternalFault` (§4).

**A restarted channel starts above everything it used before.** Because each number is at least
`session_seq_base + state_revision` and the revision only grows, a new incarnation counting from the same
base lands above every number its predecessor took, with no persistence and no change to the session
(`INV-NUMBER-ABOVE-HIGH-WATER`). The counter still advances on every attempt, so a number another caller
happened to take is one internal fault and the next command is minted a fresh number. Other callers
of the session in the same epoch keep to numbers below `session_seq_base`.

Membership commands (admit, remove, clock-lock) are **not** part of this channel's first slice.

## 9. Authentication

The channel asks a `PeerAuthority` two things: `authenticate(peer, message, proof)` and, at apply
time, `is_current(snapshot)`. `PeerDirectory<S: SecretStore>` implements both:

* **Proof.** `HMAC-SHA256(key, "FFCP-v1-auth" || signing_bytes)`, the full 32-byte tag, compared in
  constant time; a proof of any other length is refused. The label ties a tag to this protocol and
  version. HMAC comes from the workspace `hmac` and `sha2` crates, as in `franken-stream`; this crate
  does not depend on `franken-stream`. The primitive is pinned to RFC 4231 cases 1 and 2. The golden
  file pins five proofs (`auth_vectors`) computed by Python's standard `hmac` over the five signing
  vectors, and thirteen tampers (`tamper_vectors`), each changing exactly one signed field of its base
  request: peer, `seq`, `epoch`, the expected revision's value, its removal, and a revision of zero
  against none, member, delta, command kind (same payload byte, different tag byte), stop `now_ns` and
  tail, cancel target and mute flag. The Rust replay checks that its proof equals the Python tag, that the
  directory accepts the Python tag itself, and that every tampered request is refused under the original
  tag. The removal of a revision is tampered on an absolute command, because the body constructor
  refuses a relative command without one, so such a tamper could never reach the tag check.
* **Keys.** Each peer's key lives in the `SecretStore` (P01) under `SecretKind::ControlPeerKey` and
  nowhere else; the directory holds no key bytes. A key must be at least 16 bytes. That is a length
  policy: entropy cannot be checked here.
* **Admission, revocation, binding.** An admission carries a `version` and an optional epoch the key
  is bound to. Revocation wipes the key and leaves a tombstone at that version; only a strictly higher
  version re-admits. A rebinding or re-admission yields a new version, and any earlier snapshot is no
  longer current. The number of identities ever admitted is bounded (`MAX_PEERS` = 16), so the floor
  table is bounded too.

**Not decided here.** How a peer obtains its key (pairing), where keys persist, and key rotation
belong to P03, U01 and N01. The only store this crate has is a volatile in-memory one compiled for
tests; `EphemeralPeers` and `test_key` (fixed, non-secret fixture keys) exist only under `cfg(test)`.
Nothing here shows that a key is held in hardware or encrypted at rest.

**Authentication is not freshness.** A valid request that an attacker held back and delivers later
is still a valid request. What limits it is the epoch it names (a key bound to an epoch is refused
under another), the revision it expects (mandatory for relative commands), and the ledger (a
`(peer, seq)` with an outcome on record is never applied again). An absolute volume or a mute with no
expected revision that was never seen by the channel can be applied late. The contract does not claim
otherwise; a timestamp or session nonce would be a protocol change.

**Replies are not covered.** `Settlement`/`SubmitResult` are values handed to the caller. This
contract defines no response wire format and no authentication of replies; a client that trusts an
unauthenticated "committed" has no protection from this module.

## 10. Bounds

Every size and time is a configuration field, and a zero is refused at construction.

| Field | `provisional()` | Meaning |
|---|---|---|
| `ordinary_capacity` | 16 | ordinary commands waiting |
| `priority_shared_capacity` | 4 | priority slots any peer may use |
| `priority_local_reserved` | 2 | priority slots only the local user may use |
| `ledger_capacity` | 64 | outcomes remembered |
| `retention` | 30 s | how long an outcome is remembered |
| `pending_ttl` | 5 s | how long an accepted command may wait |
| `max_per_step` | 4 | commands applied per `step` |
| `ack_budget` | 2 s | how long after its outcome is recorded an acknowledgement is still on time (later: `Late`; it has no other effect) |
| `lease_margin_ns` | 0 | G01's clock uncertainty u: the lease stops being usable u before its expiry (§4) |
| `session_seq_base` | 2^32 | lowest session command number; each number is at least this plus the revision (§8) |
| `ordinary_rate` | burst 8, 1 per 100 ms | per peer |
| `priority_rate` | burst 4, 1 per 250 ms | per peer |

**These numbers are provisional and unmeasured.** The bead names none of them; they have not been
tuned against any board, link or user behaviour. They bound the memory and the work, which is what the
contract needs; they are not a latency claim.

Priority is not fairness. A remote peer may fill the shared priority slots (4) and a stream of
authenticated priority commands is served before ordinary work. That is bounded by the per-peer
priority rate limit and the pending TTL, and the local user's priority commands are served ahead of
every remote priority command; it is not eliminated.

## 11. Diagnostics

`ChannelStats` counts every `submit` into exactly one bucket, so `accounted() == received` always
(rejected: unauthenticated, epoch-not-bound, rate-limited, queue-full, id-reuse; answered: from ledger,
already queued, out of window; accepted). `committed`, `withdrawn`, `cancels_applied`, `refused`,
`expired_pending` count what `step` did, and `ledger_record_failures` counts an outcome that could not
be recorded (zero in correct operation). `Diagnostics` pairs these with queue lengths, ledger size,
tracked peers and the session's **committed revision**, so "received" is never shown as "took effect".

### The JSONL log

`ControlChannel::enable_log(ChannelLog)` turns on one record per command that reaches a terminal outcome in
a `step`: committed, refused (with the reason), withdrawn, expired, or a cancel that was applied. A record
is one line of JSON in the shared `ffw.log.v1` shape (`schema_version`, `timestamp_mono_ns`, `run_id`,
`case_id`, `correlation_id`, `member_id`, `group_id`, `source_epoch`, `state_revision`, `event_kind`,
`message`, `queue_depth`, `latency_us`, and `cause` where there is one), so a reader built for the other
diagnostics reads these; a test parses every line into the shared `DiagnosticEvent` and requires the
re-serialised bytes to equal the line.

* **Correlation.** `correlation_id` is `<peer pseudonym>#<seq>`. `source_epoch` is the group's epoch,
  `state_revision` the session's committed revision when the command settled (the revision it produced,
  for a commit), `queue_depth` the commands still waiting, `latency_us` the time between acceptance and
  settlement.
* **Redaction by construction.** Nothing a peer supplied is copied into a record. Peer, member and group
  identifiers appear only as keyed one-way pseudonyms (`p-` and sixteen hex characters, the construction
  the shared diagnostics sink uses, so a pseudonym agrees across both). `event_kind`, `message` and `cause`
  are built from a fixed vocabulary and from numbers; a refusal's underlying reason is the *variant* of the
  session error or the *code* of the lease error, never its text, which can carry a member id. `run_id` and
  `case_id` are labels the harness chooses, validated to the label alphabet. The pseudonym key is random per
  run, is kept nowhere, and prints as `[REDACTED]`; no key, proof or secret reaches the log. A refusal
  carrying a key-shaped member id and a key-shaped peer id is tested end to end: the sender is told the
  member it named, and the log holds neither.
* **Bounded.** At most `max_records` records and `max_bytes` bytes, and no line over 1024 bytes (a longer
  one is dropped and counted, never truncated). Nothing blocks or waits. When full, an ordinary record is
  dropped and counted; an internal fault is *critical* and evicts the oldest ordinary record to make room,
  and if even that cannot make room it is counted as `critical_lost` and the log reports itself incomplete.
  `emitted == stored + dropped` always. The facts waiting for the end of a step are bounded by the queue
  bounds and are drained every step.
* **No effect on the channel.** A full or absent log changes nothing the channel does; a test runs the
  same script with and without it and compares the settlements, counters and session state.
* **Time.** Timestamps are the `now_ns` given to `step`, clamped never to go backwards.
* **Acknowledgements.** `acknowledge` writes one record per acknowledgement, whatever its outcome:
  `n02.ack.on_time`, `n02.ack.late` or `n02.ack.superseded` for one that completed its entry, and
  `n02.ack.rejected.<why>` (`duplicate`, `not_settled`, `unknown`, `out_of_window`, `mismatch`,
  `unauthenticated`) for one that did not. The `correlation_id` is the command's own, so the acknowledgement
  record joins the command's record; `latency_us` is how long after the outcome was recorded the
  acknowledgement came (zero where that is not meaningful); an unauthenticated one carries the failure word
  (`bad_proof`, `unknown_peer`, `revoked`) as its `cause`, and its claimed identifier appears only as a
  pseudonym. The outcome is decided before the log is touched and is not consulted again, so the log cannot
  change it. Because anyone can send an acknowledgement, acknowledgement records are held to **half** the
  log's records and half its bytes: past that a record is dropped and counted (`ack_dropped`, also in
  `dropped`), so a flood cannot push command records out, and when an internal fault needs room the
  acknowledgement records are evicted first.

Independent vectors: `n02_log_vectors.json`, generated by `tests/n02/gen_log_vectors.py` with `hashlib`
and `json`, pins seven pseudonyms and four complete lines (a commit, a session refusal with a member, a
refusal for want of a lease with its cause, and an expiry), and six acknowledgement lines (on time, late,
superseded, unauthenticated with its cause, forgotten, mismatched), which the Rust must reproduce byte for
byte. The Rust builds each acknowledgement line from the outcome the fact names, so the vocabulary and the
arithmetic are pinned too.

**What it is not.** It is an in-memory bounded buffer the owner drains with `ChannelLog::drain`; it writes no
file, so there is no disk bound to test. Only `step` outcomes and acknowledgements are logged: a request turned away at `submit`
(unauthenticated, rate limited, queue full, and so on) is counted in `ChannelStats` but not written as a
record. There is no sink I/O here, so "slow" is modelled as an owner who never drains, "full" as the bounds
being reached, "tiny" as a byte bound smaller than a line, and "unavailable" as no log enabled; a real
file or network sink, with its own latency, is not modelled, and the timing here is the host's, not a
LAN's or a device's. The `fault` field of the shared schema (an injected fault schedule) is never set. It does not
integrate with the shared Q00 runner.
