# Contract N02 — Reliable Bounded Control Channel (`ffw-ugf`)

**Status: implemented offline in `crates/franken-control/src/channel`, not yet compiled or run
centrally. Bead open; it is blocked on N01, U01 and P03 for closure, and nothing here closes it.**
Scope is the message-handling state machine between authenticated peers and one
`franken_session::UnifiedGroupSession`: authentication, replay and retry handling, bounded queues,
rate limits, epoch and revision fencing, cancellation, and counters. Transport (sockets, framing,
encryption of the link) is N01/N07's, user-interface wiring is U01's, and the real key hierarchy is
P03's. Nothing in this contract touches a device, a network, or a provider. Everything below is
host simulation of a state machine; it says nothing about a network, a real MAC, a board or what is
audible.

## 1. What the channel is

`ControlChannel<A: PeerAuthority>` has two calls, deliberately separate:

* `submit(now_ns, request)` — a peer's signed request arrives. The answer says whether it was
  **accepted into a queue**, answered from memory, or turned away. **Accepted is not committed.**
* `step(now_ns, &mut session)` — the owner of the session applies what has been accepted, a bounded
  number per call, and gets back one `Settlement` per command that reached a terminal outcome.

Time is passed in as nanoseconds; the channel reads no clock and opens no socket. The caller drives
`step` from its own schedule, so the latency of "accepted to applied" is the caller's period times
the queue position, not something this module hides.

## 2. Request and what the proof covers

A `ControlRequest` is a `RequestBody` plus an `AuthProof` (1..=64 bytes). The body is
`(peer, seq, epoch, expected_revision?, command)`:

| Field | Rule |
|---|---|
| `peer` | 1..=32 bytes of `a-z 0-9 . _ -`; the identity the authority knows |
| `seq` | at least 1; per peer; the idempotency key together with `peer` |
| `epoch` | the group epoch the sender believes is current |
| `expected_revision` | the session `state_revision` the sender last saw; **required** for relative commands |
| `command` | one of the seven below |

| Tag | Command | Lane | Notes |
|---|---|---|---|
| 1 | `SetMemberVolume{member, volume 0..=100}` | ordinary | |
| 2 | `SetGroupVolume{volume 0..=100}` | ordinary | |
| 3 | `AdjustMemberVolume{member, delta -100..=100}` | ordinary | relative |
| 4 | `AdjustGroupVolume{delta -100..=100}` | ordinary | relative |
| 5 | `SetMemberMute{member, muted}` | priority | |
| 6 | `StopGroupPlayback{now_ns, irrevocable_dma_tail_ns}` | priority | |
| 7 | `Cancel{target_seq}` | priority | withdraws an earlier **ordinary** command of the same peer |

The bytes the proof covers (`RequestBody::signing_bytes`), all integers big-endian:

```
"FFCP" | version=1 | len(peer) peer | seq u64 | epoch u64 |
presence u8 [revision u64 if presence=1] | tag u8 | command fields
```

with a member label as `len u8 | bytes`, a volume as one byte, a delta as one two's-complement byte,
a mute flag as one byte, and the stop and cancel fields as `u64`s. Every field is covered; the
presence byte makes "no revision" differ from "revision 0". Five worked byte strings are pinned in
`crates/franken-control/tests/vectors/n02_scenarios.json` (`signing_vectors`), derived by hand and
checked by both the Python reference and the Rust replay.

## 3. Submit order

Each stage refuses without having changed any later stage. **Nothing is mutated before stage 1
passes.**

1. **Authenticate.** `PeerAuthority::authenticate(peer, signing_bytes, proof)`. A failure
   (`UnknownPeer`, `Revoked`, `BadProof`) returns at once: no rate-limit bucket is created or spent, so
   a flood of forgeries cannot use up a real peer's allowance. Priority is not an exception.
2. **Epoch binding.** A key bound to epoch *e* is refused (`EpochNotBound`) under any other epoch. A
   peer not bound to an epoch (the local user) skips this.
3. **Rate limit**, per authenticated peer **and** per lane: a token bucket of `burst` with one more
   token per `interval`; a refusal states the exact wait.
4. **Duplicates.**
   * A request with the same `(peer, seq)` already waiting: identical → `AlreadyQueued`; different →
     `IdReuse`.
   * An outcome on record: identical request → `Settled(outcome)` (the recorded outcome, never a new
     one); different → `IdReuse`.
   * Not on record but at or below the peer's **floor** → `OutOfWindow{floor}`: unknown, and not
     applied.
5. **Bounded enqueue** into the ordinary or the priority lane; a full lane → `QueueFull`.

A request refused at stages 1–3 or 5 records nothing and consumes no command number: the same bytes
can be sent again when the reason has passed. (A stage 5 refusal has already spent a rate-limit token,
because the limit is checked first; a stage 1 refusal spends none.)

## 4. Step order

Expire anything that has waited `pending_ttl` (→ recorded `Refused(Expired)`). Then, at most
`max_per_step` times: take the next command — the local user's priority command first, otherwise the
oldest priority command, otherwise the oldest ordinary one — and:

1. **Re-check the authority** (`is_current`). A peer revoked, re-admitted or rebound since the command
   was accepted yields `Refused(AuthorityExpired)` with no effect.
2. **Cancel** is handled here (§6) and skips the checks below.
3. A **remote controller** is held to the group epoch (`StaleEpoch`, `EpochAhead` — both refused, and
   the channel never advances the epoch) and to `expected_revision` (`RevisionMismatch`). The
   **local user** is exempt from both: it acts on what is audible in front of it. It is still
   authenticated, rate limited, and deduplicated.
4. A relative command is resolved against the live value (member volume or group master) and
   clamped to 0..=100; an unknown member is `Refused(UnknownMember)`.
5. The command is handed to `UnifiedGroupSession::apply_command` at the session's current epoch with
   a channel-minted number (§8). A session refusal is `Refused(Session(error))`.

Every terminal outcome is recorded by `(peer, seq)` together with the request body it answered.

## 5. Guarantees

Each is checked by named scenarios in the golden file and by named Rust tests; the mapping is
`tests/n02/cases.json`, and `tests/n02/test_reference_model.py` verifies it.

| Id | Claim |
|---|---|
| `INV-AUTH-FIRST` | A request that does not authenticate changes nothing: no queue, no ledger entry, no rate-limit allowance. |
| `INV-LOST-ACK` | When the acknowledgement of a committed command is lost, the retry is answered with the recorded outcome and the command is not applied again. |
| `INV-ONE-EFFECT` | However many times a command is delivered, it takes effect at most once. |
| `INV-DUP-RELATIVE` | A duplicated relative volume change applies exactly one delta, whether the copy arrives before or after the original is applied. |
| `INV-RETRY-STORM` | A storm of retries leaves queue length and ledger size unchanged and produces one effect. |
| `INV-ID-REUSE` | The same command number with different content is refused, while the first is waiting and after it settled. |
| `INV-WINDOW-AGE` | After the retention period an outcome is forgotten, and a retry is answered as unknown (never re-applied). |
| `INV-WINDOW-COUNT` | When the ledger is full the oldest outcome is forgotten explicitly, and newer ones are still answered. |
| `INV-NOT-FOREVER` | Exactly-once is not promised forever: beyond the window the channel reports unknown and does not guess. |
| `INV-STALE-LEADER` | A controller acting under an old epoch changes nothing once the group's epoch has moved on. |
| `INV-EPOCH-BINDING` | A key bound to one epoch is refused at the door under any other epoch. |
| `INV-NO-EPOCH-ADVANCE` | Nothing the channel applies can advance the group's epoch, so a request cannot fence out the legitimate leader. |
| `INV-EXPECTED-REVISION` | A command whose expected revision is not the current one is refused with no effect. |
| `INV-EXPIRED-AUTHORITY` | A peer revoked or rebound after its command was accepted has no effect when the command would run. |
| `INV-BOUNDED-QUEUE` | Every queue is bounded; a full lane refuses new work, and a refusal for want of room does not consume the command number. |
| `INV-REFUSAL-KEEPS-NUMBER` | A request turned away before acceptance can be sent again unchanged once the reason has passed. |
| `INV-REFUSAL-RECORDED` | A command refused after acceptance has its refusal recorded as its outcome, and a retry is told the same. |
| `INV-RATE-LIMIT` | Rate limits are per authenticated peer and per lane, and refusals state the exact wait. |
| `INV-PRIORITY-LANE` | Stop, mute and cancel travel in a separate lane that is served before ordinary work. |
| `INV-LOCAL-STOP-FIRST` | A local stop is applied in the first step after it is accepted, ahead of every queued remote command, through a full queue and a remote flood. |
| `INV-RESERVED-SLOTS` | The local user keeps priority slots a remote peer cannot take, and the lane is still bounded. |
| `INV-PRIORITY-NOT-BYPASS` | Priority never bypasses authentication: a forged stop is refused like any forged request. |
| `INV-LOCAL-EXEMPT` | The local user is not refused for epoch or expected revision; a remote controller in the same position is. |
| `INV-PENDING-EXPIRY` | An accepted command that waits longer than the pending limit expires unapplied, and that is its recorded outcome. |
| `INV-NO-UNBOUNDED-RETRY` | No retry or wait is unbounded: queue time, ledger memory and rate are all limited. |
| `INV-CANCEL` | Cancel withdraws a waiting ordinary command of the same peer before it commits, and changes nothing after, for another peer, or against a stop. |
| `INV-RELATIVE-CLAMP` | Relative volume is resolved against the live value in the channel and clamped to 0..=100. |
| `INV-STEP-BUDGET` | A step applies at most its budget of commands; the rest wait for the next step. |

## 6. Cancel

A `Cancel{target_seq}` names an earlier command of the **same peer** (the target is looked up under
the cancelling request's own peer, so one peer cannot withdraw another's). In order:

* the target is waiting in the ordinary lane → it is removed and recorded `Withdrawn`; the cancel is
  `CancelApplied{target_seq}`;
* the target is waiting in the priority lane (a stop or a mute) → `Refused(NotCancellable)`;
* the target has an outcome on record → `Refused(TooLateToCancel)`;
* the target is at or below the floor and forgotten → `Refused(TargetOutOfWindow{floor})`;
* otherwise → `Refused(NothingToCancel)`.

A cancel cannot target itself (refused when the body is built). A cancel skips the epoch and revision
checks: it can only remove its own sender's waiting work, which is harmless under any epoch.

## 7. The outcome ledger and what "unknown" means

`OutcomeLedger` remembers the terminal outcome and the request body for each `(peer, seq)`, bounded by
**count** (`ledger_capacity`, oldest evicted first) and by **age** (`retention`, measured on a clock
that never runs backwards). When an entry is evicted the peer's **floor** rises to at least its `seq`.

* A retry found in the ledger is answered from it.
* A number at or below the floor and not in the ledger is `OutOfWindow`: the channel no longer knows
  whether it was applied, and **will not apply it**. The sender must read the group state and decide.
* A number above the floor and not in the ledger has never been recorded. This holds because an
  applied command stays in the ledger until eviction, and eviction raises the floor. The floor is
  conservative in one direction: it can also cover numbers never seen that sit below an evicted one,
  and those too are reported unknown rather than guessed at.

**This is not exactly-once forever, and the contract does not claim it.** It is: *at most one
application per command, an answer for as long as the outcome is remembered, an explicit "unknown"
afterwards*. The ledger is volatile — it does not survive a restart, and a restarted channel starts
with empty memory and no floors. Whether a command sent before the restart was applied is then
unknowable from the channel alone; the session state is the record. Durable idempotency is not
provided here.

## 8. The session boundary and an open dependency

`UnifiedGroupSession::apply_command` has its own per-epoch idempotency (`command_seq`, window
`COMMAND_DEDUP_WINDOW` = 1024, floor eviction) but no authentication, no expected-revision check, no
relative volume and no cached outcomes. The channel therefore sits **above** it:

* client numbers never reach the session (two peers' numbers would collide in its single space); the
  channel mints its own strictly increasing numbers from `session_seq_base`;
* the channel always passes `session.current_epoch`, so it can never advance the epoch.

**Open dependency (raise with the session owner).** The session's number space is shared by every
caller in an epoch, and it keeps only the newest 1024. After roughly a thousand channel commits in one
epoch its floor has risen past the small numbers a membership caller would use, and those are refused
as below the window. Until the session offers a sequence space for the channel of its own (or a
separate dedup namespace per caller), a membership change after that many channel commits needs a new
epoch. The test `the_channels_own_command_numbers_never_collide_with_the_session_even_past_its_window`
shows the channel's own commands are unaffected; it does not, and cannot, cover the membership case.

**Status of that dependency.** The session owner confirmed (mail 3659) that driving `apply_command` with a
strictly increasing channel-minted number at `session.current_epoch` is the intended use, and that
`DuplicateCommand` or `CommandBelowWindow` from the session can only mean a channel counter fault, never
a client-facing result. G01 is additive (mail 3686): a separate `membership` module with its own error
type, `GroupMembership::advance_epoch` (issuer-token gated) and the cutover methods. An epoch advance
or a membership activation resets the session's record, bumps `state_revision` once, and consumes no
`command_seq`; a client whose expected revision predates it is refused by this channel's revision
check, which is the intended result. The orchestrator accepted option (c) as a known limit for this
slice (mail 3678). The channel does not yet map those two session errors to an internal fault; that
change is pending.

Membership commands (admit, remove, clock-lock) are **not** part of this channel's first slice.

## 9. Authentication

The channel asks a `PeerAuthority` two things: `authenticate(peer, message, proof)` and, at apply
time, `is_current(snapshot)`. `PeerDirectory<S: SecretStore>` implements both:

* **Proof.** `HMAC-SHA256(key, "FFCP-v1-auth" || signing_bytes)`, the full 32-byte tag, compared in
  constant time; a proof of any other length is refused. The label ties a tag to this protocol and
  version. HMAC comes from the workspace `hmac` and `sha2` crates, as in `franken-stream`; this crate
  does not depend on `franken-stream`. The primitive is pinned to RFC 4231 cases 1 and 2, and a
  proof is pinned to a value computed by Python's standard `hmac`.
* **Keys.** Each peer's key lives in the `SecretStore` (P01) under `SecretKind::ControlPeerKey` and
  nowhere else; the directory holds no key bytes. A key must be at least 16 bytes. That is a length
  policy: entropy cannot be checked here.
* **Admission, revocation, binding.** An admission carries a `version` and an optional epoch the key
  is bound to. Revocation wipes the key and leaves a tombstone at that version; only a strictly higher
  version re-admits. A rebinding or re-admission yields a new version, and any earlier snapshot is no
  longer current. The number of identities ever admitted is bounded (`MAX_PEERS` = 16), so the floor
  table is bounded too.

**Not decided here.** How a peer obtains its key (pairing), where keys persist, and key rotation
belong to P03, U01 and N01. The only store this crate has is a volatile in-memory one compiled for
tests; `EphemeralPeers` and `test_key` (fixed, non-secret fixture keys) exist only under `cfg(test)`.
Nothing here shows that a key is held in hardware or encrypted at rest.

**Authentication is not freshness.** A valid request that an attacker held back and delivers later
is still a valid request. What limits it is the epoch it names (a key bound to an epoch is refused
under another), the revision it expects (mandatory for relative commands), and the ledger (a
`(peer, seq)` with an outcome on record is never applied again). An absolute volume or a mute with no
expected revision that was never seen by the channel can be applied late. The contract does not claim
otherwise; a timestamp or session nonce would be a protocol change.

**Replies are not covered.** `Settlement`/`SubmitResult` are values handed to the caller. This
contract defines no response wire format and no authentication of replies; a client that trusts an
unauthenticated "committed" has no protection from this module.

## 10. Bounds

Every size and time is a configuration field, and a zero is refused at construction.

| Field | `provisional()` | Meaning |
|---|---|---|
| `ordinary_capacity` | 16 | ordinary commands waiting |
| `priority_shared_capacity` | 4 | priority slots any peer may use |
| `priority_local_reserved` | 2 | priority slots only the local user may use |
| `ledger_capacity` | 64 | outcomes remembered |
| `retention` | 30 s | how long an outcome is remembered |
| `pending_ttl` | 5 s | how long an accepted command may wait |
| `max_per_step` | 4 | commands applied per `step` |
| `ordinary_rate` | burst 8, 1 per 100 ms | per peer |
| `priority_rate` | burst 4, 1 per 250 ms | per peer |

**These numbers are provisional and unmeasured.** The bead names none of them; they have not been
tuned against any board, link or user behaviour. They bound the memory and the work, which is what the
contract needs; they are not a latency claim.

Priority is not fairness. A remote peer may fill the shared priority slots (4) and a stream of
authenticated priority commands is served before ordinary work. That is bounded by the per-peer
priority rate limit and the pending TTL, and the local user's priority commands are served ahead of
every remote priority command; it is not eliminated.

## 11. Diagnostics

`ChannelStats` counts every `submit` into exactly one bucket, so `accounted() == received` always
(rejected: unauthenticated, epoch-not-bound, rate-limited, queue-full, id-reuse; answered: from ledger,
already queued, out of window; accepted). `committed`, `withdrawn`, `cancels_applied`, `refused`,
`expired_pending` count what `step` did, and `ledger_record_failures` counts an outcome that could not
be recorded (zero in correct operation). `Diagnostics` pairs these with queue lengths, ledger size,
tracked peers and the session's **committed revision**, so "received" is never shown as "took effect".
