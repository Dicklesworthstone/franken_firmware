# E05 contract: boot-hook and rollback semantics, qualified offline

Bead `ffw-xcz`. Offline model and tests only: nothing here touches a device, a network or any file but
the profile you name. Outputs: `scripts/e05/boot_model.py` (simulator), `scripts/e05/trace_check.py`
(independent checker), `tests/e05/` (profiles, hand-written cases, three test modules),
`scripts/e2e/e05` with `scripts/test/e05.suite.json` (shared Q00 runner).

## 1. What this is, and what it refuses to do

The model answers one question per image: given what is *known* about its boot chain, what happens to
audio ownership when the hook is missing, unreadable, hangs or fails, the launcher binary is missing or
dies, power is lost mid-write, or the unit restarts repeatedly.

* Facts, not guesses. An image profile is eleven named facts (section 2). Each is `observed` (a boolean
  value and a source) or `unknown` (a named external blocker). A decision that consults an unknown fact
  makes the whole run **UNQUALIFIED** and names the blockers. Nothing reads an unknown fact as fine.
* Predicates are separate. *present*, *readable*, *executed*, *exited_ok* and *service_started* are five
  events. The vocabulary has no *writable* or *installed* claim, so hook presence can never stand for
  installation access, successful startup or zero risk.
* It models how the boot chain **consumes** a hook and what a launcher does when something goes wrong.
  It contains no write primitive, update-feed detail or access route; the committed fixtures state
  semantics only. Facts for the 57.23 line come from the sibling `frankensonos` research as input
  statements, labelled as such in each fact's `source`; none was re-measured here.
* Unknowns stay unknown. No evidence found in either repository describes stop-marker semantics, and
  nothing describes the second-generation (86.10) boot chain. Both are carried as unknowns with blockers
  (section 6), not invented.

## 2. Image profile and the eleven facts

`tests/e05/profiles/<image>.json`, schema `ffw.e05.profile.v1`: `schema`, `image`, `kind`
(`synthetic` or `extracted`), `facts`. An observed fact is `{status, value, source}`; an unknown fact is
`{status, blocker}` with `blocker` of the form `EXT-E05-NAME`. Anything else is refused (exit 2).

| Fact | Meaning when its value is true | 57.23 | If unknown or false |
|---|---|---|---|
| `hook_gate_existence_only` | the boot script skips the hook exactly when the file is absent | observed true | false: an absent hook is run as a missing file, i.e. a hook failure |
| `hook_interpreted` | the hook is run through an interpreter, so no exec bit is needed | observed true | false: a hook without its exec bit fails |
| `hook_runs_synchronously` | boot waits for the hook to return | observed true | false: a hung hook does not stall boot |
| `hook_failure_nonfatal` | a failing hook does not abort boot | **unknown**, `EXT-E05-RCS` | false: a failing hook stalls boot |
| `jffs_noexec` | a binary on the writable partition is not runnable in place | observed true | false: it runs |
| `stock_stop_effective` | a stopped stock daemon stays stopped (no respawn; this is where stop-marker semantics would matter) | **unknown**, `EXT-E05-STOP` | false: stock respawns and the launcher yields |
| `watchdog_covers_boot_stall` | a stalled boot is reset by a watchdog | **unknown**, `EXT-E05-WDOG` | false: a stalled boot has no recovery path |
| `watchdog_restarts_daemon` | a stopped or killed stock daemon is restarted by a watchdog | observed true | false: rollback after stopping stock has no recovery path |
| `fs_rename_atomic` | rename over an existing file is atomic across power loss | **unknown**, `EXT-E05-FS` | false: even temp-then-rename can leave a half hook |
| `hook_survives_update` | an update keeps the hook | observed true | false: an update returns the unit to stock |
| `update_interrupted_preserves_hook` | an interrupted update keeps the hook | **unknown**, `EXT-E05-UPDATE` | false: an interrupted update returns the unit to stock |

`86.10` (second generation): all eleven facts unknown, blocker `EXT-E05-S2`.
`synthetic-benign`: all eleven observed true, kind `synthetic`; it exercises the rules and is not a device fact.

## 3. Transition rules (one boot)

Steps, in order: `jffs_mount`, `hook_gate`, `hook_read`, `hook_run`, `preflight`, `stock_stop`,
`custom_start`, `custom_ready`, `owner_commit`. A boot starts with stock holding the device and muted.
`power_loss` is transient (fires once at its step, then the unit reboots); every other fault is a
persistent condition true on every boot. Facts a step consults are listed; consulting an unknown one ends
the run UNQUALIFIED.

| Step | Fault cells | Consults | Effect |
|---|---|---|---|
| `jffs_mount` | `power_loss` | none | reboot |
| `hook_gate` | `hook_missing`, `power_loss` | `hook_gate_existence_only` | absent hook: STOCK_OK (`hook_absent`) |
| `hook_read` | `hook_unreadable`, `hook_mode_no_exec`, `power_loss` | unreadable: `hook_failure_nonfatal`; no exec bit: `hook_interpreted` (then `hook_failure_nonfatal` if false) | nonfatal failure: STOCK_OK; fatal: boot stalls |
| `hook_run` | `hook_hangs`, `hook_exits_nonzero`, `power_loss` | hang: `hook_runs_synchronously`, then `watchdog_covers_boot_stall`; nonzero: `hook_failure_nonfatal` | a partial hook is a FAILED (`partial_hook_executed`); at the attempt cap STOCK_OK (`attempt_cap`); otherwise the attempt counter increments |
| `preflight` | `binary_missing`, `binary_not_runnable`, `power_loss` | with the binary on the writable partition: `jffs_noexec` | failure: rollback before stock is touched, STOCK_OK |
| `stock_stop` | `stock_stop_fails`, `power_loss` | success path: `stock_stop_effective`; missing acknowledgement: `watchdog_restarts_daemon` | no ack: rollback; ineffective stop: STOCK_OK (`stock_respawn_detected`) |
| `custom_start` | `binary_start_fails`, `power_loss` | rollback needs `watchdog_restarts_daemon` | failure: rollback |
| `custom_ready` | `binary_exits_nonzero`, `binary_hangs`, `power_loss` | rollback needs `watchdog_restarts_daemon` | failure: rollback (`binary_exit`, `ready_timeout`) |
| `owner_commit` | `binary_crashes_after_ready`, `power_loss` | rollback needs `watchdog_restarts_daemon` | crash loop: restart with delays 1, 2, 4, ... (never audible), rollback at the cap (`restart_cap`); clean: unmute after stable, reset the counter, CUSTOM_OK |

*Stall.* A boot that cannot proceed is reset only if `watchdog_covers_boot_stall`; otherwise FAILED
(`no_recovery_path`). Repeated stalls reboot until the attempt cap, or until `max_boots` (8), which is
FAILED (`restart_loop_unbounded`).
*Rollback.* If stock was never stopped it is simply STOCK_OK. If it was, rollback needs
`watchdog_restarts_daemon` and the policy's `restore_stock`; without them FAILED (`no_recovery_path`),
muted.
*Provisioning* (the write of the hook, cut by power loss): atomic discipline sub-steps `write_temp`,
`fsync_temp`, `rename`, `fsync_dir`; in-place discipline `truncate`, `write`, `fsync`. A cut before
`rename` leaves the prior hook; at `rename` or `fsync_dir` it leaves either old or new content (the model
resolves the either-or deterministically; both are whole files) and consults `fs_rename_atomic`. In place,
`truncate` and `write` leave a **partial** hook. *Update:* `none` consults `hook_survives_update`;
`power_loss` consults `update_interrupted_preserves_hook`.
*Verdicts:* STOCK_OK, CUSTOM_OK, FAILED(reason), UNQUALIFIED(blockers). UNQUALIFIED is never a pass.

Launcher policy under test (`Policy`, defaults are the safe baseline): `atomic_write`, `preflight`,
`stop_ack_required`, `unmute` (`after_stable`), `attempt_cap` (3), `backoff`, `restore_stock`,
`log_reasons`, `claim_from_presence`, `strict_unknown`, `binary_location` (`exec_fs`). Every non-default
value is a planted defect, used as a negative control.

## 4. Invariants and the independent checker

`trace_check.py` judges a trace and does not import the model. It reads events (`boot`, `step`, `event`,
`owners`, `audible`, `reason`, `claims`, `delay`), the verdict and the profile's fact statuses.

| Invariant | Rule (violation kinds) |
|---|---|
| INV-1 one audio owner | never two owners, never audible with no owner, never custom audible before ready, terminal owner matches the verdict (`two_owners`, `audible_unowned`, `audible_before_ready`, `bad_terminal_owner`) |
| INV-2 recovery path | absence of one is a failed case (`no_recovery_path`) |
| INV-3 bounded restarts | at most 5 restarts per boot and 6 boots; delays at least 1 and non-decreasing; custom audible at most once per boot (`unbounded_restarts`, `no_backoff`, `repeated_audible_activation`) |
| INV-4 interrupted write | a half-written hook is never executed (`partial_hook_executed`) |
| INV-5 exact reasons | every path-changing event, every rollback (also as `rollback_reason`) and the verdict carry a reason (`missing_reason`) |
| INV-6 unknown is not ok | an ok verdict may depend only on observed facts (`unknown_resolved_ok`) |
| PRED predicates | each reported claim has its own earlier event in the same boot (`unsupported_claim`) |
| ORDER | steps never go backwards within a boot (`step_order`) |

**Restart and cancellation.** Restart is modelled: `power_loss` at every step, repeated boots under a
persistent fault, and the crash loop. Cancelling a hook write is the provisioning cut (section 3).
Process-level cancellation of the CLI does not apply: it is a one-shot pure function that writes only
standard output (`E05-CLI-NO-WRITES`). The render path, nonblocking sink, group ids and queue counters
named in the bead's logging paragraph do not exist in an offline boot model; they belong to the beads
that build them. Receipts are the shared runner's (`ffw.receipt-stream/1`); this module keeps no schema
of its own.

## 6. Result on the real evidence, and what is not known

57.23, 34 cells: **7 definite** (5 STOCK_OK, 2 FAILED: the planted in-place writes) and **27
UNQUALIFIED**, blocked by `EXT-E05-STOP` (19 cells), `EXT-E05-FS` (4), `EXT-E05-RCS` (2),
`EXT-E05-WDOG` (1), `EXT-E05-UPDATE` (1). 86.10: 34 of 34 UNQUALIFIED by `EXT-E05-S2`.

What 57.23 qualifies today: a missing hook boots stock; a missing or non-runnable launcher binary is
caught by preflight before stock is touched; a launcher binary left on the writable partition is not
runnable in place (`jffs_noexec` observed), so a launcher design cannot rely on running from there; a
missing stop acknowledgement rolls back to stock; an in-place hook rewrite is unsafe.

What it cannot qualify, and the evidence that would: each is supplied as an external receipt from the
human-led lane; this repository runs none of it.

| Blocker | Missing evidence |
|---|---|
| `EXT-E05-STOP` | whether a stopped stock daemon stays stopped, including any stop-marker or supervisor-respawn semantics. **No stop-marker semantics were found in either repository.** Until known, no cell that completes the handoff to the custom owner can be qualified. |
| `EXT-E05-RCS` | the complete early-boot script text for the image (does a failing hook abort boot?) |
| `EXT-E05-WDOG` | what the watchdog covers: only the stock daemon, or also a stalled boot, and its timing |
| `EXT-E05-FS` | rename atomicity and fsync durability on the writable partition for the image's kernel |
| `EXT-E05-UPDATE` | what an interrupted update leaves of the hook |
| `EXT-E05-S2` | any boot-chain evidence for the second-generation image line |

**Abstractions.** One hook and one launcher; time is abstract (the attempt counter is persisted
atomically; a hang is a boolean, not a duration); "audible" is a state bit, not an output measurement;
electrical and amplifier behaviour are not modelled. The synthetic profile shows the rules reach their
branches, not that a device behaves that way. Facts taken from the sibling lane were not re-verified.
Downstream consumers (U01 state custody, U03 activation handoff) read this contract and the profiles; no
Rust consumer exists yet.
