# U01 — minimal persistent state and calibration custody (`ffw-mgb`)

A small, versioned, crash-consistent journal for the few things a slim speaker must keep across a power cut: settings,
paired-peer credentials, board calibration, a few opaque records, and monotone high-water marks. This document is the
specification; `tests/u01/reference.py` is an independent implementation written from it, and `crates/franken-journal`
is the Rust implementation. They agree byte for byte on the shared vectors.

**What this is not.** It is not encryption and not hardware-backed key custody: a credential in the journal is as secret
as the medium is. It does not defend against someone who can rewrite the medium (physical rollback resistance is a
separate task). It is not a filesystem and takes none as a dependency. It touches no device: the core runs over a small
`Storage` trait, and the only storage here is an in-memory fake that can fail at any byte and a file-backed one in a test
example. The platform backend over real flash is P02's. No upstream `frankenfs` code is adopted; the one idea reused
(append-only frames with a checksum, compaction into a second segment) is generic and written from scratch, so there is
no upstream revision to record.

## 1. The medium

`Storage` is two erase segments of `segment_bytes` each, with:

* `read(offset, out)`: sees everything issued so far, synced or not.
* `program(offset, data)`: can only clear bits (1 to 0). Programming a byte so that a clear bit would have to be set fails
  (`bits_cannot_rise`); the journal therefore never needs a read-modify-write and never writes over a dirty byte.
* `erase(segment)`: sets a whole segment to `0xFF`.
* `sync()`: everything issued before it is durable once it returns `Ok`.

Assumptions, each exercised by the fake: operations issued between two syncs reach the medium in issue order (the fake
also applies them newest first, and the design does not depend on the order); a power cut leaves the durable bytes plus
any byte-prefix of the unsynced operations, so the last operation may be torn at any byte, and an erase may be torn
(its first bytes erased, the rest as they were); a `sync` that fails may or may not have made the data durable, and the
journal treats its outcome as unknown. Not modeled: bit rot and read disturb of data already synced (§6 says what the
journal does if it meets damage), partial-bit programming of one byte, and wear leveling below the segment.

## 2. On-media format (all multi-byte fields big-endian)

**Segment header, 16 bytes:** `'F' 'J'`, `version` u8, `0` u8, `generation` u32, `first_seq` u32, `crc` u32. The checksum
is CRC-32/IEEE (`zlib.crc32`) over the first twelve bytes. A segment whose first two bytes are cleared (`00 00`) is
**retired**: its checksum no longer holds.

**Frame:** `0xA5`, `kind` u8 (1 = transaction, 2 = snapshot), `length` u16, `seq` u32, `crc` u32, then `length` payload
bytes. The checksum covers the first eight bytes and the payload.

**A valid segment** is a valid header whose version is known, then a *snapshot* frame with `seq == first_seq`, then zero or
more *transaction* frames with consecutive sequence numbers. Nothing else is a segment: a header with no valid first frame,
a first frame that is a transaction, a snapshot frame in the middle.

**Payload:** `count` u16, then that many operations:

| tag | operation | fields after the tag |
|---|---|---|
| 1 | `put` | `ns` u8, `klen` u8, key, `vlen` u16, value (blob namespaces) |
| 2 | `delete` | `ns`, `klen`, key |
| 3 | `reset` | `ns` |
| 4 | `install` | `klen`, id, `version` u64, `slen` u16, secret |
| 5 | `revoke` | `klen`, id |
| 6 | `reset_pairing` | none |
| 7 | `raise` | `klen`, key, value u64 |
| 8 | `tomb` | `klen`, id, `version` u64 (snapshot frames only) |

Namespace ids: 1 settings, 2 credentials, 3 calibration, 4 records, 5 marks. **Schema 0** (legacy) knew tags 1 to 4 only,
and its `install` had no version field (read as version 1). A schema-0 segment is read, then rewritten as schema 1 on
open (migration). A header with a version above 1 is **refused** (`unsupported_version`), never formatted over, if it is
the newest segment.

**Canonical state.** A snapshot is the state as a payload: operations in namespace order 1, 2, 3, 4, 5, keys ascending as
bytes; a live identity is an `install`, a revoked one a `tomb`. Equal states have equal canonical bytes, so the oracle
compares bytes.

**Lengths are checked before bytes are taken.** The decoder compares every announced key and value length with its bound
and the payload with the bytes that remain *before* reading or allocating; the scanner compares a frame's length with the
cap for its kind and with the room left in the segment before allocating its buffer.

## 3. Namespaces

| namespace | key ≤ | value ≤ | entries ≤ | rules |
|---|---|---|---|---|
| settings (1) | 16 | 32 | 16 | last write wins; staged in memory, flushed as one transaction, rate-limited |
| credentials (2) | 32 (peer id) | 128 (secret) | 16 identities, live **and** revoked | versioned; see below |
| calibration (3) | 32 (board profile) | 256 | 4 | its own operations; read by exact profile id, never converted |
| records (4) | 32 | 256 | 4 | opaque blobs, committed immediately (for example a voter record) |
| marks (5) | 16 | u64 | 8 | a high-water mark never goes down |

(Those are the standard limits. The vectors use a small configuration, 512-byte segments, so every boundary is reachable.)
A configuration is refused (`bad_config`) unless one segment holds its worst-case snapshot plus one maximal transaction.

**Three separate operations.** `reset_settings` clears settings (and anything staged) and nothing else. `clear_calibration`
clears calibration and nothing else. `reset_pairing` revokes every live credential and nothing else. No other call
clears calibration. Every one of them is a single transaction.

**Credentials follow N02's `PeerDirectory`:** an identity is *live at a version* or *revoked with a tombstone at the
version it had*. `install(id, version, secret)` admits a new identity, or replaces a live one at a **strictly higher**
version (`not_newer` otherwise). A revoked identity returns only at a version **strictly above its tombstone**
(`revoked` otherwise). `revoke` of a live identity leaves the tombstone; of a revoked one, `already_revoked`; of an
unknown one, `not_found`. Version 0 is not a version. **A tombstone keeps its identity slot**, so a revocation never needs
free space and a house cannot exhaust the table by revoking; the cost is that slots are not recycled, and a house past
sixteen identities needs a deliberate factory reset (reformat), which is a loud, separate act. Normal recovery cannot
resurrect a revoked identity because the tombstone is part of every snapshot and every replay applies the same rule.

**Marks:** `raise(key, value)` below the current value is `mark_regressed`; equal is a no-op and writes nothing.

**Every rejection writes nothing,** and so does every operation that would not change the state (the same value, an equal
mark): no-op transactions are not written, so a client that re-sends cannot wear the medium.

## 4. The publication state machine

A commit is `Staged → Written → Synced → Published`:

1. **Staged:** every operation is validated against a *copy* of the state (all or nothing), the payload is encoded, its
   size checked against the transaction cap.
2. **Written:** one `program` of the whole frame at the end of the log (or, when the segment is full, the compaction in §5).
3. **Synced:** `sync` returned `Ok`: the medium now holds the new state.
4. **Published:** only now is the in-memory state replaced and the caller told `Ok`.

A storage failure at step 2 or 3 **poisons the journal**: the published state is unchanged, every later call returns
`poisoned`, and `phase()` names the last step that completed. The outcome on the medium is unknown (a failed `sync` may
have persisted the frame), so the only way forward is to reopen, which returns exactly the old or exactly the new state.
A frame is *committed* when it is complete and its checksum holds; a torn frame is not, and recovery stops before it.

## 5. Compaction and retirement

When the next frame does not fit in the active segment, the new state is written as the *snapshot* first frame of the
**other** segment: erase it if it is not blank, program the header (generation + 1, `first_seq` = the next sequence
number), program the snapshot frame, sync. That sync is the publication. Until it returns, the old segment is intact and
is what recovery finds. Nothing is ever overwritten in place, and no step but a compaction's target needs an erase.

The old segment is then **retired** (its magic is programmed to `00 00`; programming needs no erase) at the start of the
next commit, or by open. Retirement is deferred housekeeping, not part of the commit, so a cut between the two leaves two
valid segments and recovery takes the higher generation and retires the other.

**Why retire at all.** Without it, damage to the current segment (not a power cut: bit rot, a bad block) would silently
fall back to an older segment, one that may predate a revocation. With it, damage to the current segment leaves *no*
valid segment, and open reports `unrecoverable`: the journal is formatted empty and the caller is told, so credentials
and calibration are lost loudly instead of a revoked identity quietly coming back. This is a deliberate choice for
credentials; a deployment that prefers rollback for calibration alone needs a separate store.

## 6. The bounded scanner and recovery

Open scans both segments. A scan reads the 16-byte header, then at most one frame header per 12 bytes of the segment, and
stops at the first frame that is not: magic `0xA5`, a known kind, a length within the cap for its kind and within the
segment, the expected sequence number, the right kind for its position (snapshot first), a matching checksum, a payload
that decodes, and operations that apply cleanly. Everything after the first bad frame is ignored. Then:

* Among segments with a valid state, the **highest generation** wins.
* A **dirty tail** (bytes after the last valid frame that are not erased) or a **schema-0** segment is rewritten into the
  other segment at once, so the next append never lands after garbage and never needs an overwrite.
* A stale valid (or unsupported) segment is retired.
* No valid segment, both blank: **blank**, format. No valid segment, medium not blank: **unrecoverable**, format and tell.
* The newest segment has an unsupported version: `unsupported_version`, nothing is written.

`Recovery` reports the source, the generation, the number of frames replayed, whether the tail was dirty, the schema it
migrated from, whether it retired a segment and whether it compacted.

## 7. Bounds on writes, wear and capacity

* **Settings are staged in memory.** Any number of changes between flushes costs no writes. `flush_settings(now)` commits
  all staged settings as **one** transaction, and no more often than `min_flush_interval_ticks` (`rate_limited` carries
  how long to wait; it writes nothing). A volume storm is therefore one frame per interval.
* **Credentials, calibration, records and marks commit immediately.** A revocation is never rate-limited. (It can still be
  refused by a spent wear budget when the segment is full: a medium at the end of its life, which the caller must surface.)
* **Wear budget:** `max_segment_gen` bounds the number of compactions (each erases one segment). When it is spent, an
  append that still fits works; one that needs a compaction fails with `wear_exhausted` and writes nothing. The generation
  is stored in the header, so the budget survives restarts.
* **Capacity:** per-namespace entry limits, the transaction cap (`txn_too_large`), and the segment check of §3.

## 8. Errors and diagnostics

Every error is a stable name (`invalid_key`, `value_too_long`, `bad_op`, `not_found`, `namespace_full`, `bad_version`,
`not_newer`, `revoked`, `already_revoked`, `mark_regressed`, `malformed`, `txn_too_large`, `rate_limited`, `poisoned`,
`wear_exhausted`, `storage`, `unsupported_version`, `bad_config`) with at most a counter (a version, a wait). **No error,
`Display` or `Debug`, carries a key or a value.** The tests assert it for the rejection paths that take a key or a value.

## 9. How this is tested, and what each result means

| check | what it shows |
|---|---|
| `reference.py` + `battery.py` | every rule above, in an independent implementation; ten properties |
| cut-point oracle (`enumerate_cuts`) | power cut at every storage-operation boundary and every byte budget of the unsynced writes, in issue order and in reverse; the recovered state is exactly the state before or after the step that was running, exactly the state after once the step has returned, and the empty journal after a torn format |
| failure injection | a write or erase that fails, a sync that fails and persists, a sync that fails and loses: the journal poisons, publishes nothing, reopens to old or new |
| 16 hostile images | torn tail, flipped bit, hostile length, replayed frame, torn compaction, two valid segments, unsupported and legacy schema, retired segment, damaged current segment |
| `mutate.py` | 28 mutants of the reference (CRC off, sync removed, tombstones dropped, a mark may fall, …); the battery fails for each |
| `make_vectors.py` → `u01_vectors.json` | the Rust crate must reproduce the reference's media bytes after each scenario, the digest of the media after **every** power cut, and the result and the repair bytes of every image |
| `scripts/e2e/u01 --binary …` | a REAL process is killed (abort inside the write or erase that crosses byte N; SIGKILL at arbitrary moments) and the file image is recovered. It needs an example binary the running host can execute: a binary built by central RCH is a Linux executable and is not brought back to a macOS orchestrator |
| `tests/u01_process.rs` in `cargo test -p franken-journal`, judged by `tests/u01/judge_log.py` | the same experiment on the central worker, by test name: after a clean run the FILE's SHA-256 equals the reference's final medium for all four scripts; a process killed at sampled bytes (abort) or by SIGKILL recovers exactly the old or the new state; the 16 hostile images recover on a real file in a real process as the reference says, and a second restart writes nothing. It finds the `journal_crash` example the same invocation built, fails closed (reported BLOCKED) if it is absent, and never falls back to a stand-in |

**Verification status.** The Python reference, its battery, the mutants and the vectors run on the host. The Rust crate
and the process-restart cases have not been compiled or run by their author; they run only through the centralized path.
A pass of the cut-point oracle is a result about this model of the medium; it says nothing about a particular flash part.

## 10. Consumers (not done here)

* **N02:** its `SecretStore` and `PeerDirectory` map to the credentials namespace, with the same tombstone rule; its
  persisted revision or epoch high-water mark is a mark. An adapter is N02's to write against `Journal`.
* **G01:** `DurableVoterRecord` is a record (≤ 256 bytes today; its encoded size must be checked against that bound) and
  its epoch a mark.
* **P02:** the real `Storage` over the board's flash or a file, behind the platform layer.
* **E05:** which path persists across a reboot on each image (boot-hook and rollback semantics) decides where the two
  segments live.
