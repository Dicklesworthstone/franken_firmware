# T01 contract: native Tailscale protocol and resource feasibility (`ffw-32a`)

Status: **study with a negative-for-now outcome; nothing built, nothing measured on a target.** What exists is a frozen profile (`docs/tailscale/profiles.json`), an evidence
ledger of verbatim primary-source excerpts (`tests/tailscale-fixtures/evidence/ledger.json`), synthetic fixtures (`tests/tailscale-fixtures/synthetic/`), the rules and source probes
(`tests/t01/`), the entry point `scripts/e2e/t01`, and the narrative `docs/tailscale/feasibility.md`. The bead stays **open** for its owner to close: section 10 says what is not claimed.

A negative result closes the investigation only (the bead's own rule); **this candidate study is INCOMPLETE and pending: the T01-X01 compile attempts built as type-checks only (nothing was linked or run) and the T01-X02 on-target figures are blocked, and nothing here claims it is closed or moves those items to another bead.** The native requirement stays required: this study neither waives it nor satisfies it, and it does not close T02 (native
implementation), T04 (development admission) or Q06 (external qualification). T04 is provisional development admission; full native qualification is a separate Q06 result after
implementation and combined tests.

## 1. Scope

Endpoint identity, control registration, discovery, NAT traversal, relay and key rotation feasibility beyond WireGuard encryption alone, on the two retained-kernel families: PowerPC
32-bit big-endian (stock Linux 2.6.14, nominal 32 MB) and MIPS32r2 big-endian (stock Linux 2.6.35, nominal 128 MB). Both kernels are **unqualified** (E03: no matching full-system
guest exists); the Debian 4.9 (PowerPC) and 4.19 (MIPS) QEMU guests are separate harness rows and are never evidence about a stock kernel. Offline work only: the sources were fetched
read-only and are pinned by commit or exact version; no tailnet, account, device or provider was contacted.

## 2. Definitions

Native support (the bead): each node enrolls under its own identity, receives network state and applies access policy; its control and data planes interoperate with the owner's
tailnet. A userspace WireGuard tunnel by itself does not implement Tailscale membership (ledger T01-E45). The classes a candidate can have, derived from its facts by `classify`:

| class | meaning | counts as the native implementation? |
|---|---|---|
| `native_strict_rust` | a strict-Rust process with its own tailnet identity, control plane and data plane | only if every behavior is `supported` on the target, which needs a run on the target |
| `official_reference` | the same, in another language (the Go client) | never: it is the reference for behavior, not strict Rust |
| `wireguard_only` | a WireGuard data plane with no control plane | never (no membership) |
| `wrapper` | rides on another daemon on the same device, or embeds another runtime | never |
| `gateway` | access through another host's identity | never; named separately, as the bead requires |
| `control_server_only` | a coordination server | never |

No Go reference client or gateway counts as a strict-Rust native implementation. `tests/t01/cases.json` holds twelve hand-written facts-to-class rows, including the unclassifiable ones.

## 4. Rules

* `classify(facts)`: the table in section 2; an unrecognizable fact set is an error, not a default.
* `derive_cell(behavior, platform, extensible)`: a platform that cannot run the candidate is `incompatible` whatever it implements; a `partial` or `not_implemented` behavior is
  `implementable_upstream_work` only where the gap can be closed in a code base we can extend, else `incompatible`; an `unknown` behavior is `no_evidence`; an `implemented` behavior is `supported`
  **only** when the candidate has run on the target (`ran_on_target`, with a receipt), otherwise `no_evidence`. `not_applicable` (a gateway on a speaker) is not a verdict about the speaker.
  An incompatibility that rests on a stock kernel release must say so (`conditional_on`), because that release is reported, not verified.
* `budget_verdict(measured, cap, reserve_floor, reserve)`: a reserve below the 4 MiB floor is invalid; no measurement is `pending`; no cap is `pending`; a unit mismatch or a measurement
  without a receipt is invalid; otherwise `pass` only if `measured + reserve <= cap`. No admitted numeric RAM cap exists until the shared budget is allocated, so absent budget is pending, not pass,
  and every figure in the profile is pending, not applicable, or an explicitly labelled observation that is not a footprint. No native footprint is promised before a complete configuration has been measured.

## 5. Synthetic fixtures and what they assert

`tests/tailscale-fixtures/synthetic/` holds a synthetic identity set (placeholder keys, `.invalid` names, tailnet-range addresses), a network map, a relay map and a key-expiry timeline. Nothing in
them is a real key, device, account or site. The expectations in the files were written by hand from these sentences:

* Packet filter: default deny; a packet is allowed only if some rule matches its source, destination, port and protocol; `*` matches any. Twelve hand-written decisions.
* Route: `direct` if the direct path works; else the peer's home relay region if it exists and is reachable; else the reachable region with the lowest measured latency; else `unreachable`. Nine cases.
* Key expiry: an expired key stops the endpoint's connections until it reauthenticates (official documentation, ledger T01-E10); the expiry instant itself is expired; an expired key wins over every
  other condition. The warning window (7 days), the offline bound on a stale network map (1 day) and the refusal to judge expiry on an untrusted clock are **provisional policy of the native design**,
  decided for the first time by T04, not Tailscale behavior and not measurements. Twelve hand-written steps.

## 6. What cannot be done locally (blocked, never passed)

* **T01-X01, the legacy-ISA build probes.** The contract asks for two attempts on each legacy target (`powerpc-unknown-linux-musl` and `mips-unknown-linux-musl`, separate runs): the check of the seven
  core crates AND the same check of the whole library (`-p tailscale`), "expected to stop at the first crate that does not build; the receipt names it". Both are `cargo check`, a type-check, and both
  are judged from the CAPTURED LOG of a central run, committed redacted under `toolchain/results/tailscale/builds/*.log`. The runs are root's, on its strict-remote lane, from one synced root that holds
  the pinned tailscale-rs tree, the consumer workspace (`x01_core`, which depends on the seven core crates and nothing else) and the cargo-resolved lock for it (`tests/tailscale-fixtures/x01/consumer.lock`,
  sha256 `89b750bec181a50442b5663f804b34911d706c4b8156778aea3ead94810f52ea`, 183 packages, 163 crates.io). **Core:** `rch exec --source-content-receipt --worker W -- cargo +nightly-2026-08-31 check --locked -Z build-std=core,alloc,std,panic_abort -j1 --manifest-path Cargo.toml --target {triple} -p x01_core --message-format=json`.
  **Whole library:** the same with `--manifest-path tailscale-rs/Cargo.toml -p tailscale` (the upstream workspace under its own lock, which is part of the pinned tree). The capture wrapper writes
  `COMMAND: <json argv>` as the first line and then rch's stdout and stderr. The judge (`judge_build_record`) reads that log and nothing else, never anyone's account of it:
  the command and the executed remote command (an allowlist: `check`, `--locked`, the pinned toolchain and build-std set, one of the two pinned package selections with its manifest, one pinned target,
  json messages; any other argument, any `--config` that is not one of rch's own or the pinned C compiler configuration below, and any environment variable that changes the build fails); rch's source content receipt (the sha256 of every synced file,
  held against the four pinned consumer files, the tailscale-rs tree digest RECOMPUTED from the recorded list and held against the pin, and no cargo config, toolchain override or build script in the root or
  in `x01_core`); cargo's artifacts (every crates.io crate from the crates.io index, for the core attempt in the lock or in the toolchain's own std set, every path package inside the synced root, nothing under
  the other target); and the terminal result, three witnesses that must agree: cargo's build-finished message, rch's exit and the receipt's exit code. **A BUILT attempt** has success, exit 0 in both,
  one Finished line and no error, and must show a library artifact for each of the seven core crates (and for `tailscale` in the whole-library attempt), `x01_core` (core attempt), build-std's `core`,
  `alloc`, `std` and `panic_abort` and the `compiler_builtins` 0.1.160 fingerprint of the pinned toolchain. **A STOPPED attempt** has failure in all three (build-finished false, the same non-zero exit in
  rch and the receipt, no Finished line); it is a valid record that keeps its stop, named by cargo's own error line and classified only from the log's text: `missing-c-toolchain` when a build script
  reports that cc-rs cannot find the target's C compiler (the tool is named), which is a toolchain blocker and not an ISA or source finding; any other stop is `unclassified` and is read as neither.
  **The C compiler for the MIPS whole library.** aws-lc-sys's build script needs a C compiler for the target, and the workers have none for MIPS (the first MIPS whole-library record stopped there). The
  adapter run sets it through exactly three explicit cargo env keys, one `--config` argument each (`env.CC_mips_unknown_linux_musl.value="<wrapper>"`, `.relative=true`, `.force=true`), naming one of three
  pinned wrapper files that root syncs beside the tree under `x01-cc/`: the repository's own `toolchain/linker/zig-cc-mips-be` (sha256 `b0d60bcb217f48b552807e09688aa14c8eae78c930976b720d2fe91b2a14723d`) and an adapter
  `x01-cc/zig-cc-mips-be-ccrs` (sha256 `17848d169db2dc71d048a13999c8a605104b6b77d3e846b2359039ab725bfa8d`, committed as `tests/tailscale-fixtures/x01/x01-cc/zig-cc-mips-be-ccrs`; kept unchanged, its recorded build stands) and its hardened
  successor `x01-cc/zig-cc-mips-be-ccrs-v2` (sha256 `3dc93ff4f618cd96f1a8f4dbe68b0f37a9712778d3bf0f3f6e3d634eb61e64ab`, committed beside it). All enforce Zig 0.14.1 (any other
  Zig exits 97) and Zig's big-endian o32 soft-float target `mips-linux-musleabi`. The first passes through the Rust `--target=` spelling that cc-rs appends, which Zig cannot parse; the second drops exactly
  `--target=mips-unknown-linux-musl` and `--target=mips-linux-musleabi` and refuses `--target=OTHER` and `-target` (exit 98) but forwarded the bare two-argument `--target OTHER` and `-target=OTHER`, which
  the broader wording "any other override" should have covered (it did not affect the recorded cc-rs invocation); the third refuses all four spellings (exit 98). The judge accepts the configuration only for the whole-library attempt on MIPS, only as exactly
  those three keys for a pinned wrapper path, only when the synced file list carries each wrapper at its pinned sha256 and no other file under `x01-cc/`, and no other `--config` argument at all. The one-argument
  inline-table spelling is refused by cargo and is accepted only as the record of that refusal; a log that claims to have built with it does not hold. Cargo may refuse before it builds anything: a log with no cargo
  message, the same non-zero exit in rch and the receipt, no Finished line and an error line is a valid stop (`cargo-config-rejected` when the error names a `--config` argument this very command carried).
  A second class is read from the same kind of text: `c-compiler-rejected-target` (a build script failed, cc-rs reports that the compiler command failed, and the compiler said it cannot parse the very
  target spelling of the command). Every stop of an attempt stays in the account, also when a later run built it. PROVENANCE LIMIT: the successful log does not show the compiler being run; that Zig 0.14.1
  compiled the C sources rests on the pinned wrapper file (which enforces it), the three keys that point cargo at it, the synced file hash that says which file it was, and the earlier records of the same
  attempt without it. The adapter's behavior is tested with a stand-in `zig`; no real Zig is run here.

  crates and the whole library for both triples and finished with exit 0. **What it is not:** a link, a run, a memory or CPU figure, an enrollment or a native endpoint; T01-X02 and the native
  requirement are untouched. LIMITS: the log is not signed, so a log edited consistently everywhere is indistinguishable from a real one; rch's own `receipt_root`, `content_root` and `command_sha256` are
  recorded, not recomputed; the separate status file and any custody note are not used; for the whole-library attempt the judge does not re-derive the closure against the upstream lock (`--locked`
  and the pinned tree digest, which includes `tailscale-rs/Cargo.lock`, carry it). The earlier unrun lines against the whole upstream workspace with `-p ts_keys ... -p tailscale` are replaced by the above.
  The historical receipts under `toolchain/results/tailscale/receipts/` still record X01 as BLOCKED for lack of a build record, and are kept exactly as they were.
* **T01-X02, memory and CPU on the target.** There is no 2.6.14 PowerPC or 2.6.35 MIPS full-system guest, so no honest on-target figure exists. A harness-guest run (Debian 4.9 / 4.19) is indicative only

## 10. No claim

* The pinned core and whole-library type-checks pass on both legacy ISA targets. No client ELF is linked or run, and no footprint, CPU or latency is admitted. The profile's measurements remain pending or not applicable.
* No claim about the stock kernels beyond what E03 says (reported, unqualified); the incompatibilities that rest on them are marked conditional.
* No claim of provider or tailnet behavior: nothing enrolled, nothing connected. Fixtures are synthetic and prove the models, not Tailscale.
* No claim that any crate is *portable*, *OS-free*, *correct* or *audited for our use*, or free of the `unsafe` and `rand`/`chrono` boundaries named above; only that the listed crates have no intra-workspace edge to the runtime, OS or TLS allowlist, while the third-party closure (for example `libc` through `getrandom`) stays unqualified until a selected Cargo graph and build.
* No claim about tailscale-rs main after v0.6.1, or about any other Rust or WireGuard implementation (none other was pinned).
* Open for T02/T04/Q06: a reactor strategy (tokio-free I/O over the P02 platform layer), the TLS backend question, NAT traversal and key rotation (upstream or ours), the unsafe review, and the shared RAM budget.
